# Per-SoC parameter sheets

The rest of `rockchip-npu-notes` describes the RK3588 NPU. Most of it is
**IP-inherent** — true of the rknpu/NVDLA-derived block on any Rockchip SoC that
carries it: the matmul-as-1×1-convolution model, the CNA→CORE→DPU sequence, the
precision-field encodings, the BS/BN/EW/LUT datapath, the tile-layout algebra, the
"no on-chip layout conversion" and "no hardware gather" facts. Those do not change
from chip to chip and are stated once, in the subsystem docs.

What **does** change per SoC lives here, one sheet per chip:

- **Machine parameters** — CBUF banks and bank size, the matmul tile cap, the
  weight tile-group sizes, the usable-datatype menu, the core count. These are the
  values `rocket-userspace`'s `rocket_hw_profile` collects.
- **The register offset map** — the numeric CNA/CORE/DPU register offsets. These are
  IP-**revision**-specific, not shared across every Rockchip NPU: the RK3576 NPU
  re-packs the CNA block relative to the RK3588 (see [rk3576.md](rk3576.md)). The
  *block bases* (CNA at core+0x1000, CORE at +0x3000) and the register *semantics*
  are shared; the within-block offsets are not.
- **SoC integration** — physical base addresses, clocks, resets, power domains,
  IRQs, IOMMU wiring. Pure device-map facts.

| RK3576 | 2 | Runs on hardware. Its int8 **direct** conv encoder computes bit-exactly across a swept geometry envelope, with every boundary closed by construction. Its fp16 convolution computes bit-exactly too and delivers every output channel — `rocket_rk3576_plan_ic()` splits an arbitrary `ic` into the 16-channel slices one task contracts, bit-exact against a CPU model at `ic` 16/32/64/128, `k` 1/3/5, planes to 56x56 — at `ic/16` submits. One bound sets the envelope: the DPU's output element stride is `16/ic` words, so 16 is the contraction width at which an element lands in its own two bytes. Its **first conv** — a packed image of four or fewer channels, which is a different CNA program rather than the same one at a small channel count — computes bit-exactly in fp16 over image channels 1-4, kernels 1-7, both strides and planes to 224x224 — the stem a vision model opens with, which has no single-task plan and runs through the row window, on a float weight cube of four lanes per (output channel, tap); one such program delivers 32 output channels and no more, so the library splits the output channels around it. Its **int8** form computes too, so a QUANTIZED stem runs and is the one to use — 3.6 ms against the fp16 form's 13.25 ms at the same 224x224 stride-2 shape, because every wide-output program on this part poisons its next submit and pays a power-cycle guard on every call after the first, while an int8-output one has no such hazard. The int8 cube was read off the part rather than out of a capture — one byte per weight, output channels grouped by 32, the tap row outside that group and the tap column folded in beside the four lanes — and one int8 program delivers 64 output channels where one float program delivers 32. Three geometry bounds come with it and two are silent, so all three are refused: a non-zero left pad (`CNA_PAD_CON0` bits[15:8] alone decide whether the DPU writes at all), an output width of exactly `iw/stride`, and an output width that is also a multiple of 16 — jointly the ONNX symmetric-SAME convention. A fourth is the INPUT ZERO POINT and it is on the BORDER alone: at a non-zero one the interior stays bit-exact while the padded taps do not, where the direct path is exact everywhere at the same zero points, so the shape is refused until `CNA_PAD_CON1`'s domain on this sub-encoding is decoded. One image channel is not among them: the emitted program will not fetch a one-byte-per-pixel row, since the feature DMA's width field carries `line_stride - 1` and that is right only from ic=2 up, so the entry programs a single channel as TWO — a zero lane against zero weights — bit-exact to 224x224 with ic=2's envelope. What broke it open was submitting a captured op stream VERBATIM: a register-identical emitter wrote nothing at every geometry tried and a leave-one-out revived none of it, while the vendor's own program wrote its whole surface — so the mode worked and the extrapolation away from the captured geometry did not. The CNA converter's offset registers are inert, so the packed image is plain two's complement and the input zero point folds into the coefficient `A` term. The fp16 register program is NOT the int8 one at another precision: there is no kernel-width channel fold, the CBUF entry count loses that fold's lookahead granule, the row stride takes the element size and the CVT is bypassed — and one vendor float value, the BS operand reader `0x501C`, makes the DPU write nothing at all when emitted against this library's coefficient group, so a capture is an oracle for a whole program rather than for a register spliced into a different one. Its **depthwise** conv computes bit-exactly too, over channel counts 8-256 (including non-multiples of 32), kernels 1-7, both strides and odd planes — its registers came from manufactured captures, but its coefficient group and int8 weight cube are neither the direct path's nor in any capture and had to be read off the part. **Matmul** computes at int8 through `rocket_matmul_int8_rk3576()`, whose output is int8 through the DPU's requant. K past one task's contraction is SPLIT, through the 32-bit writer: its budget is one 16-byte atom per (16-channel block, pixel) whatever the OUTPUT element width is, so most channels never reach DDR, and a wider programmed `oc` plus a weight-cube scatter turn the surface back into a plain cube — bit-exact to K=16384. What the budget IS a function of is the DPU's own operand width, and widening it halves the scatter to 2x, which doubles the N tile and halves the submits. A row task's output surface is bounded at 8 KiB, and that bound is over the whole PLANE — `iw * oh_full * oc_prog < 4096` — which a row split can honour only by shortening `oh_full`: on a shape whose plane comes out `Mx1` a cap stated in rows alone is met by every task while the surface is M times over, and the wide writer then returns a silently part-right matrix on most natural shapes. Stated correctly the bound costs that writer exactly the submits its wider N tile was reached for, so the planner takes the narrow one on all 315 shapes of an M/K/N sweep, and a plane too wide for even a one-row task is refused rather than run. BOTH writers intermittently emit atoms as zeros, and the rate is a property of the MEMORY SYSTEM rather than of the program: it goes from 11% of row tasks to 45% under host streaming-memcpy load, while the count of atoms never emitted at all — the poisoning — does not move, which is what separates the two hazards. A dropped atom and a legitimately zero accumulator are the same bytes and repetition does not tell them apart, so the library settles them against the arithmetic: a sentinel makes "never emitted" a per-atom fact, the task is redone once, and from the second attempt the zero atoms' accumulators are computed on the CPU over that K slice and the surface kept only if they really are zero. **The poisoning is ONE hazard and every wide output carries it**: measured with a canary that separates a dead program from a poisoned one, the fp16 first conv, the fp16 direct conv and both int32 writers each leave the next submit of any kind writing nothing, while all three int8-output paths leave it alone — one output byte never carries it and wider always does. A sacrificial submit does not absorb it, and the register condition is decoded by a JOINT sweep rather than a leave-one-out: the int32 writers carry it in one register (DPU `0x4010`'s `out`) and the fp16 path in two bits TOGETHER (DPU `0x4038[4]` and `0x4050[17]`, neither doing anything alone, which is why every one-at-a-time sweep came back empty) — but those two bits ARE the float arithmetic, so no non-poisoning fp16 encoding exists and the guard can only be paid for. What is decoded is the price: the guard tracks `power/autosuspend_delay_ms` at twice the delay, and lowering that system-wide is NOT free — a resume costs ~230 us and every job whose inter-job gap falls between the new delay and the old pays it, a 60 Hz frame interval included. So the library DRIVES the power cycle instead of waiting for it: write a zero delay, poll `runtime_status` until it reads `suspended`, restore the caller's value. At the stock 50 ms delay that takes the fp16 stem from 226 ms to 13.25 and the int32 matmul gate from 16.2 s to 9.9, with the steady-state policy every other consumer sees unchanged. The cycle clears the hazard about 87% of the time, so what makes the guard reliable is the NUMBER of redos rather than a better cycle: over twelve fp16 gate runs the redo fired on 358 row tasks and the attempt that failed next was attempt 2 for 45 of them, 3 for 10, 4 for 2, 5 for 1 and 6 for none, every cycle confirmed to have reached `suspended` first — so a cap of four leaves about 0.6% of retried tasks failing outright and eight leaves none. A task that reads unwritten really is unwritten: a 2 ms settle before the redo rescued 0 of 67 of them while the power cycle recovered all 67. The coefficient group's asymmetric `B` term is settled: the DPU ADDS `B*sum(x)`, so a weight zero point is programmed negated. **The op library reaches this part**: `rocket_conv2d_int8_rk3576()`, `rocket_conv2d_dw_int8_rk3576()` and `rocket_conv2d_fp16_rk3576()` take row-major tensors and own the cubes, the row plan, the output-channel split, the de-scatter and the submit-loop retries, and the two public entries whose semantics the part computes — `rocket_conv2d_dw_int8()` and `rocket_conv2d_fp16()` — dispatch there. Their envelope is WIDER than the single-program emitter's by a decoded amount: the weight-slice cap is keyed on the output-channel groups one program drives, so splitting those raises the slice the part accepts and fourteen refused shapes compute, `ic*kh*kw <= 4608` becoming about 5600. Zero points are folded exactly and gated. The per-submit floor is the driver's completion poll rather than the silicon, and is settled at 439 us — against 1654 at the stock 1 ms, 3.77x. What bounds it is not the poll rate: `PC_DONE` fires before the DPU's writes have drained, so the per-job IOMMU detach faulted writes still in flight (fixed by keeping the domain attached) and the fence was signalled before the writes were visible. Both halves are closed. The visibility one is closed by retiring on the DPU's own completion — `RAW_STATUS` `DPU_0`/`DPU_1`, what the RK3588 takes as its interrupt, which sets 82-343 us after `PC_DONE` here, scaling with the bytes in flight — which lets the period drop to 50 us. A task whose DPU output element is wider than one byte raises no DPU completion at all, so the wait is bounded and those retire on `PC_DONE` after a grace period. That grace is a deadline rather than a settle, so it also covers the drain of every job that DOES raise a completion — a narrow-output matmul fails 10 runs of 10 at 200 us and none at 250, and the drain reaches 745 us on the int8 stem at 224x224 k7 s2 — which is why the default is 500 and not the 250 the fp16 path would prefer. **The host cube scatter was most of the wall, not the submit**: packing row-major tensors into this part's cubes an element at a time through the index functions cost a divide, a modulo and a call per byte, which at K=N=1024 was twelve of that matmul's thirteen milliseconds. At `kh=kw=1` three of those scatters are contiguous runs at both ends, so the matmul's feature pack, weight pack and output de-scatter became blocked memcpys, and the convolution entries — a real CHW-against-NC1HWC2 transpose — hoisted the per-element division out to one pair per channel. Bit-exact throughout, and against a single-threaded scalar CPU reference the matmul went 1.0x to 2.6x at M=32 and 6.0x to 12.9x at M=256, the 1x1 convolutions 2.2x to 5.3-21.7x, the 3x3 direct convolutions about double, and depthwise 1.4-1.6x to 2.1-2.9x. **The CHW <-> NC1HWC2 transpose is a 16x16 NEON block, and eight live vectors is the point**: written as one array of sixteen `uint8x16_t` it needs thirty-two registers with its scratch, so the compiler spills the array to the stack and it measures 3x slower than the same transpose done as two 8x8 halves plus a swap of the off-diagonal quadrants. The full-group predicate is a constant argument to one `always_inline` helper, so one source yields both the unpredicated sixteen-channel loop and the partial-group one; a runtime per-lane predicate costs 10-25%. On the graph it is 1.41x and bit-identical — 30.1 ms to ~21, feature scatter 10.91 to 4.94 and de-scatter 7.90 to 5.30 — which makes the SUBMIT the largest single bucket at 41% for the first time on this path. What is left in those two buckets is the bytes and not the loop: the de-scatter's PREP_BO drain is only 0.53 ms of its 5.3, and at ~5 MB each way both run at 2.1-2.4 GB/s against this part's single-thread memcpy ceiling of 4.4. **A tensor then stays in CUBE LAYOUT between consecutive layers and both buckets go**: a direct conv's output surface stride is `ow*oh` exactly and a feature cube's channel-group stride is `ih*iw`, so layer n's surface IS layer n+1's cube byte for byte whenever the plane and the channel rounding agree. Three refusals bound it — more than one output-channel tile (each owns its own surface BO), a padded surface stride (the depthwise path writes `round4(ow*oh)`, so 7x7 breaks and 112/56/28/14 do not), and an input channel count that is not a multiple of 32 (a handle's own cube relies on the zero it memset into the padding channels) — and the linking has to be a pre-pass over already-packed handles, since a producer that skipped its de-scatter for a consumer that then refused the cube would have left no row-major tensor at all. 24 joins of 30 layers, 20.9-21.4 ms to 11.9-12.3, 1.73x, on the same 40 submits, with the de-scatter bucket down to 0.8 ms and the SUBMIT at 62% of the library time. The convolution entries' WEIGHT side was still per-element after that, and running a graph rather than a shape is what showed it: the per-output-channel filter sums and the weight cube scatter were 90% of the layers that cost most while the submit was 1-3%, and straightening both took the graph from 146 ms to 115. A graph's wall is host arithmetic over the WEIGHTS, not dispatch -- the whole inference is 40 submits, and the three most expensive layers are 5, 1 and 1 of them. **Packing a layer's weights ONCE through a handle then takes 65% of what remained** -- 98.8 ms to 33.6, 2.94x on the same 40 submits, bit-identical (`rocket_conv2d_int8_pack_rk3576()` / `_prepacked_rk3576()`, one code path with the per-call entries rather than a second implementation, since a transient call builds the same handle and packs each output-channel tile as its loop reaches it). Only 29 ms of that 65 is the weight arithmetic the profile predicted, and **closing the profile's accounting is what found the rest**: the profiler ended at the de-scatter while the BO teardown happens after it, so 16.1 ms per inference -- unmapping a megabyte-sized dirty mapping per tile, per layer, per inference -- had been attributed to nothing at all. The feature bucket then halved with its scatter loop untouched, because 16 of its 28 ms were the allocation, the zeroing memset and the two cache ioctls, which settles the open question the other way: the feature pack was not mostly the scatter, it was the buffer. A handle freezes its fd (a BO belongs to its file and an IOVA is per-fd, so a foreign fd would submit successfully against meaningless addresses and is refused), its output-channel tile (the cube's group count follows the tile) and its quant contract. Gate residency against the ARITHMETIC rather than the wall: 173 shapes through pack plus TWO prepacked calls compared element for element, two because the second call is the first to reuse a held cube and a held surface. The rest of the op library has no encoder for this part and REFUSES rather than emitting the RK3588 program, which this part completes without writing anything. Batching a tile's row tasks into ONE submit — the obvious way to amortize a 439 us floor paid once per row window — does not run: a drm task descriptor carries ONE PC program whatever the regcmd stream holds, because the driver programs `PC_TASK_CON` with `TASK_NUMBER = 1` per descriptor, so task 0 lands and task 1 is the first missing, deterministically, on every attempt with the power domain confirmed cycled between them. Collecting it is a kernel patch (the RK3576 analogue of the RK3588 series' batched submit) rather than a userspace change, since the driver already runs multiple drm tasks back to back but each through its own completion poll, and the poll is the floor. The part has TWO cores, and the second one is a hazard rather than a lever: it binds, reads core 0's version word and runs jobs, but two worker fds are worth 1.3-1.7x on ONE core as well — the gain is submit pipelining, since a single core is not saturated by one fd at a 439 us floor — and two rocket jobs IN FLIGHT AT ONCE compute wrong answers on 96-100% of calls, grossly, over as much as 94% of the surface. The condition is simultaneous EXECUTION, and the correspondence is one to one against a driver-side count of jobs that started while another core had one in flight — read that counter rather than `runtime_active_time`, which reads full on both cores in every cell because both stay powered. The window is the job's own 439 us submit (delaying one worker: zero wrong from +750 us), and it crosses processes, so no userspace mitigation exists. Four mechanisms are refuted: residual per-core state (the serial cell is clean, including with differing weights per worker, which is the cell that can see an operand swap), the two register banks being one aliased twice, the IOMMU domain (separate MMUs, and forcing every context onto one shared domain still corrupts with zero domain swaps), and the vendor's RK3576-only `state_init` plus its `pc_dma_ctrl` serialization applied as a whole delta. What is left is a shared datapath resource. Holding one worker fixed and sweeping the other's footprint names it as the CBUF feature staging area — the trigger is not capacity (a four-granule aggressor still corrupts three quarters of the victim's calls) and the extent is the feature plane specifically, not the weight cube and not how long the intruder held anything. But PLACEMENT does not separate the two cores, so the collision is not two jobs writing the same granules. The CBUF base is a real, honoured address — the low half of `0x103c` and `0x1040` is a granule offset, and a task computes at every base up to `4096 + F - plane` and fails 64 granules past it, at four planes measured — and moving one job's staging fully clear of the other's plane leaves the corruption flat at 68-78%, with the overlap counter non-zero throughout and a base past a job's own bound taking it to 100% self-wrong as the positive control. Nothing else in `CNA_CBUF_CON0` is a bank base (bits 30-31 inert, bit 29 live but corrupting), and the NPU GRF carries no per-core CBUF field at all, only a shared 16-bank clock gate. So no userspace-reachable partition exists and an address partition would not have helped; what fits every measurement is contention on a shared feature-write path rather than shared storage, NVDLA giving the CBUF separate feature and weight write ports [hypothesis]. It is not a silicon impossibility — the vendor schedules independent jobs on both cores by design — but nothing an encoder emits reaches it. They also share ONE power domain, so the wide-output poison guard must suspend EVERY bound core: the domain collapses only once both are runtime-suspended, and a guard that waited on the first device let poisoned submits through. **A WHOLE NETWORK runs**: MobileNetV1-224 at int8, 27 convolutions plus a PPU pooling layer and a classifier, every one of the 29 compute layers bit-exact against a CPU model of the part's own arithmetic, **about 12 ms per inference with resident weights and the tensors kept in cube layout between layers** (21 ms with the transposes at every boundary, 115 ms with no resident weights at all), returning TFLite's own top-1 and whole top-5. Against TFLite the graph differs on 0.095% of elements and every one of them by a single count — that residue is the requant rather than a defect, since this DPU's OUT_CVT carries a 15-bit multiplier and rounds ties to even where TFLite carries 31 bits and rounds half away from zero, and the ranking survives what the last bit does not. Running the graph found three things a per-op gate structurally could not. **Two CBUF F rungs deliver only at `kh == 1`**: 256 and 512 were characterised on a k=1 plane, and at any taller kernel each delivers 4096 granules — the F=0 budget — so a task the planner puts on one writes a full surface with a wrong tail; measured at one granule total across five plane widths, k=1 exact at every width and k=3 wrong at every one, with the delivered budget backing out to the row from the surviving prefix. Nothing in the correctness envelope had reached them, because every shape in it sits at F=0. **TFLite's SAME padding is asymmetric, and it is an OUTPUT EXTENT rather than a materialised border.** The CNA takes no configured trailing pad — it DERIVES the pad its last window consumes from the output extent and the leading pad — so a stride-2 SAME convolution over an even plane is a leading pad of ZERO against an extent one larger than the symmetric formula gives, and nothing has to be copied. That geometry was already inside the int8 correctness envelope, in six swept shapes; what kept it out of a graph was the descriptor, which could only say "derive the output from a symmetric pad", and the row-major buffer it forced is what broke the cube chain at every stride-2 depthwise layer. `rocket_conv2d_desc.oh/.ow` now name the extent (zero meaning the symmetric derivation, so nothing existing changes) and the bound is the KERNEL: a trailing pad of `kh` or more is an output row whose whole window is pad, and it is refused, as is an extent the fp16 and RK3588 paths did not derive themselves. And **a TFLite stem does not satisfy the int8 first conv's bounds directly** — TFLite's SAME stem has `pad_left = 0` — so the network runs its stem on the direct path with the image widened to eight channels, the added ones holding the input zero point against zero weights, which is exact for any zero point. **It IS reachable though, by moving the input rather than the pad.** "A stride-2 sample grid's parity cannot be moved by padding" is true and incomplete: the grid also moves when the input moves, and an input shifted one pixel against a pad of one is a shift of TWO — a whole stride. Extend the image by TFLite's trailing row and column, feed the program that buffer from row 1 column 1 with both register pads at 1, and 394272 of 394272 interior outputs are bit-exact against TFLite's own grid; what is left is the output's top row and left column, 1.8% of the surface, whose outermost taps read the pad constant instead of image row 0 and column 0. Wired into the graph behind a flag and byte-for-byte identical to the widened lowering over all 401408 elements — but against a RESIDENT graph it is a LOSS, 5.5-5.8 ms against the widened path's 3.5-3.7, because the packed-image path has no resident handle (BO teardown alone is 36% of its call) and the host border fix-up is 1.7-1.9 ms for 1.8% of the surface. The earlier "worth ~4 ms" compared it to the widened path TRANSIENT, and resident weights had already collected that; both costs closed it lands near 2.9 against 3.5, so it is a sub-millisecond lever. Off by default, gated either way. Whether the program can express a zero left pad AT ALL is settled at the geometry rather than at `CNA_PAD_CON0`: a non-zero lead and `ow*stride == iw` are jointly inconsistent with a zero lead at k3 s2, so the entry refuses before any register is written. **A depthwise weight zero point rides in the WEIGHT CUBE** rather than the coefficient group, which has no `B` field: every (channel, tap) has two live bytes and the datapath ADDS them, so `w - w_zp` is exact across the pair over [-256, 254]. That is the form every per-tensor TFLite depthwise filter carries, and re-centring in int8 is not available — 12 of that model's 13 depthwise layers overflow it. `rocket_pool_int8_rk3576()` is the library entry over the PPU, a separate entry rather than a dispatch from the RK3588's because that one truncates the average toward zero and this one rounds half to even. **Per-axis weight quantization reaches the depthwise path**, which is the half a real per-axis model is mostly made of, and it is the cheaper half: the 48-byte depthwise coefficient group carries the same per-output-channel int16 C, a depthwise accumulator is bounded by `kh*kw` taps instead of `ic*kh*kw` so the C ramp reaches the int16 field's own ceiling, and one task covers the whole layer because output channel c is bound to input channel c. The worst distance to an exact per-axis requant is 0.5 counts at spreads to 100x and 0.8 at 1000x, against 0.5-1.9 on the direct path, and without the output-channel split the direct path buys its accuracy with. **And per-axis runs as a GRAPH, where the error does not compound**: MobileNetV1-224 with every convolution and depthwise convolution re-quantized per output channel — real spreads of 150x at the stem and 145x, 129x and 105x at depthwise layers — puts every one of the 29 compute layers within ONE count of an exact per-axis requant and returns TFLite's own top-1 and whole top-5. The per-op gate's worst case of 26.6 counts stands where it was measured (a synthetic 100x spread at ic=128 in one tile); a real model does not land there because the planner sizes C against the actual accumulator bound and the wide-scale channels are the small-accumulator ones. The output-channel tile lever is never taken on it — the predicted gain error is 0.003%-0.82% per layer, under the 1% target — so no layer pays an extra submit. **The open `rocket_gem_bo_free` crash is closed, and it was never a BO-lifetime bug**: `rocket_copy_tasks()` frees the submit job's task array on its failure path without clearing the pointer, and `rocket_job_cleanup()` frees it again -- an unprivileged double free of a kmalloc-16 object on any submit whose task array fails to copy or whose `regcmd_count` is zero, which is exactly what a caller hands the kernel when its generator refuses a shape and leaves the descriptor zeroed. One object with two owners, so the damage surfaces anywhere: the two faults it was chased through were a scatterlist walked in `drm_gem_shmem_release()` and a wild `phys_to_virt()` inside `swiotlb_bounce()`, and neither is a defect in those paths. `slub_debug=FZPU slab_nomerge` settles it deterministically -- six "Object already free" reports over three runs of the uAPI error-path selftest before, zero after -- and that selftest exits 0 either way, which is why two sessions of green gates ran over it. The reproducer that never reproduced was evidence about the reproducer: 300 iterations of the BO-lifetime gate and eighteen rounds of the compute gates never fired, because not one of them submits a job the kernel rejects. The RK3588 reaches the same double free identically, and `patches/rocket/087` is now hardware-validated there: six reports over three runs without it and zero with, two per run on both parts, 83 of 83 ctest entries passing on the fixed module under slub_debug. A board whose image ships no kernel headers can still take that A/B -- CONFIG_MODVERSIONS is all a modules_prepare tree lacks, and the CRCs are already on the board in the shipped module's own __versions section. **The DPU LUT's input map is decoded and gated**: `index = (value - LE_START) / 2^sel`, the `0x00020000` table covering `[LE_START, 0]` and the `0x00030000` one `[0, LO_END)` at 512 intervals each, with LE_START (`0x4110`-`0x411C`, four lanes), LO_END (`0x4140`-`0x414C`) and the step (`0x410C`) all live and programmable -- bit-explained against a CPU model at three different steps and at an asymmetric window, 8192 samples a span, max one output count. It interpolates linearly at the full resolution of the step and its domain is half-open at the top, `value == LO_END` taking the overflow clamp. The value it sees is the BS stage's output `(acc + A)*C`, so a caller places each output channel's range inside the window with the same per-channel C a per-axis quantization drives -- which is what the vendor does, and why it never moves the window and why at fp16, where that scale rides the coefficient buffer rather than a register, sigmoid and tanh emit register-identical programs with tables spanning 6.25 and 3.02 input units. What hid all of this was a register in the vendor's own enable set: BN_CFG `0x4060` is `0x20` on every vendor activation and `0x903` in its bare-conv control, and transcribing it pins the LUT at the table join for every input across twenty-two binades while the readout still tracks the table faithfully, so it reads as a working LUT whose input map is in no register. BN is then multiplying by an operand register no vendor program writes, on a part whose register file is not cleared between jobs. The LUT itself is the EW stage -- `EW_LUT_BYPASS`, bit 7 of `0x407C`, the RK3588's field layout at a moved offset. Its table-load program is DPU + DPU_RDMA only and takes `PC_OPERATION_ENABLE` = `0x18`, and the load and the use want to be one job because a separate submit can take a runtime-PM cycle between them. **The LUT is now an op**: `rocket_act_int8_rk3576()` computes sigmoid, tanh, swish, hardswish, hardsigmoid and elu over a row-major int8 tensor, and it is EXACT for every int8 input rather than an interpolation of one — it lowers onto a depthwise 1x1 identity whose weight is the index step `2^sel`, which puts input value q at table index q - in_zp + 512 exactly, so each of the 256 possible inputs reads its own entry and the interpolation never runs. Depthwise because a 1x1 direct identity needs an oc x ic weight matrix, quadratic in the width and past the `ic*kh*kw <= 4608` slice rule at any real one. 180 of 180 cases bit-exact against a CPU model of the chip's arithmetic, at most one count from an exact f(). exp, gelu and sqrt are deliberately absent: no vendor capture emits a 513-entry table for any of them. [porting-patterns.md](porting-patterns.md) is the cross-chip sheet: what the RK3588 and
RK3576 pair establishes about porting to a third part. Which classes of claim transfer
as reliable priors (the datapath algebra), which are coin flips and must be re-measured
(anything downstream of a machine parameter), the six edit operations the register
re-pack is built from, and the method for matching a register by value and function
rather than by offset. Read it before assuming any RK3588 fact on a new SoC.

An IP-inherent fact that turns out to differ on a new chip is a bug in the claim, not
a per-SoC parameter — promote the correction into the subsystem doc and note the SoC
that disproved the old scope. The RK3576 CNA re-pack did exactly that to the old
"register offsets are not SoC-specific" claim.
