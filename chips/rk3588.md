# RK3588 SoC parameter sheet

## Overview

The RK3588 NPU is an [RKNPU](../GLOSSARY.md), derived from NVIDIA's NVDLA, with 3 cores. It is
marketed at 6 TOPS, the int8 convolution peak. The RK3588 is the hardware-validated reference
target, and the other notes describe it unless they state otherwise. The subsystem notes and
[../hardware-overview.md](../hardware-overview.md) describe the hardware in full, and
[rk3588-validation.md](rk3588-validation.md) records how this sheet's facts were established.
Every fact here is [HW sweep] or [source-confirmed] unless tagged otherwise.

The driver is mainline `rocket` drm/accel, with the uAPI `CREATE_BO`, `SUBMIT`, `PREP_BO` and
`FINI_BO` on one `/dev/accel/accelN`. A process uses the cores by opening one fd per core.

## Support status

| Feature | Status |
|---|---|
| int4 and int8 matmul | Supported |
| int16 matmul, int64-exact over full-range operands, as four int8 matmuls | Supported |
| int16 matmul in one task, whose int32 output saturates | Bit-exact on hardware. No library entry |
| fp16, bf16 and tf32 matmul | Supported |
| int8 direct and depthwise convolution, with per-axis requant to int8 | Supported |
| fp16 convolution, and fp16 ConvTranspose | Supported |
| PPU pooling, fp16, and int8 through the fp16 pool | Supported |
| DPU LUT activations, fp16 | Supported |
| Three cores, one fd per core | Supported |

The Known issues table in the [README](../README.md) indexes the RK3588's errata. Erratum E7
is described under [Errata](#errata), below.

## SoC integration

- **Core bases**: `npu@fdab0000`, `npu@fdac0000`, `npu@fdad0000`.
- **Clock**: the compute clock `scmi_clk_npu` (the TRM's `clk_rknn_dsu0`) boots at 198 MHz, the
  vendor `POWER_DOWN_FREQ` served from the GPLL. Every higher rate is `clk_npu_pvtpll`, a ring
  oscillator in the NPU GRF (`0xfd5a2000`) whose frequency follows the rail voltage
  [TRM, HW sweep]. At a 0.80 V rail the 900 MHz request runs at 928 MHz, the vendor's 900 MHz
  OPP, and the 600 MHz request at ~816 MHz [HW sweep 2026-10-19]. Software must raise the rate
  inside the driver, after the power domain is up. See
  [../perf/clock.md](../perf/clock.md).
- **IOMMU**: `rocket` attaches and detaches per job, and each attach re-runs an MMU reset.
  Keeping the IOMMU attached on the same fd saves ~20 µs/submit. See
  [../perf/iova-and-multicore.md](../perf/iova-and-multicore.md).
- **IOVA**: each fd has a 4 GB window. Use N fds for N cores.
- **Bus QoS**: five NoC QoS nodes serve the NPU's AXI masters, and neither driver programs them
  (§"Bus QoS").
- **Hardware version**: PC `VERSION` (`0x0000`), which the vendor driver reads for
  `RKNPU_GET_HW_VERSION`, reads `0x46495245`, ASCII "FIRE", on core 0 [external:
  poad42/opennpu_rk3588, not reproduced here].

### Bus QoS

The NPU's AXI masters have five NoC QoS nodes, which the NPU power domains' `pm_qos` lists
[source-confirmed: `rk3588-base.dtsi`]. They are `qos_npu0_mwr` `0xfdf72000`, `qos_npu0_mro`
`0xfdf72200`, `qos_npu1` `0xfdf70000`, `qos_npu2` `0xfdf71000` and `qos_mcu_npu` `0xfdf72400`.
The vendor driver's RK3588 configuration has `bw_priority_addr = 0x0` [source-confirmed: BSP
`rknpu_drv.c`]. The mainline device tree has all five nodes and no `priority-init` property
anywhere [live 2026-08-21, kernel 7.1.7-1-arm64]. Neither driver therefore programs them.

Under the vendor driver, `priority-init=7` and `mode-init=0` on all five run ~200 KB matmuls
about 2x faster than the unprogrammed nodes do. Matmuls from 1.3 MB up are unchanged [external:
poad42/opennpu_rk3588, see [../SOURCES.md](../SOURCES.md)]. fp16 LLM prefill moves 1.86-1.91 MB
a submit at micro-batches of 128 to 2048 rows [HW sweep 2026-08-21]. The CBUF and the tile cap
fix the tile, so a smaller micro-batch does not bring a submit into that regime.

**Not characterized:** a QoS setting under `rocket`, and the submit sizes of a detection graph.

### Board-level parameters

These values are from the Rockchip RK3588 Hardware Design Guide V1.4 [source-confirmed]. They
describe the platform the NPU measurements in these notes were taken on. The RK3576 differs in
its DRAM bus, its NPU rails and its package, so check [rk3576.md](rk3576.md) before using an
RK3588 number for it.

| Parameter | Value |
|---|---|
| DRAM bus | 64-bit, 4x 16-bit channels, LPDDR4/4X/5, max 32 GB |
| DRAM clock | 2112 MHz (`VDD_DDR_S0` at 0.870 V / 2.50 A / 2.18 W) |
| Theoretical peak bandwidth | ~33.8 GB/s |
| NPU rails | `VDD_NPU` plus `VDD_NPU_MEM` (405 mA, separately regulatable) |
| NPU peak | 0.850 V / 4.00 A / 3.40 W at 1000 MHz |
| NPU main capacitance | > 200 uF |
| Package / θJA | EHS-FCBGA, 8.7 C/W (JEDEC 2S2P reference figure, no heat sink) |

The NPU's memory has its own rail, `VDD_NPU_MEM`. The RK3588 gives every major block its own
memory supply (`VDD_NPU_MEM`, `VDD_GPU_MEM`, `VDD_CPU_BIG0/1_MEM`, `VDD_CPU_LIT_MEM`,
`VDD_VDENC_MEM`). The design guide documents combining it with the logic rail as a
low-power-scenario concession. The RK3576 has no NPU memory rail.

On a Turing RK1 at 928 MHz, 15 minutes of continuous load hold the clock at 922-928 MHz
[HW sweep 2026-10-19]. The NPU stays at or below 49 °C over that run. Longer runs and other boards are not
characterized ([../perf/clock.md](../perf/clock.md)).

## Programming model

### Register offset map

The offset map in Mesa's [`registers.xml`](https://gitlab.freedesktop.org/mesa/mesa/-/blob/main/src/gallium/drivers/rocket/registers.xml), which
`librocketnpu`'s regcmd encoder for the RK3588 is written on, is the RK3588's. The block bases are [source-confirmed: Mesa `registers.xml`]:

| Block | Base |
|---|---|
| PC | `0x0xxx` |
| CNA | `0x1xxx` |
| CORE | `0x3xxx` |
| DPU | `0x4xxx` |
| DPU_RDMA | `0x5xxx` |
| PPU | `0x6xxx` |
| PPU_RDMA | `0x7xxx` |

The offsets within a block are specific to the RKNPU revision. The RK3576 re-packs the CNA
block at the same block base ([rk3576.md](rk3576.md)).

### fp16 matmul arithmetic

**Conditions:** vendor RK1, `rknpu` 0.9.8, each core pinned, 2026-09-27. One shape
(512×384×256), one task, fp16 in with fp32 out.

The fp16 × fp16 -> fp32 matmul follows one host model on every core. Each aligned 32-product
K group is summed exactly and rounded once to fp32, nearest even. The group partials then
accumulate in K order in fp32, nearest even, from zero. The fp16 MAC multiplies each operand
in NVDLA's coarse form, with exponent `max(e,1) >> 2` and the significand shifted left by
`e & 3` [source-confirmed, nvdla/hw `nvdlav1` `CMAC_CORE_MAC_exp.v`, `_mul.v`].

Off output lane n % 16 == 0, the model reproduces every element of every core bit for bit
[HW sweep]. The operands were full-range random, subnormal, softmax-like, zero-free synthetic
and real attention data. Output lane 0 of each 16-channel group differs, as Erratum E7
describes.

### Clock-gating registers

`librocketnpu`'s fp16 matmul program leaves CNA `CLK_GATE` (`0x1090`) and CORE `MAC_GATING`
(`0x300C`) unwritten, and writes `MISC_CFG` `soft_gating` as 0. The BSP driver and 87
captured vendor RKNN programs write none of them either. The undocumented CORE `0x3030` is
written as 0 by `librocketnpu`, by Mesa and by the vendor programs.

`MAC_GATING`'s reset value is 0x07800800. Bits 26:0 are one field, `SLCG_OP_EN`, and bits
31:27 are reserved [source-confirmed: Mesa `registers.xml`]. The field's bits have these effects
on the fp16 matmul [HW sweep, vendor RK1, 2026-09-27]:

| Offset | Field | Bits | Reset | Function |
|---|---|---|---|---|
| CORE `0x300C` | `MAC_GATING` | 11 | 1 | Clocks output lanes 0-7. With the bit cleared, that half writes one constant word per core, and the other half is unchanged |
| CORE `0x300C` | `MAC_GATING` | 23 | 1 | Clocks output lanes 8-15, as bit 11 does lanes 0-7 |
| CORE `0x300C` | `MAC_GATING` | 24 | 1 | With the bit cleared, the job stops |
| CORE `0x300C` | `MAC_GATING` | The other 24 of bits 26:0 | | No effect on this workload, set or cleared |

> [!CAUTION]
> Clearing bit 24 of CORE `MAC_GATING`, or writing the register 0, stops the job. The DPU never
> raises its completion, and the driver resets the core.

The lane-0 events of Erratum E7 are independent of these registers. No swept value of
`CLK_GATE`, `soft_gating`, `MAC_GATING` or CORE `0x3030` that completes changes them on any
core [HW sweep, vendor RK1, 2026-09-27]. The exception is `MAC_GATING` bit 11 cleared, which
replaces lane 0 with a constant word. None makes a core agree with another or with the model.

**Not characterized:** multi-bit `MAC_GATING` values other than zero, all ones and the reset
value, and the reserved bits 31:27.

## Errata

<a name="the-three-cores-do-not-compute-identically"></a>

### Erratum E7: fp16 matmul output differs between cores on output lane 0

- **Description:** The three cores compute the fp16 × fp16 -> fp32 matmul identically, except
  on output lane 0 of each 16-channel group (output channel n with n % 16 == 0). There each
  core rarely writes a result below the [host model](#programming-model) (an event), and each
  core has its own set of inputs that do it. An event, decided inside one 32-product K group,
  lowers that group's exact sum by 2^(4·Cmax − 44) before the fp32 rounding. Cmax is the
  group's largest coarse exponent sum over its nonzero products, and the event is bit 6 of the
  group's coarse frame. Which core has the most events is a property of the inputs, not of the
  core. Repeated calls on one core are byte-identical.
- **Conditions:** RK3588, fp16 in with fp32 out. Characterized on a vendor RK1 (`rknpu` 0.9.8,
  each core pinned) at one shape (512×384×256) and one task, with `librocketnpu`'s register
  values. On the tile tested on both, a mainline RK1 (`rocket` 1.3.0) gives byte-identical
  per-core outputs [HW sweep, 2026-09-27]. The outputs are byte-identical at 300 MHz / 675 mV
  and 1000 MHz / 787.5 mV. Integer paths are core-invariant. On int8 tiles with int32 out, all
  three cores are exact and identical [HW sweep, vendor RK1, pinned per core, 2026-09-27].
- **Symptom:** Every mismatch against the model is on lane 0. On the characterization's data,
  where every group had Cmax 7, each event is exactly 2^-16 low for results from about 2^-4
  to 2. On one head's attention AV, a 512×256 output, core 2 writes an event at one lane-0
  element, (256,240), and cores 0 and 1 none. Zero-free synthetic data gave none in about 1.2 million elements per core. A
  result depends on the core that ran it, and the `rocket` driver places each job on a core by
  load. Two runs of one fp16 job can therefore differ on lane 0, and no error is reported.
- **Workaround:** None removes the difference. Lanes n % 16 != 0 compare exactly across cores,
  across runs and against the model. A test that compares fp16 outputs must exclude lane 0, or
  accept two values on it. They are the model's value, and that value with one group lowered by
  2^(4·Cmax − 44), as every recorded event is. An integer equality test compares runs.
- **Status:** Open. Why lane 0 differs, and why the cores' position classes
  ([rk3588-validation.md](rk3588-validation.md)) differ, is not known. A different summation
  order inside the group fits every result, if its mapping is not an index XOR. A different
  rounding position fits them too [hypothesis]. The occurrence follows the group's bits below
  the frame LSB, so an exact predicate needs each core's lane-0 partial-product reduction
  [expected].

**Not characterized:** other shapes, task counts, datatypes and register values, the lane-0
sets on a second board, and the event's size on other data families.

#### Event dependencies

An event depends on these [HW sweep, vendor RK1, 2026-09-27]:

- Every product of the group. Knocking out any single product removes it.
- A zero feature word. 0x0000 anywhere in the group disables it, while -0 keeps it in 20 of
  the 32 lanes.
- The group sum. The event is periodic in it with period 2^-22 and ramps with its residue.
- The operand encoding, not only the products. Each of three re-encodings changes it with every
  product unchanged: ±0 in one lane, one lane as (a×2, b/2), and the whole group.
- The exponent frame. Scaling every weight by 2^±1 or 2^±2 removes every event on every core.
  Scaling by 2^±4 keeps the coarse significands, and keeps every event. Weights scaled by 16 or
  1/16 move the same events to 2^-12 and 2^-20 on every core.
- The coarse significands, not the lane's product. A re-encoding that keeps each coarse
  significand keeps core 2's event. One that keeps the product but moves bits between the
  operands can move it. No function of a lane's (shift, product, sign) is exact.
- Only the lanes with bits below the frame's LSB. Randomizing the one frame-aligned product's
  significand keeps the event, and randomizing every shifted lane removes it.
- A rare coincidence among those lanes. Random zero-free groups, including groups with the
  triggering group's exponents and signs, produced no event on any core. No predicate over the
  group's contents is known.

No permutation of the group's lanes maps core 2 onto core 0. An event needs most of the group:
groups of the frame lane plus one to four others produced no event on any core.

### Erratum E13: a core stops completing jobs after job timeouts

- **Description:** A job that outlasts the driver's 500 ms deadline is retired and its core is
  reset. When the job's DMA is still active at the reset, the core's IOMMU cannot stall, and
  later jobs on that core intermittently never complete. Repeated timeouts end with the power
  controller unable to idle an NPU power domain. The next runtime resume of the core then takes a
  synchronous external abort in the IOMMU's resume path, and the core stays `resuming`.
- **Conditions:** RK3588 (Turing RK1) on mainline `rocket` 1.3.0, kernels 7.2.0-1-arm64 and
  7.2.9-1-arm64, at the 600 MHz and 900 MHz requests. A session in which jobs time out: a
  register program that never raises the completion the driver waits for.
- **Symptom:** First, an output is never written, while its fence signals as if the job
  completed. Next, the kernel log reports `rk_iommu ...: Enable stall request timed out` and a
  warning in `iommu_detach_group` called from `rocket_job_run`, or jobs time out on one core
  only. Last, it reports `failed to set idle on domain 'npu1'` (or `'nputop'`), then a
  synchronous external abort with `rk_iommu_enable_stall` or `rocket_job_run` on the stack. The
  core's `power/runtime_status` stays `resuming`, and tasks wait in uninterruptible sleep. A
  reboot request then hangs after the network stops, and only a power cycle recovers the board
  [HW sweep]. The wedge followed about 27 timeouts in one occurrence and about 560 in another.
- **Workaround:** Software must not submit a program that cannot raise its completion. A sweep
  that expects failing configurations must bound how many can time out. After an IOMMU
  stall timeout on an NPU core, the results of later jobs on that core are not reliable. Stop
  submitting, and power-cycle the board. The `rmmod` recovery in
  [../perf/clock.md](../perf/clock.md) needs every core `suspended`, which a wedged core never
  reaches.
- **Status:** Open. A timed-out job whose DMA is still active, stopping the IOMMU stall and the
  domain's idle handshake, fits every occurrence [hypothesis]. The number of timeouts that a
  board survives is not characterized. A pool submitted without `DRM_ROCKET_JOB_PPU_DONE` times
  out on every submit ([../perf/pool-completion.md](../perf/pool-completion.md)), and how many of
  those a board survives is not characterized either.
