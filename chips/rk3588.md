# RK3588 SoC parameter sheet

The RK3588 is the hardware-validated reference target. This sheet is the per-SoC parameter
summary. The full hardware narrative is in
[../hardware-overview.md](../hardware-overview.md) and the subsystem docs. Everything here
is [HW sweep] or [source-confirmed] unless noted.

## NPU identity

- The NPU is rknpu/NVDLA-derived, has 3 cores, and is marketed at 6 TOPS (the int8-conv
  peak).
- The driver is mainline `rocket` drm/accel, with the uAPI `CREATE_BO`, `SUBMIT`, `PREP_BO`
  and `FINI_BO` on one `/dev/accel/accelN`. A process reaches the cores by opening one fd
  per core.

## Machine parameters

These are the values `rocket_hw_profile` (`rocket_hw_rk3588`) carries.

| Parameter | Value | Notes |
|---|---|---|
| CBUF banks | 12 | `NPU_CBUF_BANKS` |
| CBUF bank size | 32768 B | 12×32 KB = 384 KB per core |
| Matmul tile cap (Mt/Nt) | 256 | the M-independent resident-weight pivot |
| Weight K-group, <=2-byte datatypes | 32 | int8/int16/fp16/bf16 |
| Weight K-group, 4-byte datatypes | 16 | tf32 (4-byte halves it) |
| Weight N-group | 16 | fp16/int16/bf16/tf32. int8 is 32 and int4 64 |
| Datatype menu | int4/int8/int16/fp16/bf16/tf32 | complete. int16 writes a saturating int32 |

## SoC integration

- **Core bases**: `npu@fdab0000`, `npu@fdac0000`, `npu@fdad0000`.
- **Clock**: the compute clock `scmi_clk_npu` boots pinned at 200 MHz (vendor
  `POWER_DOWN_FREQ`). Raising it to 600 MHz is worth ~1.43x. The raise must happen inside
  the driver, after the power domain is up. See [../perf/clock.md](../perf/clock.md).
- **IOMMU**: `rocket` attaches and detaches per job, and each attach re-runs an MMU reset.
  Keeping the IOMMU attached on the same fd saves ~20 µs/submit. See
  [../perf/iova-and-multicore.md](../perf/iova-and-multicore.md).
- **IOVA**: each fd has a 4 GB window. Use N fds for N cores.

## The three cores do not compute identically

The fp16 × fp16 -> fp32 matmul follows one host model on every core, except on output lane 0
of each 16-channel group. There, each core rarely writes a result exactly 2^-16 below the
model, and each core has its own set of inputs that do it.

### The base model

Each aligned 32-product K group is summed exactly and rounded once to fp32,
nearest even. The group partials then accumulate in K order in fp32, nearest even, from zero.
Reversing the group order misses 69% of the random outputs.

Off output lane n % 16 == 0 the model reproduces every element of every core bit for bit. That
is about 39 million elements on core 0, 22 million on core 1 and 70 million on core 2. The
operands were full-range random, subnormal, softmax-like, zero-free synthetic and real attention
data [HW sweep, vendor RK1, `rknpu` 0.9.8, pinned per core,
`rocket-userspace/tools/npu_core_diff_score.c`, 2026-09-27].

### The lane-0 events

Every mismatch against the model is on lane 0, and on the
characterization's data exactly 2^-16 low, for results from about 2^-4 to 2:

| Core | Events over the characterization runs | Events on one re-run set of 33 calls |
|---|---:|---:|
| 0 | 7095 | 3648 |
| 1 | 181 | 160 |
| 2 | 1037915 | 61761 |

On that data every event of core 1's is in core 0's or core 2's set. Of core 0's events, 93%
are in core 2's. The re-run of that set was byte-identical to its first run on every
core [HW sweep, vendor RK1, pinned per core, `tests/npu_core_diff_probe` raw mode, 2026-09-27].

### Dependence on the inputs

Which core fires most is a property of the inputs, not of the core. The characterization's
groups all derive from one attention dot product. A second run holds 1.05 million groups, built
from 64 permuted variants of it [HW sweep, run t2]. On it core 1 fires on
743,682 and core 2 on 578,119. There the sets do not nest. Of core 0's events, 63% are in core
2's set, and of core 1's, 77% are in core 0's or core 2's.

A re-run of 128 of those calls was byte-identical on every core. It gave 37,315 events on
core 0, 48,449 on core 1 and 35,059 on core 2.

The flash-attention element (256,240) sits on lane 0 and is in core 2's set only. Its identity
copy, placed at all 131072 positions of one call, deviates at 8192 of them on core 2. Those are
lane 0 of every row, and it deviates nowhere on cores 0 and 1. Two RK3588s give byte-identical
outputs per core for its tile [HW sweep, 2026-09-27,
`rocket-userspace/tests/fa_core_matmul_probe`]:

| Board | Driver | How the core was known | Core 2 | Cores 0 and 1 |
|---|---|---|---|---|
| Mainline RK1 | `rocket` 1.3.0 | `gpu_scheduler` trace, per job | `3f4d6f30`, 24 of 24 calls | `3f4d7030`, 66 of 66 |
| Vendor RK1 | `rknpu` 0.9.8 | `RKNPU_CORE_MASK`, pinned | `3f4d6f30`, 10 of 10 | `3f4d7030`, 20 of 20 |

### The deciding K group

An event is decided inside one 32-product K group. Permuting the tile's 384 K indices,
applied to both operands, keeps every exact dot product:

| Permutation | Tiles where (256,240) differs between cores |
|---|---|
| None | 1 of 1 |
| Whole 32-, 64- or 128-wide blocks moved, contents kept | 20 of 20 at each width |
| Products moved only inside their own 8-, 16- or 32-wide block | 10, 9 and 6 of 20 |
| Products moved across 32-wide blocks (whole 8- or 16-wide blocks, inside 64 or 128, any) | 1-2 of 20 |

Every row counts tile 0, which is unpermuted. A move inside the group can put the event in
core 0's set instead. Core 0 was the core below the model in 10 of the 25 in-group cases.

Single transpositions of the deciding group (k 32-63) map the sets, 32 repeats each:

- **Core 2**: 37 of 496 remove the event.
- **Core 0**: 24 create one, and every one of them moves lane 5 (k 37).
- **Core 1**: none moves it.
- **Outside the group**: 0 of 341 transpositions and 0 of 704 knockouts or sign flips move it.

### The coarse frame

An event is bit 6 of the group's coarse frame. The fp16 MAC multiplies each operand in
NVDLA's coarse form, with exponent `max(e,1) >> 2` and the significand shifted left by `e & 3`
[source-confirmed, nvdla/hw `nvdlav1` `CMAC_CORE_MAC_exp.v`, `_mul.v`]. An event lowers one
group's exact sum by 2^(4·Cmax − 44) before the fp32 rounding. Cmax is the group's largest
coarse exponent sum over its nonzero products. Every characterization group had Cmax 7, hence
2^-16. Weights scaled by 16 or 1/16 move the same events to 2^-12 and 2^-20 on every core
[HW sweep, vendor RK1, run s13].

Each of 885,667 recorded lane-0 mismatches is one group's event, reproduced bit for bit
[`npu_core_diff_score` with `NPU_CORE_DIFF_ATTRIB=1`]. None is ambiguous between
groups. A re-run of s8 on core 2 and s13 on all three cores gave byte-identical output.

### What an event depends on

An event depends on these [HW sweep, vendor RK1, 2026-09-27]:

- Every product of the group: 32 of 32 single knockouts remove it.
- A zero feature word: 0x0000 anywhere in the group disables it, in 0 of 8188 variants, while
  -0 keeps it in 20 of 32 lanes.
- The group sum: the event is periodic in it with period 2^-22 and ramps with its residue.
- The operand encoding, not only the products: each of three re-encodings changes it with every
  product unchanged. They are ±0 in one lane, one lane as (a×2, b/2), and the whole group.
- The exponent frame: scaling every weight by 2^±1 or 2^±2 removes every event on every core.
  Scaling by 2^±4 keeps the coarse significands, and keeps every event.
- The coarse significands, not the lane's product. Every re-encoding that keeps each coarse
  significand keeps core 2's event (47 of 47). Of those that keep the product but move bits
  between the operands, 8 of 38 move it. So no function of a lane's (shift, product, sign) is
  exact.
- Only the lanes with bits below the frame's LSB. Randomizing the one frame-aligned product's
  significand keeps the event 40 of 40 times. Randomizing every shifted lane keeps it 0 of 128.
- A rare coincidence among those lanes. 40,960 random zero-free groups fired 0 times on every
  core, including groups with the triggering group's exponents and signs. Sum-level candidates
  (the group sum's fraction, carry counts, shift-class sums) reach precision 0.26 and recall
  0.70 on core 2's held-out half, and at most 0.005 precision on cores 0 and 1.

An event does not depend on the clock or the voltage: the outputs are byte-identical at
300 MHz / 675 mV and 1000 MHz / 787.5 mV. No permutation of the group's lanes maps core 2
onto core 0.
The search covered 31 rotations, 15 in-half and 7 in-quarter rotations, all 120 bit
permutations of the lane index, and every index XOR. Why lane 0 differs is not known. The
occurrence follows the group's bits below the frame LSB, so an exact predicate needs each
core's lane-0 partial-product reduction [expected].

### Position classes

Each core's group positions fall into classes. Two positions are in one class when
swapping their contents never moves an event. Each pair was swapped on 750-1500 bases that
fire [HW sweep, vendor RK1, run t2]. A swap across classes moves the event on 1-24%
of them:

| Core | Classes of the group's 32 positions | Singletons | Unresolved |
|---|---|---|---|
| 0 | {0-2, 6, 8, 12-15, 19, 22-26, 29}, {16-18, 21, 27, 30}, {11, 20} | 3, 4, 5, 7, 28, 31 | 9, 10 |
| 1 | {3, 5, 6, 9-11, 13-25, 27-30}, {0, 2, 4} | 1, 7, 8, 26, 31 | 12 |
| 2 | {0-4, 6, 10, 16, 17, 19-22, 26-28, 31}, {7, 9} | 5, 8, 11-15, 18, 23, 25, 29, 30 | 24 |

An unresolved position differs from a class on under 3 bases in 1000. The class sizes differ
between cores, so no relabeling of positions maps one core onto another. Swaps give the classes
but not how they nest, so the reduction tree's shape is not recovered.

One lane's content moves the event the same way across a class. One lane was swept over
8192 words at each of the 32 positions [HW sweep, run t3]. On core 2 the event
pattern is the same at every position of the large class and at 8, 13, 18 and 30. The other
positions share three patterns, {5, 7, 14, 15, 25}, {9, 11, 12} and {23, 24, 29}. Core 0 with
the lane at position 5 reproduces core 2's first pattern exactly, and core 1 fires at none.

### Predicate search

An event needs most of the group. Setting lanes to -0 lowers core 2's firing rate from 0.66
at one lane to 0.01 at sixteen and to zero at 24. A group of the frame lane plus one to four
others fires 0 times in 262,144 on every core [HW sweep, run t4]. A re-run was
byte-identical. So there is no small firing group to decode.

No predicate was found. Candidates were scored on held-out firing groups against the
always-true predicate, whose F1 is 0.724 at core 2's 0.567 base rate. None scored above it:

- Thresholds on the group residue and on the lanes' summed sub-frame fractions.
- Carry counts over eight partial-product decompositions, NVDLA's Booth rows among them.
- NVDLA's carry-save split, emulated bit-exactly from `nvdla/hw`.

An additive model over each lane's content and position class predicts held-out arrangements
of the same bases at 0.996-0.998. Scored on other bases it falls to 0.79-0.95, so it describes
the bases, not the rule. What the search could not have found: every lane content came from one
family (Cmax 7, shifts 0-5, 562 contents). A lane term that differs at other frames, at shifts 6
and 7 or on negative features is outside it. The per-lane partial-product split is this silicon's
own, and a sweep cannot observe it.

### Gating registers

No gating register moves an event. The fp16 matmul program leaves CNA `CLK_GATE` (`0x1090`)
and CORE `MAC_GATING` (`0x300C`) unwritten and writes `MISC_CFG` `soft_gating` as 0. The BSP
driver and 87 captured vendor RKNN programs write none of them either. Every completing value
changed no lane-0 set on any core and made no core agree with another or with the model:

- `MAC_GATING` written as its reset value 0x07800800, as all ones, and with each bit toggled alone.
- `soft_gating` 0x3F and each bit alone.
- `CLK_GATE` 0x17 and each bit alone, and all three registers together.

Their outputs are byte-identical to the unwritten program [HW sweep, vendor RK1, 35 calls a core,
`rocket-userspace/tools/npu_core_diff_gate.sh`, 2026-09-27]. A write that lands and changes nothing
reads the same as one that never lands, and `CLK_GATE` has no witness of its own. Not searched:
multi-bit `MAC_GATING` values other than zero, all ones and the reset value.

The undocumented CORE `0x3030` moves nothing either. The emitter writes it as 0, as Mesa and
the vendor programs do. All ones and each bit alone are byte-identical to the control on 35 of 35
calls per core [HW sweep, vendor RK1, `ROCKET_CORE_3030`].

`MAC_GATING`'s bits have visible meanings. Bit 11 clocks output lanes 0-7 and bit 23 lanes
8-15. With one of them cleared, that half writes one constant word per core, and the other half
is unchanged. Bit 24 cleared, or the register written 0, stops the job: the DPU never raises its
completion and the driver resets the core. The other 24 bits change nothing on this workload.

### What the characterization held constant

The characterization held constant one shape (512×384×256), one task, and fp16 in
with fp32 out. It also held one board for the lane-0 sets, the emitter's register values, and
one data family for the event's size.

### Equality gates

**An equality gate on this path compares lanes, not cores.** Lanes n % 16 != 0 compare exactly
across cores, across runs and against the model. Lane 0 compares trigger sets. So a gate
excludes lane 0, or accepts the model's value or that value with one group lowered by
2^(4·Cmax − 44), as every recorded event is. On real attention data an event hits 1 lane-0
element in 16384 on core 2 and none on cores 0 and 1. Zero-free synthetic data gave none in
about 1.2 million elements per core.

### Integer path

The integer path is core-invariant. Full-range int8 tiles through `rocket_matmul_int8`
(int32 out) at the same shape are exact on all three cores, 2.6 million elements each. The
three cores' outputs are identical [HW sweep, vendor RK1, pinned per core, 2026-09-27]. So the
effect is a float-path property, and an integer equality gate still compares runs.

### Cause

Why the core classes differ is not known. A different summation order inside the group fits
every result, if its mapping is not an index XOR. A different rounding position fits them too
[hypothesis].

### Core placement

**A result can therefore depend on which core ran it, and one run compared to one run
compares core draws.** `rocket` places each job on a core by load, so a multi-core path's
output is a draw. The flash-attention handler's two output states are this effect.

Over 1800 traced trials, every odd output had head 12's AV job on core 2. Every other
output had it on core 0 or 1. The counts are 456 of 456 odd, and 1344 of 1344 modal. One
worker never reaches core 2, because the scheduler alternates one fd between cores 0 and 1
[HW sweep, mainline RK1, `rocket-userspace/tools/fa_trace_join.py`, 2026-09-27].

## Board-level machine parameters

These values are from the Rockchip RK3588 Hardware Design Guide V1.4 [source-confirmed].
They are the platform facts the NPU numbers in these notes were measured against. The
RK3576 differs in its DRAM bus, its NPU rails and its package, so see [rk3576.md](rk3576.md)
before carrying a number across.

| Parameter | Value |
|---|---|
| DRAM bus | 64-bit, 4x 16-bit channels, LPDDR4/4X/5, max 32 GB |
| DRAM clock | 2112 MHz (`VDD_DDR_S0` at 0.870 V / 2.50 A / 2.18 W) |
| Theoretical peak bandwidth | ~33.8 GB/s |
| NPU rails | `VDD_NPU` plus `VDD_NPU_MEM` (405 mA, separately regulatable) |
| NPU peak | 0.850 V / 4.00 A / 3.40 W at 1000 MHz |
| NPU main capacitance | > 200 uF |
| Package / θJA | EHS-FCBGA, 8.7 C/W (JEDEC 2S2P reference figure, no heat sink) |

The separate `VDD_NPU_MEM` rail is the notable one. The RK3588 gives every major block
its own memory supply (`VDD_NPU_MEM`, `VDD_GPU_MEM`, `VDD_CPU_BIG0/1_MEM`,
`VDD_CPU_LIT_MEM`, `VDD_VDENC_MEM`). The design guide documents combining it with the logic
rail as a low-power-scenario concession. The RK3576 has no NPU memory rail at all.

At this operating point the whole-chip ceiling is dispatch, not thermal (see
[../perf/](../perf/)).
