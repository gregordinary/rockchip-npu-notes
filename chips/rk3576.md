# RK3576 SoC parameter sheet

## Overview

The RK3576 NPU is an RKNPU with two cores, `npu0` and `npu1`, marketed as 6 TOPS. The RK3588
has three. It runs through the same mainline `rocket` drm/accel driver as the RK3588, with the
same uAPI and `/dev/accel/accel0`, and no interface change in userspace. The mainline `rocket`
core was merged in kernel 6.18, and RK3576 support is an RFC series applied to it
[source-confirmed: gahingwoo repo, kernel fragment `CONFIG_DRM_ACCEL + ROCKET + CRC32C`]. The
device-tree compatible string is `rockchip,rk3576-rknn-core` [source-confirmed: RFC patch 1].

The main difference from the RK3588 is the re-packed CNA register offset map. The companion
sheet [rk3576-regcmd.md](rk3576-regcmd.md) has the register encoding.
[rk3576-validation.md](rk3576-validation.md) records how this sheet's facts were established,
and the sources it draws on.

**Conditions:** H96 MAX M9, kernel 7.1.6 with patches `0001`-`0024` of the RFC series in-tree
(uAPI interface 1.5) [HW sweep, H96 MAX M9, 2026-08-04]. A section that depends on the `rocket`
module version names it.

## SoC integration

The RK3576 NPU's addresses, interrupts, power domains, clocks, resets and IOMMU are listed
below. A fact without its own tag is [source-confirmed] from the vendor kernel, the gahingwoo
series and BL31, per Ga Hing Woo's `notes/rk3576-npu-values.md`:

- **Core bases**: npu0 `0x27700000` (cna `0x27701000`, core `0x27703000`, mmu
  `0x27702000`), and npu1 `0x27708000` (cna `0x27709000`, core `0x2770b000`, mmu
  `0x2770a000`). The MMU is at core+0x2000. The NPU GRF syscon is at `0x26018000`.
  The cores are 0x8000 apart, inside one 64 KB `RKNN TOP` window, where the RK3588 uses a
  0x10000 per-core stride.

  The gahingwoo series' v2 and v3 device trees place core 1 at `0x27710000`, which is wrong.
  Its v4 and later place it at `0x27708000`. The TRM memory map gives `RKNN TOP` 64 KB at
  `0x27700000` and a *separate* `RKNN_NSP` 64 KB block at `0x27710000` [TRM]. The vendor
  kernel's `rknpu` node reads `reg = <0x27700000 0x8000>, <0x27708000 0x8000>`
  [source-confirmed]. On live silicon, `0x27708000` returns core 0's exact version pair, while
  `0x27710000` returns a word that changes between boots [HW sweep]. Those postings' own
  `rknn_mmu_1` at `0x2770a000` is correct, so their core node contradicts the core+0x2000 rule.

  A driver pointed at `0x27710000` drives the NPU MCU subsystem. The version word reads as
  garbage, every job times out, and the `rocket_core_reset()` that follows takes core 1's
  IOMMU down (`MMU_DTE_ADDR is not functioning`). The device tree must place core 1 at
  `0x27708000`, and `patches/rk3576/npu/0007` contains the fix.
- **IRQs**: GIC_SPI 247 (core0 + mmu0), 248 (core1 + mmu1), which `/proc/interrupts` numbers
  279 and 280 (SPI + 32). A core and its MMU share the
  line.
- **Power domains**: `RK3576_PD_NPU` / `_NPUTOP` / `_NPU0` / `_NPU1` (the vendor DT
  powers two core domains from one node).
- **Clock**: the compute engine is clocked through a separate, firmware-managed (SCMI)
  domain, independent of the CBUF bus clock. The RK3588 has the same arrangement, the one
  behind its clock parking. The SCMI NPU clock is `CLK_RKNN_DSU0`. Related clock gates:
  `ACLK_RKNN0/1`, `HCLK_RKNN_ROOT`, `ACLK_RKNN_CBUF`, `HCLK_RKNN_CBUF`. OPP rates reach ~1 GHz
  (`1000000063` Hz), and a PVTPLL ring/length table is present in the source.
- **Resets**: `SRST_A_RKNN0/1`, `SRST_A/H_RKNN_CBUF`, `SRST_A/H_RKNNTOP_BIU`. There is no
  `SRST_H_RKNN0/1`, unlike on the RK3588. The vendor node lists both core resets and both CBUF
  resets, and its soft reset asserts all four together. `rocket`'s binding names the core's
  `srst_a` alone, so `rocket` never resets the CBUF short of a power cycle. The consequence
  for the wide-output hazard is in [rk3576-regcmd.md](rk3576-regcmd.md) §"Per-job core reset".
- **IOMMU**: per-job attach/detach with an MMU reset per attach, as on the RK3588. The two
  enabling IOMMU fixes are in mainline from v7.3-rc1. `841363ebb508` takes every clock the DT
  lists, and `b10d5920cafa` clears a stale page fault before enabling stall. The upstream
  series contains the pmdomain fixes, a power-on settle delay and a reset cycle at power-on.
- **Power-on settle**: the NPU power domain needs ~15 us of internal preparation after it
  powers on [source-confirmed].

> [!CAUTION]
> An access to the NPU power domain's QoS registers inside its ~15 us settle window hangs the
> SoC [source-confirmed, Rockchip on the
> [v13 thread](https://lore.kernel.org/all/86d0a09c-f1e1-4310-aa39-6526268bdc76@rock-chips.com/)].
> With the delay at 0, the first power-on of the NPU domain takes an asynchronous SError in
> the QoS restore (`rockchip_pd_power` -> `regmap_write`). It does so whether the domain switches
> the rail or `regulator-always-on` holds it up, so the requirement is the domain's and not the
> rail's. Software must wait ~15 us after the NPU power domain powers on before that access.

The NPU GRF also contains two registers that `rocket` does not program:

- **Core work state.** `NPU_GRF_RKNNST` (NPU GRF `0x26018000` + `0x1C`) is read-only, and
  the TRM names bit 0 `core0_work_on` and bit 1 `core1_work_on` [TRM]. Neither `rknpu` nor
  `rocket` reads it. Read from the CPU, it holds 0 while core 0 computes, so it does not
  indicate a busy core [HW sweep, H96 MAX M9, 2026-09-27]. The `0x30000055` hold, the DPU
  drain and a two-core overlap are observed through `RAW_STATUS` and timing instead.
- **SRAM read margin.** `NPU_GRF_MEM_CON0`-`2` (`0x08`-`0x10`) configure the NPU's SRAMs.
  `MEM_CON0` names a read-margin field `RM` at bits [4:2], where all three reset values hold 4
  [TRM]. The vendor sets `RM` from the rail voltage with the NPU OPP table's
  `volt-mem-read-margin` rows (1 at 855 mV and above, 2 at 765, 3 at 675, 4 at 495)
  [source-confirmed: BSP `rk3576.dtsi`, `rknpu_devfreq.c`, `rockchip_opp_select.c`]. `rocket`
  leaves the reset value, 4, in all three words [HW sweep, 2026-09-27], where the vendor
  programs 3 at 750 mV. The TRM gives no direction, so that 4 is the conservative setting is
  read off the vendor's table, not measured [expected].

> [!CAUTION]
> The NPU GRF's bus clock, `pclk_nputop_root`, is `rocket`'s `pclk`. It is gated whenever the
> device is runtime-suspended, along with all four NPU power domains. A read with that clock
> gated is untested, and a bus stall there is [expected]. Software must hold `power/control`
> at `on` before a `/dev/mem` read of the NPU GRF, and set it back to `auto` after.

### Block bases

The node `reg-names` place the RK3576 blocks at the RK3588's offsets within a core [live,
device tree]:

| Block | `reg-names` | Offset in the core | Registers |
|---|---|---|---|
| PC | `pc` | +0x0000 | `0x0xxx` |
| CNA | `cna` | +0x1000 | `0x1xxx` |
| CORE | `core` | +0x3000 | `0x3xxx` |
| DPU | `dpu` | +0x4000 | `0x4xxx` |
| DPU_RDMA | `dpu_rdma` | +0x5000 | `0x5xxx` |

The match confirms, independently and on live hardware, that the re-pack is *within* the CNA
block, not a relocation of the blocks.

The RK3576 binding lists more banks than the RK3588's. The RK3588 `rocket` DT exposes only
`pc`/`cna`/`core` (`fdab0000.npu pc` / `cna` / `core` in `/proc/iomem` on an RK1). The
difference is in the driver binding. The CPU maps only what it touches directly, and DPU and
PPU registers are programmed through the regcmd stream, not MMIO. Neither chip's DT maps a PPU
bank (`0x6xxx`/`0x7xxx`), so the RK3576 node list does not show the PPU.

The RK3576 has a PPU pooling engine, programmed through the regcmd stream, and PPU pooling is
bit-exact on hardware (Support status). Its registers are in
[rk3576-regcmd.md](rk3576-regcmd.md) §"The PPU pooling program".

### Clocks, resets, power

The two NPU cores share their CBUF clocks, a power-domain parent and the `vdd_npu_s0` rail. The
NPU clock holds one rate for a whole boot.

#### Clocks and resets

- Both cores take the same six clocks (`aclk hclk npu pclk aclk_cbuf hclk_cbuf`). The CRU has
  exactly one `ACLK_RKNN_CBUF` and one `HCLK_RKNN_CBUF`, with no `..._CBUF1`. The vendor kernel
  lists them once on an aggregate node covering both cores, and the RFC's own `rknn_mmu_1` and
  `power-domain@RK3576_PD_NPU1` both list them. The upstream RFC device tree lists only four on
  core 1, which is an omission rather than a hardware asymmetry.
- `reset-names` is `srst_a` only. The RK3576 has no `SRST_H_RKNN0/1` analog, and the live
  binding has no `srst_h` slot.
- The NPU CRU clocks are present and named as SoC integration gives them: `clk_rknn_dsu0` (the
  SCMI NPU clock), `aclk_rknn0`, `aclk_rknn1`, `aclk_rknn_cbuf`, `hclk_rknn_root`,
  `hclk_rknn_cbuf`, `pclk_nputop_root`, plus `scmi_clk_npu`.
- The CBUF is clocked as one unit for both cores. The clock tree has exactly one `aclk_rknn_cbuf`
  (the NPU rate, 786 or 594 MHz) and one `hclk_rknn_cbuf` (198 MHz), with no per-core variant
  [live]. The reading agrees with the TRM's shared 16-bank CBUF clock gate and with the absence
  of any per-core CBUF field in the NPU GRF. It is consistent with the two-core corruption being
  contention on one shared CBUF datapath [hypothesis]. It is equally consistent with the
  undervolt hypothesis above, and does not separate the two.

Software must list all six clocks on core 1's device-tree node. `rocket_core_init()` gets all
six with `devm_clk_bulk_get()` for every core, so core 1 fails probe with
`-ENOENT: Failed to get clk 'aclk_cbuf'` until its node lists them. The patch
`patches/rk3576/npu/0007` adds them.

#### Power domains

- The power domains form a hierarchy, `npu` -> `nputop` -> `npu0`, `npu1`, with two compute
  domains, which confirms the 2-core structure.
- The power domains cycle per job. The domains `npu`/`nputop`/`npu0`/`npu1` are all `off` at
  idle, all read `on` while jobs are in flight, and then return to `off`. The driver's runtime-PM
  path therefore works on the RK3576 [live].

#### NPU clock rate

The NPU clock does not park. `scmi_clk_npu` / `clk_rknn_dsu0` hold one rate with the NPU power
domains off, and with them on and jobs running. With no `assigned-clock-rates`, that rate is
~786 MHz (786431952 / 786431998 Hz) [live]. With `assigned-clock-rates = <594000000>` it is
594000000 Hz [live 2026-10-02, kernel 7.2.8-1]. The RK3588 boots its NPU at 198 MHz and needs
a clock patch to reach its 928 MHz operating point. The RK3576 has no analog of that
`POWER_DOWN_FREQ`-style park, and needs no clock patch to run at its boot rate.

The NPU has no DVFS in this kernel. It has no `devfreq` node and no OPP table:
`/sys/class/devfreq/` has only `27800000.gpu` (800 MHz, with a 300-950 MHz rate list). The NPU
runs at one rate for a whole boot, the one the device tree assigns or the boot firmware leaves.
The rail `vdd_npu_s0` sits at 750 mV against a 550-950 mV range [live 2026-07-29, and
2026-10-02 on kernel 7.2.8-1].

> [!NOTE]
> A figure's tag states its clock. Every measurement tagged 786 MHz ran with no
> `assigned-clock-rates` and the rail pinned by `regulator-always-on`: 750 mV, `enabled`,
> `num_users=1`, 786431952 Hz [live 2026-09-25, kernel 7.2.3-1]. An external project measures
> two-core corruption at 786 MHz at 750 mV. The corruption vanishes at 594 MHz / 750 mV and at
> 786 MHz / 800 mV. Any single-core result tagged 786 MHz was taken at that clock and voltage too,
> so the caveat covers more than the two-core work.

The specified maximum is 1000 MHz at 800 mV, and the CRU's OPP data reaches ~1 GHz
(`1000000063` Hz) [source-confirmed: RK3576 Hardware Design Guide V1.1 peak-current table]. The
clock headroom is therefore roughly 1.27x above 786 MHz and 1.68x above 594 MHz. The regulator
range covers the voltage it needs [source-confirmed: RK3576 Hardware Design Guide V1.1
peak-current table]. Software sets that rate through `assigned-clock-rates` in
the device tree, which is how 594 MHz is set. The other method is an SCMI `set_rate` from inside
the driver, as on the RK3588. No sysfs interface sets the rate.

A higher clock is unlikely to shorten library calls on the RK3576 [expected]. The submit is 22%
of library wall-clock time against the host's 78%. Within a submit, the fixed cost is the
completion poll and the DPU drain rather than MAC throughput.

**Not characterized:** library calls at a clock above 786 MHz.

The 786 MHz timings do not describe a board at 594 MHz. At 594 MHz the four one-kick graphs
take 0.6-1.4 ms longer, 12-21%. Scaling each graph's execution term (2.25-5.75 ms at 786 MHz)
by the clock ratio predicts 0.7-1.9 ms, so the clock is the likely cause [hypothesis]. The
library and the kernel also differ between the two columns, so the clock is not isolated.

| Network | 786 MHz | 594 MHz |
|---|---:|---:|
| MobileNetV1 | 5.0 ms | 5.6-5.7 ms |
| MobileNetV2 | 6.5-6.6 ms | 7.5-7.7 ms |
| ResNet-18 | 6.6 ms | 7.9-8.0 ms |
| Inception V1 | 7.0-7.1 ms | 8.2 ms |
| Inception V3 | 33.4-33.7 ms | 37.4-40.5 ms |

**Conditions:** H96 MAX M9, `bench 100`, resident weights, governor `ondemand`. Each graph but
Inception V3 runs as one kick in one submit, with one write-guard bracket per BO
([../perf/rk3576-graph.md](../perf/rk3576-graph.md) §"One bracket per BO"). ResNet-18's stem is
the materializing packed stem, 33 tasks. The 786 MHz column is from 2026-08-03. The 594 MHz
column is [live 2026-10-02, kernel 7.2.8-1, `rocket` 1.6.0]. Its image boots with
`cpuidle.off=1` on the kernel command line, a second condition the 786 MHz column did not have.

#### NPU supply rail

With `domain-supply` on the NPU power domain and no `regulator-always-on`, the rail
power-cycles with the workload. `vdd_npu_s0` reads `disabled`, `num_users=0` at rest, and
`enabled`, `num_users=1`, 750 mV with a job in flight [live 2026-10-02, kernel 7.2.8-1]. The
driver's autosuspend delay is 50 ms, so the rail drops in any gap between submits longer than
that. A job submitted with the rail off computes, and the jobs that follow it match it byte for
byte.

> [!NOTE]
> Before the first job of a boot, that rail reads `enabled`, `num_users=1` with the device
> runtime-suspended. `npu`, `nputop` and `npu0` stay powered from boot until the first
> runtime-PM cycle [live 2026-10-02, kernel 7.2.8-1]. Read the at-rest state after a job has
> run.

The vendor's voltage for a clock depends on the chip's bin, which mainline does not read. The
vendor kernel picks the bin from a PVTPLL oscillator count at NPU GRF offset `0x54`, with the
NPU forced to 800 MHz and 750 mV. A higher count selects a higher bin and a lower voltage
[source-confirmed: BSP `drivers/soc/rockchip/rockchip_opp_select.c`, which logs
`pvtm-volt-sel=`]. Mainline takes no such reading, so only a vendor-kernel boot log of the same
board gives its bin. Against the step at or above each clock, 594 MHz at 750 mV is inside the
table at every bin. At 786 MHz and 750 mV it is inside only at `L5` and above
[source-confirmed: BSP `rk3576.dtsi` `npu_opp_table`, RK3576 rows only]:

| Bin | 600 MHz step | 800 MHz step |
|---|---|---|
| `L0`-`L1` | 737.5 mV | 800 mV |
| `L2` | 725 mV | 787.5 mV |
| `L3` | 725 mV | 775 mV |
| `L4` | 725 mV | 762.5 mV |
| `L5` | 725 mV | 750 mV |
| `L6` | 725 mV | 737.5 mV |
| `L7`-`L10` | 725 mV | 725 mV |

The SoC variants stop lower. The table above is the standard RK3576's. The variant the vendor
table tags `S` tops out at 500 MHz. The J and M variants have their own rows to 850 MHz.
`rk3576j.dtsi` disables 800 and 850 MHz there as overdrive that shortens the chip's life, which
leaves 700 MHz [source-confirmed: BSP `rk3576.dtsi` and `rk3576j.dtsi`, `develop-6.12`].

### Memory system, NPU rail, and thermal limits

Three board-level parameters of the RK3576 differ from the RK3588's: DRAM bandwidth, the NPU
supply rails and thermal throttling. Read an NPU figure measured on the RK3576 against them. The
figures are from the Rockchip RK3576 Hardware Design Guide V1.1 [source-confirmed], plus live
readings on the H96 MAX M9.

#### DRAM bandwidth

The RK3576's DRAM bandwidth is half the RK3588's, at an identical clock.

| | RK3588 | RK3576 |
|---|---|---|
| Bus width | **64-bit**, 4x 16-bit channels | **32-bit**, 2x 16-bit channels |
| Max capacity | 32 GB | 16 GB (8 GB per channel) |
| Standards | LPDDR4/4X/5 | LPDDR4/4X/5 |
| PHY clock | 2112 MHz | 2112 MHz |
| Theoretical peak | ~33.8 GB/s | **~16.9 GB/s** |

The bus width is [source-confirmed] from each SoC's design guide. The clock is identical on
both. The RK3588 design guide specifies its DDR rail, `VDD_DDR_S0`, at a DDR frequency of
2112 MHz [source-confirmed: RK3588 Hardware Design Guide V1.4]. On the H96 MAX M9,
`scmi_clk_ddr` reads exactly 2112000000 Hz [live 2026-07-29]. The ratio is therefore exactly
2x, with no clock difference confounding it. An RK3576 has half the DRAM bandwidth of the RK1,
the RK3588 board every RK3588 figure in these notes was measured on.

Achieved streaming bandwidth on the H96 MAX M9:

| Threads | Achieved |
|---|---|
| 1 | 9.0 GB/s |
| 2 | 8.7 GB/s |
| 4 | 8.3 GB/s |

**Conditions:** H96 MAX M9, 8 GB, 256 MB buffers, `memcpy`, pinned to the A72 cluster, read
and write traffic counted [live 2026-07-29].

Achieved streaming bandwidth is ~53% of the theoretical peak, the usual figure for a copy
benchmark on LPDDR. One A72 thread already saturates the bus, and more threads make it slightly
worse. The saturated bus is the mechanism behind three behaviors measured separately on the
RK3576:

- **int32 writer atom drop.** The int32 writers' atom drop tracks DDR traffic. It rises from
  5.8% of row tasks on a quiet host to 51.7% under a host streaming `memcpy` to DDR. A single
  host thread streaming to DDR consumes the whole bus. The NPU's write DMA then contends for
  a resource with nothing left in it.
- **DPU write drain.** The DPU write drain is long on the RK3576. In `RAW_STATUS`,
  `DPU_0`/`DPU_1` set 82-343 us after `PC_DONE`, scaling with the bytes in flight. The drain
  reaches 745 us on the int8 stem at 224×224 k7 s2. The grace `dpu_grace_us` is a 500 us
  deadline by default on `rocket` 1.5.0, and on 1.6.0 its default of 0 waits for the writing
  block. A bus half as wide predicts about twice the RK3588's drain for the same output
  [expected].
- **Host cube pack.** The host cube pack runs within about 2x of a straight copy. The pack
  blocks its scatters into `memcpy` runs, which are block moves rather than per-element index
  calls. A NEON 16×16 block does the CHW <-> NC1HWC2 transpose. The conv path's feature
  scatter and output de-tile run at 2.1-2.4 GB/s, against a single-thread `memcpy` maximum
  of 4.4 GB/s on the RK3576.

  The pack is therefore bulk copying against a bus one thread already saturates. Neither
  threading the pack nor more vectorization speeds it up, and only moving fewer bytes does.
  Packing a layer's weights once through a handle moves fewer bytes, and takes the measured
  time from 98.8 ms to 33.6. Keeping tensors in cube layout between consecutive layers removes
  the pack at each join. MobileNetV1-224 then measures 10.4-10.5 ms, against ~21 ms with a NEON
  transpose at every layer boundary (§"A whole network").

#### NPU supply rails

The RK3576's NPU has no separate memory rail [source-confirmed, both design guides].

| | RK3588 | RK3576 |
|---|---|---|
| NPU rails | `VDD_NPU` **+ `VDD_NPU_MEM`** (405 mA, separately regulatable) | `NPU_DVDD` only |
| Peak | 0.850 V / 4.00 A / 3.40 W at 1000 MHz | 0.800 V / 4.00 A / **3.20 W** at 1000 MHz |
| Supply | DC/DC BUCK | RK806S-5 BUCK2 (5 A rating) |
| Main capacitance | > 200 uF | > 90 uF |

The RK3588 gives every major block its own memory rail: `VDD_NPU_MEM`, `VDD_GPU_MEM`,
`VDD_CPU_BIG0/1_MEM`, `VDD_CPU_LIT_MEM`, `VDD_VDENC_MEM` [source-confirmed, both design
guides]. Its guide notes that `VDD_NPU_MEM` "can be combined with `VDD_NPU`" only where
power consumption is not a concern. The RK3576 has exactly one MEM rail in the whole SoC,
`LOGIC_MEM_DVDD`, and no NPU equivalent. The NPU's internal memory arrays, the CBUF among them,
are supplied from `NPU_DVDD` itself.

On the RK3576, no supply can therefore hold NPU array state up while the logic drops. Two
findings are consistent with that. A register sweep established independently that the
wide-output hazard's corrupted state lives in an NPU-internal memory array rather than in a
register. And a runtime-PM power cycle is the only thing that clears that state.

The missing rail does not by itself explain the cycle's ~87% success rate. Runtime PM powers
down the on-die power domain, not the external rail. The rail arrangement supports that
mechanism without measuring it [hypothesis].

`NPU_DVDD` peaks at ~80% of BUCK2's 5 A rating, so board headroom above the specified 1000 MHz / 800 mV point is thin.

#### NPU thermal throttling

The RK3576 has no NPU throttle between idle and a critical thermal event at 115 C.

| | RK3588 | RK3576 |
|---|---|---|
| Package | EHS-FCBGA | EHS-FCCSP698L, 16.1 × 17.2 mm |
| θJA | 8.7 C/W | **15.84 C/W** |

**Conditions:** θJA simulated on a JEDEC 2S2P board with no heat sink, from both design guides
[source-confirmed]. It is a reference figure rather than a board figure.

The smaller package sheds heat about 1.8x worse for the same watts.

The kernel exposes six thermal zones (`package`, `bigcore`, `littlecore`, `gpu`, `npu`,
`ddr`), so the NPU has its own sensor. `npu-thermal` has one trip point, type `critical`, at
115 C, with zero cooling devices bound to it [live 2026-07-29]. The only three cooling devices
on the SoC are `cpufreq-cpu0`, `cpufreq-cpu4` and `devfreq-27800000.gpu` [live 2026-07-29].
The design guide states the same from the other side: its SDK "provides temperature control
strategies specifically for the CPU and GPU."

On the H96 MAX M9, idle is 35-38 C across all six zones. Sustained test runs reach 40-43 C
with every cooling device at state 0 [live 2026-07-29]. Submit loops held the die at 44-49 C
[live 2026-07-25]. The margin to the critical trip is wide in practice, and it is the NPU's
only thermal protection.

> [!NOTE]
> A workload that loads the NPU rail and the A72s together loads two rails at once. The
> RK3576 package sheds heat 1.8x worse than the RK1's. The RK3576's host-bound library calls do
> that. The design guide states that per-module peak currents "cannot simply be summed up as
> the SoC's peak current" for thermal purposes. Watch die temperature on long sweeps rather
> than assuming the RK1's headroom.

### Host CPU

The host is 4x Cortex-A72 + 4x Cortex-A53 big.LITTLE (`0xd08` / `0xd03`). Software should pin
host fan-out for NPU offload to the A72 cluster, the analog of the RK3588's A76 pinning.

Both cpufreq policies default to `ondemand`, with a 408 MHz minimum frequency and maxima of 2016
and 2208 MHz [live 2026-09-25]. The RK3588 board with the same minimum lost 3.2x to an unpinned
governor ([../perf/cpu-governor-and-offload.md](../perf/cpu-governor-and-offload.md)).

**Not characterized:** the loss to an unpinned governor on the RK3576.

> [!NOTE]
> The two clusters have different caches, and the kernel's sysfs indexes them per CPU. `cpu0` is
> an A53, and only `cpu4`-`cpu7` describe the A72 cluster that runs pinned host work.

The caches, read from sysfs on the H96 MAX M9 [live]:

| | L1d | L1i | L2 (unified, cluster-shared) |
|---|---|---|---|
| A72 (`cpu4-7`) | 32 KiB, 2-way, 256 sets | 48 KiB, 3-way | **1024 KiB, 16-way, 1024 sets**, `shared_cpu_list 4-7` |
| A53 (`cpu0-3`) | 32 KiB, 4-way, 128 sets | 32 KiB, 2-way | 512 KiB, 16-way, 512 sets, `shared_cpu_list 0-3` |

Two consequences follow for any locality argument about pinned host work. The A72 L2 way is
64 KiB, so a 4 KiB page has 16 physical colors (physical address bits `[15:12]`), not the 8 the
A53's 32 KiB way gives. The 1 MiB A72 L2 is shared by all four A72s, so a four-thread host loop
contends with itself in it: the per-thread share is 256 KiB.

### Two-core operation

**Conditions:** NPU clock 786 MHz, `vdd_npu_s0` at 750 mV and held on by `regulator-always-on`
[live 2026-09-25, kernel 7.2.3-1]. Every two-core result on this sheet was measured at this
operating point, on both cores.

Core 1 probes and executes jobs, and enabling it does not increase throughput. Enabled at its
real address (`0x27708000`, see "Core bases" above), with the six clocks
`rocket_core_init()` requires, it takes jobs with no userspace change. The kernel spreads an
open fd's work across both cores' schedulers. Jobs run on both cores, and each core reports an
equal share of runtime-active time.

Two worker fds give 1.3-1.7x over one, and one core gives that gain on its own. One fd leaves a
single core idle between submits, at a ~340 us per-submit overhead, and the second fd fills
those gaps. A second core has no idle time left to fill. With core 1 unbound, two fds give
[HW sweep, H96 MAX M9, 2026-07-28]:

| Shape | Two fds against one |
|---|---|
| 8×64×32 | 1.51-1.69x |
| 32×1024×512 | 1.62-1.66x |
| 128×1024×1024 | 1.49-1.51x |
| 256×512×2048 | 1.33x |

The two cores share three resources:

- **One CBUF.** The RK3576 has one `CBUF`: 1 MB at `0x3fe80000` in the address map, outside
  either core's register bank. Its 16 banks are gated from a single field in the shared NPU
  GRF, `NPU_GRF_MEMGATE_CON0` bits[15:0] ("clock gate enable for cbuf bank 0-15"). The CRU has one
  `ACLK_RKNN_CBUF`/`HCLK_RKNN_CBUF` pair, which both cores' nodes list. The NPU GRF has no
  other CBUF field: no base, mask or window register [TRM, `Rockchip_RK3576_TRM_Part1_V1.2`].
- **One CBUF staging window per task, not per core.** On the RK3576, `CNA_CBUF_CON0` contains a
  granule allowance F, not a bank base, and the emitted word is `bit28 | F<<16 | base`. Nothing
  a regcmd encoder emits depends on the core.
- **One power domain**, which collapses only once both cores are runtime-suspended
  [HW sweep, H96 MAX M9].

The low half of `CNA_CBUF_ENTRIES` (`0x103c`) and of `CNA_CBUF_CON0` (`0x1040`) is a granule
offset: where a task's window starts and where its fetch resumes. The base is honored, and it
reaches only inside the task's own allowance window. The last base at which a task still
computes is `4096 + F - plane` [HW sweep, H96 MAX M9, measured 2026-07-28]. That bound is exact at
planes of 64, 256, 1024 and 2048 granules, and a task 64 granules past it is wrong. A job
therefore cannot be staged outside the budget it programmed.

Bits 30 and 31 of `CNA_CBUF_CON0` are inert. Bit 29 is live and corrupts the job at every
combination that sets it.

The vendor driver's `rk3576_cache_sgt_init()` hands each core a disjoint, bank-aligned slice
of the CBUF [source-confirmed: `rknpu_drv.c:123`]. Core 0 has `[0,448K)` and `[896K,960K)`, and
core 1 has `[448K,896K)` and `[960K,1024K)`. At 16 banks over 1 MB that is 64 KiB a
bank, so core 0 gets banks `{0-6, 14}` and core 1 `{7-13, 15}`, eight each. That table
partitions the CBUF as allocatable memory, through an allocator and an IOMMU mapping, and never
as a register write. `librocketnpu`'s single-core CBUF pool measures 448 KiB (7168 granules of
64 B), bank for bank the vendor's core-0 primary block.

The vendor driver schedules independent jobs on the two cores concurrently by design. It keeps
a todo list and an in-flight job per core, and `RKNPU_CORE_AUTO_MASK` balances them by queued
task count. The SDK exposes per-core context placement alongside its combined mode
[source-confirmed: `rknpu_job.c`, `rknn_api.h`]. The RK3576 is designed to run two jobs at
once. The vendor's `init_runtime(core_mask=...)` fixes the core when a context is created, before any inference, so its runtime can build
per-core state into the register program. Under `rocket`, userspace builds the register program
without knowing which core will run it.

> [!CAUTION]
> The two cores share one power domain. A guard that waits on one device can let the next
> submit through while the other core still holds the domain up. Software must drive and wait
> on every bound device, not the first. The wide-output hazard below depends on this.

#### Software support

On the RK3576, `rocket_open()` counts the bound cores under `/sys/bus/platform/drivers/rocket`.
With more than one bound, it warns once and then returns `-EBUSY` for the **second** fd. Two fds
are what put two jobs in flight.

`ROCKET_RK3576_ALLOW_MULTI_FD=1` lifts the refusal, for a probe that provokes the corruption
deliberately and for a caller that has serialized its own submits. With one core bound the
library does not refuse, and two fds give the 1.3-1.7x above. The refusal is verified both
ways on the SoC [HW sweep, H96 MAX M9]. It is silent with one
core bound and refuses with two, and the override is honored.

### Driver and device-tree state

**Conditions:** H96 MAX M9 (`rockchip,rk3576`, 8 GB), mainline Debian forky/sid, kernel
7.1.3-1-arm64 PREEMPT_RT.

On this board the RK3576 NPU enumerates, and jobs submit and complete. With the RK3576's own
regcmd encoder, its int8 convolutions are bit-exact [observed 2026-07-24/25].

With `CONFIG_DRM_ACCEL=y` + `CONFIG_DRM_ACCEL_ROCKET=m` and the RK3576 NPU device-tree
nodes enabled, `rocket` probes and `/dev/accel/accel0` comes up
(`/sys/devices/platform/rknn/accel/accel0`, `MODALIAS=platform:rknn`). The device
`27700000.npu` is bound, and both NPU power domains are attached and runtime-suspended at
idle.

#### Memory-safety fixes

The 7.1.3-1 image's in-tree `rocket` contains `patches/rk3576/npu/0001-0012` but none of
`0013`, `0014` or `0020`. It therefore has three memory-safety defects that any
`render`-group client reaches. The 7.1.6 image in Overview's Conditions contains `0001`-`0024`,
and so all three fixes.

| Fix | Trigger | Effect |
|---|---|---|
| `0013` | One malformed submit | The kernel oopses |
| `0014` | A client that submits and closes without waiting | A use-after-free in the IOVA allocator |
| `0020` | Any submit the kernel rejects for its task array | The array is freed twice, which corrupts the kmalloc-16 freelist. The fault appears in whatever allocates next |

> [!CAUTION]
> A `rocket` without `0013`, `0014` and `0020` lets any `render`-group client oops the kernel
> or corrupt its heap. Tests still run after one Oops, but three Oopses take the file-close
> path into the IOMMU layer, and the board needs a reboot. Software must run on a `rocket` that
> contains all three. Until then, do not measure on a kernel that has taken one Oops.

[rk3576-regcmd.md](rk3576-regcmd.md) gives each defect, the paths that reach it and the
comparison that verifies each fix, under these sections:

- "Kernel oops on a rejected submit"
- "BO lifetime across file close"
- "The unprivileged double free"

> [!NOTE]
> All three patches are in `series/rk3576-npu.toml`. Before 2026-07-28 that file listed the
> series only to `0012`, so an image built before that date silently leaves `0013` out. When
> asking what an image contains, check the series file, not the directory.

#### Chip identification

The accel device `rocket` registers is a synthetic `platform:rknn` aggregate with no
`of_node`, so the chip cannot be identified from `/sys/class/accel/accel0/device`. Read the
compatible from the driver-bound per-core device instead
(`/sys/bus/platform/drivers/rocket/27700000.npu/of_node/compatible`), or fall back to the
SoC-level `/proc/device-tree/compatible`. `librocketnpu`'s chip autodetect does this.

#### Device-tree nodes

The device tree instantiates `npu@27700000` and `npu@27708000`, both
`compatible = "rockchip,rk3576-rknn-core"`, and `iommu@27702000` / `iommu@2770a000`,
`compatible = "rockchip,rk3576-iommu", "rockchip,rk3568-iommu"`. The core 0 and MMU
addresses and the interrupts (GIC_SPI 247 / 248) are confirmed on live silicon, and core 1's
address is confirmed by reading it. The RFC's unit-address for core 1 is wrong (see "Core
bases"). The NPU regulator `vdd_npu_s0` is PMIC `dcdc-reg2` (750 mV nominal, 550-950 mV).

Two device-tree details are required for `rocket` to probe this way, and both are easy to get
wrong:

- **Power domains on core 0.** The core 0 node must list both NPU power domains.
  `rocket_core_init()` calls `devm_pm_domain_attach_list()`, and the driver core auto-attaches
  a node with a *single* `power-domains` entry first. The explicit attach then fails with
  `-EEXIST` (`failed to attach NPU power domains`, probe error -17), and no `/dev/accel`
  appears. Listing two entries
  (`power-domains = <&power RK3576_PD_NPU0>, <&power RK3576_PD_NPU1>`) suppresses the
  auto-attach, and the explicit attach succeeds.

  The vendor powers both NPU domains from one node the same way, even when computing on a
  single core. The CBUF->CMAC read path is only fully powered with NPU1 up.
- **Core 1.** Core 1 and its IOMMU must stay disabled for single-core bring-up. Core 0 holds
  both domains.

#### NPU supply rail

With neither `npu-supply` on the NPU node nor `domain-supply` on the power domain, nothing
claims `vdd_npu_s0`. The regulator core then disables it as unused late in boot
(`vdd_npu_s0: disabling` at t~33 s). Probe at t~8 s survives only because it runs first.

> [!CAUTION]
> An NPU rail with no consumer is disabled as unused late in boot, after `rocket` has probed.
> Adding `npu-supply` alone does not prevent it. Mainline `rocket` in 7.1 has no regulator
> support at all, so no consumer ever appears, and the rail still drops. Software must hold the
> rail with `regulator-always-on` on the PMIC node, or make the power domain its consumer
> through `domain-supply`.

The module `rocket.ko` references no `regulator_*` symbol, and the RK3588 `npu-supply`
handling is the out-of-tree `082-rocket-drv-npu-volt` patch. The rail can be held in two ways:

- **`regulator-always-on`.** Under a stock driver, `regulator-always-on` on the PMIC node holds
  the rail. Set both: `npu-supply` describes the relationship for a regulator-aware driver,
  and `regulator-always-on` keeps the rail up. With both, `vdd_npu_s0` stays `enabled` at
  750 mV past boot [live].
- **`domain-supply`.** The power domain becomes the rail's consumer. The pmdomain driver looks
  up `domain-supply` only on a domain it marks as needing a regulator. The upstream series
  adds that mark for the NPU domain. With that kernel change, `regulator-boot-on` and no
  `regulator-always-on`, the rail follows the domain, and `rocket` still needs no regulator
  support [live 2026-10-02, kernel 7.2.8-1].

#### Register banks

The driver can map fewer register banks than the DT provides. Here the DT supplies five banks,
but `/proc/iomem` shows only `pc`, `cna` and `core` mapped [live, kernel 7.1.3-1]. The mapping
is the driver's, not the image's. Through patch `0034` of the RK3576 series, `rocket` 1.6.0
included, as in mainline 7.1, `rocket_core_init()` maps only those three banks
[source-confirmed: `rocket_core.c`]. The series reads its completion bits from
`INTERRUPT_RAW_STATUS` in the `pc` bank. A DPU and DPU_RDMA mapping exists only as a separate
patch in the gahingwoo kernel series (`linux-rk3576-npu`).

Jobs submit and complete with only three banks mapped. The RK3588 `rocket` maps the same three
and runs DPU work, because the DPU is programmed through the regcmd stream rather than by the
CPU.

### Dispatch path

The RK3576 dispatch path behaves as on the RK3588: BO allocation, IOMMU mapping, regcmd fetch,
PC execution, and the IRQ and fence path [live]. Only the per-chip geometry encoding differs. An
RK3588 register program submitted to the RK3576 runs through all of it. The ioctl
`DRM_IOCTL_ROCKET_SUBMIT` returns 0, the power domains come up, and the job runs. A `PREP_BO` on
the output BO returns 0, so the completion fence signals and the DPU raised its completion IRQ.
The kernel logs no `NPU job timed out`, no IOMMU fault and no error [live].

Compute on the RK3576 depends on the regcmd encoder alone, not on the driver, the uAPI, the
memory path or the interrupt path.

> [!CAUTION]
> An RK3588 register program completes normally on the RK3576 and writes nothing to its output
> BO: no garbage and no partial result. The RK3588 program places its output dimensions at
> offsets that mean something else on the RK3576, so the output is mis-sized to nothing [live].
> An operation that still emits the RK3588 encoding writes nothing at all rather than something
> close. Software must emit the RK3576 geometry encoding for every operation.

`librocketnpu` reads the NPU's DT compatible at device open and selects the RK3576 profile. It
warns which paths have no RK3576 regcmd encoder, so a path that would write nothing is reported at open.
For bring-up, `ROCKET_CHIP=<name>` forces a profile.

`PREP_BO` syncs a whole BO for the CPU and `FINI_BO` syncs it back. Neither takes a range, so a
bracket costs a fixed 2.24 us plus 0.194 us/KiB however few bytes are touched [HW sweep, H96 MAX
M9, 2026-08-02]. Patch `0023` (interface 1.5) adds `DRM_ROCKET_PREP_BO_RANGES` and
`_FINI_BO_RANGES`.

### Kernel module build on the board

The `rocket` module builds on the board. The board's `linux-headers` package is a full kbuild
tree with `Makefile`, `Module.symvers`, `arch`, `include` and `scripts`. To build it:

1. Take pristine v7.1 `drivers/accel/rocket/`.
2. Apply the series' patches that touch that directory. On the build measured (2026-07-27)
   they were 0006 and 0008, and later patches of the series touch it too. The rest patch
   pmdomain, the IOMMU and the DT, which are built in.
3. Give it an `obj-m` Makefile.
4. Run `make -C /lib/modules/$(uname -r)/build M=$PWD modules`.

The compiler differs from the kernel's and warns. The module loads, and both convolution tests
and the matmul test pass on it unchanged.

### Documentary sources

The RK3576 TRM has no NPU register chapter. Part 1 and Part 2 contain the memory map, the
interrupt table and the CRU clock tree, and nothing on the CNA/CORE/DPU registers. The memory
map places `RKNN TOP` 64 KB at `0x27700000` and `RKNN_NSP` 64 KB at `0x27710000`, which is where
a mis-addressed core 1 node points. The RK3588's encoding has a documentary source, and the
RK3576's has none: vendor captures are its only source.

> [!NOTE]
> A `.rknn` file contains the *stored* register program. The vendor runtime patches values into
> it at load time: the addresses, and at least `0x1064`. A register that reads 0 in a decoded
> capture is therefore not known to be 0 in the program the runtime submits.

## Programming model

### Datapath common to the RK3588

The RK3576 shares the RK3588's datapath and block bases, and differs in the register encoding.
Ga Hing Woo reports that the command stream matches the vendor's line for line once the offset
map is right [source]. The match covers:

- The register command stream content
- The state-init sequence
- The soft-reset and its IOMMU re-attach
- The submit handshake

The datapath common to every RKNPU is therefore unchanged, and all of these transfer:

- The matmul-as-1×1-conv mapping
- The CNA→CORE→DPU sequence
- The precision-field encodings
- The BS/BN/EW/LUT semantics
- The tile-layout algebra

The RK3576 runs a matmul on the same CNA->CBUF->CSC->CORE->DPU pipeline as the RK3588, in
fully-connected mode, with no separate GEMM unit [external, gahingwoo
`MATMUL-PIPELINE-ANALYSIS.md`]. The matmul-as-1×1-conv mapping transfers unchanged for that
reason.

The block bases are also common. Within a core, CNA is at +0x1000 and CORE at +0x3000,
exactly as on the RK3588, and the PC's version register is at +0x0.

### CNA register encoding

The RK3576 CNA block has its own geometry-register encoding, not a shifted copy of the
RK3588's. Three things differ at once. Some registers move, and several registers that are
unused gaps on the RK3588 are live on the RK3576. At shared offsets the bit-packing differs.

Only two CNA geometry registers coincide with the RK3588's by both offset and meaning:
`0x1014` (stride) and `0x1110` (weight / DCOMP address). The feature-data address is not one
of them.

> [!CAUTION]
> The RK3576 takes the feature-data address at `0x1088` on *both* CNA datapaths, and leaves
> `0x1070`, the RK3588's slot, at zero. An RK3588 register program therefore produces
> incorrect output on the RK3576. Software must program the feature-data address at `0x1088`.

Ga Hing Woo's `vendor-capture/RK3576_CNA_MAP.md` (github.com/gahingwoo/linux-rk3576-npu) gives
the full closed-form RK3576 CNA/CORE/DPU register encoding for the vendor-toolkit conv path. It
is reverse engineered from the vendor RKNN register programs. Its captures cover first-conv ARGB, normal
`in_ch>4`, and depthwise. They include the pointwise `k=1` case, the matmul-relevant shape.
[rk3576-validation.md](rk3576-validation.md) gives its method.

> [!CAUTION]
> `RK3576_CNA_MAP.md` is wrong in four places, and a regcmd encoder that takes the published reading
> silently mis-programs the RK3576. Software that encodes from the map must apply the four
> corrections in [rk3576-regcmd.md](rk3576-regcmd.md) §"Corrections to the published map".

The table gives the CNA delta on the normal `in_ch>4` path, with those corrections applied. In
it `dw` is depthwise and `wbpk` is weight bytes per kernel (`ic·k·k·2`, or `k·k·4` for dw). The
symbol `entries` is `ceil(in_w·ic/64)`, the count of 64-byte CBUF granules in one feature row.
The RK3588 names come from
[rocket-userspace `include/npu_hw.h`](https://github.com/gregordinary/rocket-userspace/blob/main/include/npu_hw.h):

| Offset | RK3576 field | RK3588 register at that offset |
|---|---|---|
| `0x1014` | `(s<<3)\|s` stride | `CNA_CONV_CON3`, **coincides** (stride) |
| `0x1018` | `0x40000404` (precision/ARGB) | gap |
| `0x101C` | total weight bytes | gap |
| `0x1020` | `(dw?oc:ic)·k·k` | `CNA_DATA_SIZE0` (not DATAIN dims) |
| `0x1024` | `k_word<<16 \| (oc-1)` | `CNA_DATA_SIZE1` |
| `0x1028` | `(in_w·in_h·ic/64)<<16 \| (ic-1)` | `CNA_DATA_SIZE2` |
| `0x102C` | `(in_w-1)<<16 \| (in_h-1)` | `CNA_DATA_SIZE3` |
| `0x1030` | `wbpk<<16 \| (out_w-1)` | `CNA_WEIGHT_SIZE0` |
| `0x1034` | `out_w·out_h - 1` (universal) | `CNA_WEIGHT_SIZE1` |
| `0x1038` | `0x07` const | `CNA_WEIGHT_SIZE2` |
| `0x103C` | `entries<<16` (CBUF data entries) | gap |
| `0x1044` | `in_w<<16 \| entries` | `CNA_CBUF_CON1` |
| `0x1048` | `0x0B`, the CVT control word with the converter bypassed (RK3588 `CNA_CVT_CON0`, `0x104C`) | gap |
| `0x1078` | `(in_w-1)<<16 \| (in_h-1)` | `CNA_DMA_CON0` |
| `0x107C` | `ic-1` | `CNA_DMA_CON1` |
| `0x108C` | `0x000F000F`, the weight and data burst lengths (RK3588 `CNA_DMA_CON0`, `0x1078`) | gap |
| `0x1090` | `in_w·4` (CBUF input line stride) | gap |
| `0x1094` / `0x1098` | `in_w·in_h` for the plane, and `round4(in_w·ih_task)` for one task's rows (equal for a single-task plan) | gap |
| `0x118C` | `(in_w-1)<<16 \| (in_h-1)` | gap |

The first-conv `in_ch<=4` ARGB path packs about sixteen of these differently again, because its
input is a packed image rather than a cube. On that path `0x1090` is the packed row's length
in 16-byte atoms, `in_w·in_ch/16`. Register `0x1078` contains that count in its high half
instead of the width.
The full sub-encoding is in [rk3576-regcmd.md](rk3576-regcmd.md).

The CORE and DPU blocks also re-pack. On the normal path they place the output geometry, the
requant and the output address at these offsets:

| Register | RK3576 offset | Value | RK3588 |
|---|---|---|---|
| CORE output geometry | `0x301C` | `(oh_task-1)<<16 \| (ow-1)` | `CORE_CLIP_TRUNCATE` is at this offset |
| DPU output height | `0x4024` | `oh_task-1` | |
| DPU output geometry | `0x4034` | `(oh_task-1)<<16 \| (ow-1)` | |
| DPU `OUT_CVT` triple | `0x40AC`/`0x40B0`/`0x40B4` | | `0x4080`/`0x4084`/`0x4088` |
| DPU output address | `0x4018` | | `DPU_DST_BASE_ADD`, `0x4020` |

The height field is the number of rows *this task* writes, minus one, and it is not halved. A
capture whose task covers half its plane shows `(oh-1)>>1`, which looks like a halved field. A
single-task capture of the same conv writes the full `oh-1`.
[rk3576-regcmd.md](rk3576-regcmd.md) gives the encoding as an implemented emitter.

The published map leaves three things open: the tiling-derived fields, the `0x1080` pad word,
and the multi-task slicing. The tiling-derived fields mirror Mesa's CBUF allocator output
(`input_banks`, `data_entries`, atomics), packed at RK3576 offsets. In the multi-task slicing,
the input-height field contains a per-slice height set by the CBUF allocator. All three are in
[rk3576-regcmd.md](rk3576-regcmd.md). The pad word's closed form is in §"Corrections to the
published map", and the CBUF fields are in §"The CBUF budget and `0x1040`". The slicing is in
§"The row window and its three registers".

The geometry fields the RK3576 computes with are narrower than their register halves (Erratum
RK3576-E6). Width and output channels have 13 bits, the kernel 5 and the stride 3.

[rk3576-regcmd.md](rk3576-regcmd.md) §"Geometry field widths" has the table and the evidence.

#### What the RK3576 map reveals about RK3588 gaps

The RK3576 map exposes no register missing from the RK3588 program. It names geometry
quantities that the RK3588 must also configure. The `librocketnpu` RK3588 register map
(`npu_hw.h`) leaves them as gaps or programs Mesa's hardcoded values. They are:

- Input line stride (`0x1090` = `in_w·4`)
- Input surface stride (`0x1094`)
- The precision/ARGB format word (`0x1018`)
- Duplicate feature dims (`0x118c`)

Two of them have RK3588 equivalents at different offsets, because the blocks re-pack. The
`librocketnpu` RK3588 matmul program already writes both [HW sweep, RK1]. The line stride
(`in_w·4`, RK3576 `0x1090`) is written at `CNA_DMA_CON1` `0x107c`, and the surface stride
(RK3576 `0x1094`) at `CNA_DMA_CON2` `0x1080`. Four more RK3576 offsets are RK3588 registers at
a new offset:

- The total weight bytes, `0x101c`, at RK3588 `CNA_WEIGHT_SIZE0` `0x1030` [source-confirmed:
  Mesa `registers.xml`]
- The CBUF data entries, `0x103c`, at RK3588 `CNA_CBUF_CON1` `0x1044`
- The CVT control word, `0x1048`, at `CNA_CVT_CON0` `0x104C`
- The burst lengths, `0x108c`, at `CNA_DMA_CON0` `0x1078`

The packing of each is in [rk3576-regcmd.md](rk3576-regcmd.md) §"Unnamed registers and their
RK3588 equivalents".

On the RK3588, `0x1090` is a clock-gating register (`*_DISABLE_CLKGATE` fields per Mesa
`registers.xml`), and both Mesa and the `librocketnpu` regcmd encoder leave it at its reset default.
The RK3576's use of that offset for the line stride is an offset collision. The remaining
RK3576-only offsets (`0x1018`/`0x1098`/`0x118c`) are absent from Mesa's RK3588 driver
and never emitted by the bit-exact `librocketnpu` matmul. They are RK3576 additions with no
RK3588 counterpart.

The apparent gaps are the re-pack reusing offsets that the RK3588 program fills elsewhere or
correctly leaves at default. The finding is verified on the matmul path, and the vendor conv
path is separately Mesa-validated. The RK3576 conv capture does not program the RK3588's other
unknown registers (`CORE_3030` `0x3030`, `DPU_40C4` `0x40C4`, `DPU_SURFACE_ADD` `0x40C0`).

### The CNA's kernel word

The high half of CNA `0x1024` contains the kernel width in bits [31:24] and the height in
[23:16]. Only a non-square kernel tells the two apart, and [rk3576-regcmd.md](rk3576-regcmd.md)
§"Unnamed registers and their RK3588 equivalents" has the encoding.

### The symmetry audit on the CNA

The CNA is bit-exact at non-square strides. On the direct path, whether the CBUF `F` settings
256 and 512 are honored depends on the resident weight footprint, not on the kernel.

At a 48×32 plane, with `s2x1` paired against `s1x2`, the strides are bit-exact over four kinds
of test point [HW sweep, H96 MAX M9]:

- Square kernels (k3, k5)
- Non-square kernels in both orientations (k3x1, k1x3)
- The depthwise datapath
- A stride larger than the kernel on one axis only (`s3x1` / `s1x3`)

The symmetry audit drives each geometry pair, `kh` against `kw` and `sy` against `sx`, at one
rectangular plane. A test point that holds `kh == kw` or `sy == sx` cannot show a transposed
field or a bound keyed on the wrong axis.

> [!CAUTION]
> At one granule total and one kernel, the same shape is exact at `ic` 32 and incorrect at `ic`
> 64 and 128. Software must select an `F` setting by the resident weight footprint, not by
> `kh == 1`. The detail is in [rk3576-regcmd.md](rk3576-regcmd.md).

`librocketnpu`'s planner selects the setting by the footprint, and every test point of the map
is bit-exact with it. The footprint rule does not apply to the depthwise path, where 4 granules
is dead, 32 is live and the low settings are declined outright. See "CBUF allowances on the
depthwise path".

The same audit found two defects in the pooling block. One is a transposed field, the pad
nibbles. The other is a bound fitted on the same symmetry: the output-width allowance, keyed on
the kernel width where the axis is the height. Each produces output of the correct size with
incorrect values, and neither shows at a test point holding `kh == kw` or `sy == sx`. "The
PPU's pad nibbles" and "The pooling output-width allowance" describe them.

### Regcmd encoder

The RK3576 needs its own regcmd encoder for the CNA, CORE and DPU geometry registers. They differ from
the RK3588's in four ways, so a single address-translation table over the RK3588 regcmd encoder is
insufficient:

- Offset moves
- Different bit-packing at shared offsets
- RK3576-only registers
- Registers whose field contains a per-task quantity packed differently

The datapath semantics (the precision-field encodings, the BS/BN/EW/LUT meanings, the
CNA→CORE→DPU block sequence) and the block bases are common to every RKNPU, and the vendor
stream matches them line for line.

#### Programming requirements

The vendor program has no PC trailer. The captured 139-entry program is CNA + CORE + DPU +
RDMA register writes only. The vendor kernel starts the job through its own
`enable_mask`/`task_number` in the task descriptor. Under `rocket`, the `OP_ENABLE` trailer that
writes `PC_OPERATION_ENABLE` triggers compute, and the RK3588 regcmds in `librocketnpu` end with
it.

> [!CAUTION]
> A register program transcribed from the vendor capture has no `OP_ENABLE` trailer. Under
> `rocket`, the pipeline is then configured and never starts. Software must add the trailer
> that writes `PC_OPERATION_ENABLE` to every RK3576 register program.

The feature-data address is `0x1088` on both CNA datapaths, as "CNA register encoding" states.

#### Software support

`librocketnpu` supports the RK3576 with two per-chip layers:

1. A `rocket_hw_profile`, `rocket_hw_rk3576`, for the machine parameters (CBUF geometry, tile
   caps, core count, datatype menu). The RK3588 has the same mechanism.
2. A per-chip regcmd encoder for the CNA/CORE/DPU geometry registers,
   [rocket-userspace `src/npu_regcmd_rk3576.c`](https://github.com/gregordinary/rocket-userspace/blob/main/src/npu_regcmd_rk3576.c).
   It covers the convolutions, the int8, int32 and fp16 matmuls, pooling and the LUT
   activations. It starts from the closed-form `predict_cna(params)` in `RK3576_CNA_MAP.md`,
   and its int8 convolution is checked register for register against the vendor programs.

The regcmd encoder plans the granule allowance per task. The chip autodetect selects the RK3576
profile and warns which datapaths have a regcmd encoder.

The per-chip dispatch is enforced, and it covers the whole op library. The refusal sits at the
generator: every public `gen_*` in `npu_regcmd.c`, which is the RK3588 regcmd encoder. The op library
composes those generators, and all of these reach the RK3576 through them:

- Conv
- Pooling
- The LUT activations
- The norms
- The FFN
- Softmax
- Reduce
- The ViT encoders

One check therefore covers every one of them, and every call site already treats a generator
failure as fatal. The RK3576's own entries (`rocket_conv2d_int8_rk3576()`,
`rocket_conv2d_fp16_rk3576()`, `rocket_pool_int8_rk3576()`, `rocket_act_int8_rk3576()` and the
`rocket_matmul_*_rk3576()` entries) use the RK3576 regcmd encoder and never reach the refusal.

The datatype capability mask cannot make that check. It says which *precisions* a chip can run,
and the RK3576 runs int8 and fp16 through its own regcmd encoder. The check is on the encoding.

A generic entry whose RK3576 counterpart has the same contract dispatches to it on the RK3576:
`rocket_conv2d_fp16()` runs `rocket_conv2d_fp16_rk3576()`, and `rocket_conv2d_dw_int8()` runs
`rocket_conv2d_dw_int8_rk3576()`. An entry whose contract differs refuses and names the RK3576
entry instead. `rocket_conv2d_int8()` and `rocket_matmul_int8()` return a raw int32
accumulator, where the RK3576's int8 entries requantize on chip and write int8.

### `PC_TASK_CON` task-number width

`PC_TASK_CON` packs `TASK_NUMBER` in the low bits, with `TASK_PP_EN`, `TASK_COUNT_CLEAR` and
`TASK_LAST_LAYER_CLEAR` directly above it. The field is 12 bits wide on the RK3588 and 16 on
the RK3576 [source-confirmed]. The vendor `rknpu` config contains the width as
`pc_task_number_bits`, and Rockchip gave the RK3576 bit assignment on the `linux-rockchip` list
[source-confirmed] (see [rk3576-regcmd.md](rk3576-regcmd.md)).

> [!CAUTION]
> With a 12-bit `TASK_NUMBER`, only the first submit of an NPU power session writes output on
> the RK3576. Mainline `rocket` builds the word from the RK3588 accessors unconditionally, so
> `0x7001` asks the PC for a task count of 28673 instead of 1. The PC starts that program, runs
> the one task it was handed and is left mid-stream. Every later submit in the same session
> leaves its output buffer untouched. Software must build `PC_TASK_CON` with a 16-bit
> `TASK_NUMBER` on the RK3576.

A gap past the 50 ms runtime-PM autosuspend hides the defect, because the power cycle resets
the PC. On an unpatched `rocket`, put a gap between runs in every register sweep on the RK3576.
Without one, the sweep measures this defect instead of the register.

Building the word from a per-SoC width, kept in `rocket_soc_data`, removes the defect. It
costs the RK3588 nothing: at 12 bits the driver still emits `0x7001`, bit for bit. With the
per-SoC width, gap-free submits are byte-identical to each other and bit-exact against a CPU
model [HW sweep, H96 MAX M9, measured 2026-07-25]. The patch is
`rk3576/npu/0008` in the `rk3576-npu` profile.

The cause is `TASK_NUMBER` alone, and the control bits above it do not matter. The driver does
need `pc_task_status_offset`: the register it moves to `0x48` is the live task counter a chained
stream's completion is read from. The RK3576-only `state_init` hook in the vendor driver is not
needed, and neither is `pc_dma_ctrl` [HW sweep, H96 MAX M9, measured 2026-07-25]. The task
counter itself is described in [rk3576-regcmd.md](rk3576-regcmd.md) §"Per-task `PC_DONE` and
the `PC_TASK_STATUS` counter".

### Convolution datapaths

The RK3576 regcmd encoder programs four convolution datapaths: direct int8, depthwise int8, fp16, and a packed-image
first convolution at int8 or fp16.

#### Direct int8 convolution

The direct int8 convolution reproduces a CPU model bit-exactly over this tested range:

- IC and OC from 8 to 128
- Planes from 8×8 to 128×64
- Kernels k1/k3/k5
- Stride 1 and 2
- VALID and SAME
- The full signed int8 feature range
- The padded border

The weight cube is the RK3588's. The RK3576 regcmd encoder programs each of these stages correctly:

- The CNA operand DMA
- The CBUF staging
- The CSC
- The CMAC
- The BS bias add
- The OUT_CVT requant
- The output geometry
- The writer

Three bounds apply, and `librocketnpu`'s emitter keeps each by construction. Both channel counts
are *programmed* as multiples of 32. The feature plane stays inside the CBUF budget. The resident
weight slice stays inside what the output-channel group count allows. The encoding, its tests,
the corrections to the published map, and what the hardware confirms are in
[rk3576-regcmd.md](rk3576-regcmd.md).

A plane past the CBUF budget runs as row windows. Each task reads a window of the input rows and
writes the output rows it supports. The split reproduces the CPU model bit-exactly at every shape
tried, including 112×112 and 224×224 at ic=32, which have no single-task plan at all. Three
registers take a second value only on a windowed program (`0x40b8`, `0x1018`, `0x1038`).

Run as its own submit, each window costs about 1.2 ms [HW sweep, H96 MAX M9, 2026-07-25]. The
`rocket` measured lacks patch `0012` and polls for completion at the stock 1 ms period. The
driver's completion poll sets that cost, not the silicon, and at the 50 us period of `0012` a
submit costs about 0.44 ms. Unchained, a split's cost therefore scales linearly in windows, and
software should plan the fewest windows that fit.

On a kernel that supports chained submits, `librocketnpu` chains an int8 convolution's row
tasks into one kick by default. The chain removes the poll between them
([rk3576-regcmd.md](rk3576-regcmd.md) §"Chained row tasks").

With a `rocket` that has the per-SoC `PC_TASK_CON` width, the whole tested range runs in one NPU
power session. It runs with no gap between shapes and no cold-start retries. Inside the
weight-slice bound every shape is bit-exact, and `librocketnpu` refuses the shapes past it rather
than running them.

> [!CAUTION]
> The resident weight slice drives every output channel only while `ic*kh*kw <= 4608`. Past it,
> the trailing output-channel groups are lost one at a time. Software must keep the resident
> weight slice within that bound.

`librocketnpu`'s row planner has an API trap: a single-task plan can still have a window shorter
than the plane. [rk3576-regcmd.md](rk3576-regcmd.md) has both limits.

#### Depthwise convolution

The depthwise int8 convolution is bit-exact over 35 test shapes:

- Channel counts 8 to 256, including those that are not multiples of 32
- Kernels 1 through 7
- Both strides, SAME and VALID
- Planes to 112×112, including odd ones
- Shapes across a row window

Four formulas in its register program are confounded in captures of existing models:

- The channel field in `0x4050`
- Two different channel-count roundings
- The destination surface's round-up to four
- `0x118C`, which is `iw-1` in both halves

Two of the depthwise path's buffers differ from the direct path's, and no capture shows either.
A `.rknn` contains a register program and nothing about the memory those registers address. Both
layouts were measured on the RK3576:

- The coefficient group is 48 bytes for 8 output channels, with no weight-zero-point field. The
  direct group is 64 bytes, with one.
- The int8 weight cube groups channels by 64, with two live bytes per channel per tap. The float
  cube groups by 32, with one 16-bit slot.

> [!CAUTION]
> A wrong depthwise coefficient group or weight cube fails silently, so software must pack both
> in the depthwise layouts ([rk3576-regcmd.md](rk3576-regcmd.md) §"Depthwise convolution").

> [!CAUTION]
> The depthwise output's surface stride is `round4(ow*oh_full)` elements, not the plane, and
> software must size and read the output BO at it ([rk3576-regcmd.md](rk3576-regcmd.md)
> §"The depthwise output surface stride").

`rocket_rk3576_out_surf_elems()` returns the depthwise surface stride.

#### fp16 convolution

One task of the fp16 convolution program contracts exactly 16 input channels. An arbitrary `ic`
runs as `ic/16` slices summed on the host. The fp16 convolution is bit-faithful at any
input-channel count, delivers every output channel, and a caller can drive it. The bound is the
program's and not the SoC's: a matmul-form fp16 program contracts 2048 in one job (see "The
precision fork").

The DPU's output element stride is `16/ic` words, and that one fact accounts for two output gaps
[source-confirmed, HW sweep, H96 MAX M9, measured 2026-07-26]:

- At `ic = 8` the stride is two words per element. The writer uses four bytes for a two-byte
  element, and only `oc/2` channels reach DDR.
- At `ic = 32` two channels collide in one slot, and the odd ones are lost.
- At `ic = 16` the stride is exactly one. The output is the plain cube layout, with every
  programmed channel present exactly once.

The 16-channel bound is therefore a contraction width, not a writer defect. The split around it
reproduces the model exactly at `ic` 16/32/64/128 crossed with `k` 1/3/5
[source-confirmed, HW sweep, H96 MAX M9, measured 2026-07-26].

> [!CAUTION]
> An fp16 task programmed with a wrong `ic` writes a full, correctly sized output with wrong
> values, and nothing faults. Software must program 16 input channels per task. `librocketnpu`
> refuses anything outside the tested range rather than warning.

> [!NOTE]
> A test input held uniform in one axis does not detect this bound: under it, the datapath looks
> exact and is not. The detail, the test inputs and the list of traps are in
> [rk3576-regcmd.md](rk3576-regcmd.md).

> [!CAUTION]
> Three registers select the float mode, CNA `0x100C` and DPU `0x4038` and `0x4050`, and
> software must program all three together ([rk3576-regcmd.md](rk3576-regcmd.md) §"The
> float-mode registers").

The float weight cube groups both channel axes by 16, not by the int8 cube's 32. For an fp16
*output*, software must set the float narrowing at DPU `0x40B0` bit 16. `0x4010` bits [31:29]
select an output width and do not convert.

RKNN-Toolkit2 emits a genuine fp16 conv program for the RK3576 from a float ONNX with
`do_quantization=False`, which gives a float capture.

On the partial output stage, measured 2026-07-26, the split costs `ic/16` submits at about
1.4-1.5 ms of NPU wall-clock time each, flat in the work. At 56×56, `k = 3` does nine times the
multiply-accumulates of `k = 1` and takes the same 6 ms, so no compute term is visible at these
shapes. The cost is the fixed per-submit dispatch overhead, the 1.1-1.3 ms the int8 path then
took once for its whole `ic`. Host packing and
de-tile add a significant share at a full plane. The split multiplies it too: `ic/16` weight
repacks and `ic/16` de-tiles [HW sweep, H96 MAX M9, measured 2026-07-26]. The per-shape NPU and
host times are in [rk3576-regcmd.md](rk3576-regcmd.md) §"Cost of an fp16 conv".

**Not characterized:** the host time, which varies by a factor of two run to run on this board.

#### First convolution on a packed image

A convolution whose input has four or fewer channels runs as a separate program. The CNA reads a
packed image straight out of DDR and expands every pixel to four lanes. One task therefore
contracts the whole image, with no input-channel split. The program runs at fp16 and at int8, so
a float and a quantized vision stem both run. The int8 form is the one to use.

At fp16 it is bit-exact against a CPU model over 24 test shapes [HW sweep, H96 MAX M9]:

- Image channels 1 through 4
- Kernels 1/3/5/7
- Both strides, SAME and VALID
- Planes 16×32 through 224×224
- Output channels 16 through 96

A vision model opens with the 224×224 stride-2 stem. That stem has no single-task plan (6272 CBUF
granules against a limit of 6144), so it runs through the row window. Rows and output channels
then split together on the two axes. [HW sweep, H96 MAX M9]

Three parts of the fp16 program must be right together. The first is the float weight cube: four
lanes per (output channel, tap), with output channels interleaved by sixteen inside a tap. The
second is the register program, which at fp16 is a different program, not the int8 one at another
precision:

- It has no channel fold.
- The CBUF entry count loses the fold's `+1` lookahead.
- The row stride takes the element size.
- The CVT is bypassed rather than configured.

The third is the output-channel bound.

> [!CAUTION]
> One fp16 packed-image program delivers thirty-two output channels and no more. At `oc` 48, 64
> and 96, exactly 32 whole channels come back and the rest of the output is never written. The
> bound holds even though the program matches the vendor's own captures at those shapes register
> for register. Software must split the output channels into tiles of 32.

> [!CAUTION]
> Over an integer-arrangement coefficient group, the vendor's float value of `0x501C` stops the
> DPU writing. Software must keep that BS operand reader at the integer path's `0x710`
> ([rk3576-regcmd.md](rk3576-regcmd.md) §"The vendor's float BS arrangement").

The vendor's float epilogue is a different BS arrangement. `librocketnpu`'s coefficient group is
packed for the integer arrangement, which is bit-exact under either ALU mode. A vendor capture's
register values hold for the vendor's whole program, not for one value spliced into a different
program.

At the 224×224 k3 s2 stem with 32 output channels, the int8 entry takes about a quarter of the
fp16 entry's time [host-computed]. "Cost of the library entries" gives both times and their
conditions. The int8 program matches a CPU model bit-exactly at twenty shapes, including the
stem at `oc` 64 and `k` 7 [HW sweep, H96 MAX M9]:

- Image channels 2-4
- Kernels 3/5/7, both strides
- Planes 16×32 to 224×224
- `oc` 32 to 96

Its weight cube differs from the float one in every axis but the lanes:

- One byte per weight
- Output channels grouped by 32
- The tap row outside that group
- The tap column folded into the same `round16(4*kw)` row as the four lanes

One int8 program delivers 64 output channels, where one float program delivers 32. Above 64,
`librocketnpu` splits the output channels, as on the float path. Whether one int8 program
delivers more than 64 is not characterized.

The packed-image program has four geometry bounds:

- An input width that is a multiple of 16
- A non-zero left pad
- An output width of exactly `iw/stride`
- An output width that is also a multiple of 16

`CNA_PAD_CON0` bits[15:8] alone decide whether the DPU writes at all, and `pad_top` does not.

> [!CAUTION]
> Three of the four geometry bounds fail silently. A zero left pad writes nothing at all.
> Software must keep all four. `librocketnpu` refuses a shape outside them.

None of the bounds appears in any capture, because every captured first conv is a 3×3 stride-2
SAME convolution and satisfies all four. A one-channel image is programmed as two, a zero lane
against zero weights, because the emitted program does not fetch a single channel. That form is
bit-exact to 224×224, with the same tested range as two. A TFLite stem does not satisfy the pad
bound directly and still runs, through an input shift ("TFLite stem through an input shift"
below). See [rk3576-regcmd.md](rk3576-regcmd.md) for the cube and the measurements.

Beside the four geometry bounds, the input zero point bounds the border. With the image widened to eight
channels, the direct path is exact everywhere, its border included. The direct path's result
holds at the same zero points and against the same reference. [HW sweep, H96 MAX M9]

> [!CAUTION]
> At a non-zero input zero point, the packed-image program's interior stays bit-exact and its
> padded taps do not. The border falls to about half exact the moment the zero point leaves zero
> [HW sweep, H96 MAX M9]. Software must materialize the pad columns ("Materialized pad columns"
> below), or use the direct path.

A TFLite MobileNet's first convolution has a zero input zero point after the uint8 rebase. The
bound is an axis: the pad columns, at both ends and at every row. `librocketnpu` materializes
those columns rather than refusing the shape, so any zero point runs. The cost is a wider program
and an output that cannot be a consumer's cube.

`rocket_conv2d_fp16_rk3576()` takes the same row-major CHW tensor as every other entry, and
performs the interleave, the lane cube, the output-channel split and the de-tile. It splits the
output channels one submit per tile of 32. `rocket_conv2d_int8_rk3576()` performs these stages:

- The packed image
- The cube
- The row window
- The output-channel split
- The zero-point fold
- The de-tile

#### The `CNA_PAD_CON1` pad map

`CNA_PAD_CON1` is the CNA border pad constant: the value a padded tap feeds the MAC. No value of
it corrects the packed path's pad columns. Its map has three properties [HW sweep, H96 MAX M9]:

- The map is `(int8_t)byte`. Neither path centers it: `0x00` feeds 0, `0x7F` feeds 127, `0x80`
  feeds -128, `0xFF` feeds -1.
- It is per image channel on the packed path: channel `c` reads byte lane `c`. A `0x7F` in lane 1
  alone moves channel 1's pad and neither of the others. The direct path reads one value across
  its whole MAC group.
- The packed path's pad columns do not read it. The pad rows track the register. The pad columns
  feed 0 whatever is programmed, in all four lanes and at every value tried, the unused fourth
  ARGB lane included. On the direct path both axes track it.

The dead pad columns are the half of the border that is wrong at a non-zero input zero point.
`librocketnpu`'s emitter writes the identity the map wants. The direct path takes
`(int32_t)in_zp`, and the packed path the byte `(uint8_t)in_zp` in each image channel's lane.
Both are `0x1084 = 0` at `in_zp` 0.

#### Pad columns on the packed path

On the packed path, the pad columns feed a constant 0 at both ends and at every row. The pad rows
and the corners honor the register at both ends. On the direct path all of them honor it.
The value each edge feeds, as `fed = output + in_zp` [HW sweep, H96 MAX M9]:

| Configuration | Pad rows (top, bottom) | Pad columns (left, right) | Corners |
|---|---|---|---|
| Packed, `in_zp` 0 | 0, 0 | 0, 0 | 0, 0 |
| Packed, `in_zp` 20 | **20, 20** | **0, 0** | 20, 20 |
| Direct, `in_zp` 0 | 0, 0 | 0, 0 | 0, 0 |
| Direct, `in_zp` 20 | 20, 20 | 20, 20 | 20, 20 |

At `in_zp` 0 a dead column feeds the right answer. The wrong trailing region of the output is the
right pad column.

No other register reaches those columns either. The packed and direct programs differ on 17
non-address registers at one geometry. Setting any one of them to the direct program's value
leaves the columns at 0 wherever the interior still computes. The one that moves the columns to the
zero point, `CNA 0x100C -> 0`, zeroes the ARGB mode word itself. The program then stops being the
packed encoding, and its interior fails.

**Not characterized:** a condition of two or more registers on the pad columns.

#### Materialized pad columns

The pad columns are materializable, so the bound does not end the encoding. The error is `-in_zp`
times the sum of the weights over the taps in a pad column, and it is data independent. It sits in
the accumulator, though, and the entry returns a requantized int8. Repairing an affected output
therefore means recomputing it.

Host repair is the expensive method. On a 224×224 k7 s2 stem it costs 9.8 ms of host work against
a ~2 ms saving, with the governor pinned. The work is 3 output columns × 112 rows × 64 channels at
147 taps.

The input extension is the cheap method: it keeps the hardware from synthesizing the columns.
Extend the image by

    L = pad - p + stride*d

columns at the input zero point, give the program `pad_left = p`, and take output column `x + d`
as the model's output column `x`. The one column the hardware still synthesizes is read only by
output `x' = 0`, which is discarded. The encoding's own geometry bounds (`iw % 16`, `ow % 16`,
`ow*stride == iw`) then force a wider programmed input and output, and the surplus output columns
are cropped. The programmed image grows by sixteen output columns, `16*stride_x` input columns
(`iw + 16*stride_x`), which is what the geometry bounds force.

The extension is bit-exact against the direct lowering at four test points, which vary everything
the formula is a function of. In each, the unextended program is wrong on pad-column outputs alone,
with the interior clean [HW sweep, H96 MAX M9]:

| Test point | Model pad | L | `iw` | `ow` | `in_zp` | Unextended, wrong | Extended, wrong |
|---|---:|---:|---|---|---:|---:|---|
| ResNet-18 stem `k7 s2` | 3 | 4 | 224 -> 256 | 112 -> 128 | -128 | 7938/21504 | 0/802816 |
| `k5 s2` | 2 | 3 | 224 -> 256 | 112 -> 128 | -128 | 14336/14336 | 0/802816 |
| `k3 s2` | 1 | 2 | 224 -> 256 | 112 -> 128 | -128 | 1086/3584 | 0/401408 |
| `k3 s1` | 1 | 1 | 64 -> 80 | 64 -> 80 | +20 | 214/4096 | 0/131072 |

Two geometries have no extension: a zero left pad (a different bound, where the DPU writes nothing
at all) and `kw < 1 + stride_x`, which asks for a negative trailing pad.

`librocketnpu` performs the extension. A caller passes its own geometry, and nothing about the
descriptor says an extension happened. The entries `rocket_conv2d_int8_rk3576()` and
`_pack_rk3576()` plan it whenever the packed encoding meets a non-zero input zero point. They
materialize the columns inside the image they already interleave. They crop the surplus in the
de-tile they already run, so the crop is a narrower read rather than a pass of its own.

Both entries still refuse the two geometries with no extension. The entry is exact at the caller's
own geometry at all four test points above [HW sweep, H96 MAX M9].

The extension changes the join to the next layer, and the join still holds. The output is `owx`
wide where the consumer wants `ow`. The caller's tensor starts at column `D = 1` of it, because the
extension discards the leading output column, the one the hardware still synthesizes. The
producer's output is therefore a sub-rectangle of its output buffer rather than the caller's plane.
Reading it in place needs a row pitch and a column offset the consumer can be told.

#### A plane inside wider rows

The PPU and the CNA can each read a plane that sits inside wider rows [HW sweep, H96 MAX M9].

On the PPU, three registers describe the read:

| Register | Function |
|---|---|
| `0x600C` | What the windows consume: `(ow-1)*sx + kw` less the leading pad, clamped to the plane |
| `0x7024` | The DDR line stride |
| `0x7028` | The channel-group jump |

The plane appears only in the strides. The PPU honors a line stride above the consumed extent,
and a source base part way into a row [HW sweep, H96 MAX M9].

> [!CAUTION]
> If one `iw` stands for both the plane and the pitch, a pitch passed as the plane lifts the clamp
> on `0x600C`. A window meant to read a synthesized pad then reads the producer's surplus columns
> instead. The error shows only where the windows overhang the plane, and there the output is
> full, plausible and wrong. Software must program the plane and the pitch separately.

The field `pool_params_rk3576_t.src_line_elems` is the pitch, and 0 takes `iw`, so every program
that does not set it is byte-identical. `rocket_rk3576_cube` has `pitch_w` and `col_off` (0 and 0
= a contiguous plane, which is every other producer here). A pool consumer takes them.

The library's convolution consumer refuses on the field, for reasons of buffer ownership rather than
of the register set (below). The column offset is added at the program and not folded into the
cube's byte offset. The chained-run rule asserts a cube join by comparing a consumer's feature base
against a producer's output base for exact equality. Folding the offset in moves that address by
one atom and breaks every chained run the join exists to create.

The CNA reads a pitched plane through three registers, none of which is the pitch on its own.
Its width field is `0x1078` high half (`iw-1`), and its RK3588-named line stride is `0x1090`
(`iw*4` words). `librocketnpu`'s emitter derives both from `iw`, because every capture has a tight
plane. Measured on the RK3576, the registers that read a pitched plane are:

| Register | Function |
|---|---|
| `0x1044` low half | The DDR row advance, in 64-byte granules |
| `0x103C` high half | The fetch length, also in granules. It must stay at the plane's count |
| `0x1094` | The channel-group jump, already a caller-supplied quantity |
| `0x1078` low half | The DMA's row budget, spent at the advance and not at the fetch length |

The CBUF is filled contiguously with the fetch length, and the window walks it at `iw` atoms a
row. The row budget is the register that is not obvious. A pitched walk consumes
`fetch_rows * entries_plane` granules of address at the pitch's rate.

> [!CAUTION]
> Moving `0x103C` to the pitch along with the row advance puts the read back at the tight stride.
> The output is then full and wrong. Software must keep `0x103C`'s high half at the plane's count.

> [!CAUTION]
> With the row budget left at the plane's value, a pitched walk runs out part way down the plane.
> Every row past that point reads whatever the DMA had left. Software must inflate `0x1078`'s low
> half to `ceil(rows * entries_pitch / entries_plane)`, which makes the map affine to the last
> row.

The RK3588 names `0x1090` the line stride. On the RK3576 it is not the row stride. It advances the
address by its own value once every four rows, while the rows between step by the fetched width.
No value of it sets a pitch.

The window grid does not follow the budget. The output extent and both derived pads come from the
real geometry. A pitched convolution therefore still synthesizes the trailing pad that a widened
plane would read real bytes for. Programming the pitch as the plane, and letting the output
extent limit the windows, differs in that alone. That cheaper form is exact wherever the window
grid stays inside the caller's plane: at k1, and at the stride-2 shape whose grid fits exactly.

> [!CAUTION]
> A convolution that programs the pitch as its plane is wrong on the trailing columns wherever a
> trailing pad is derived. At 28×28 k3 SAME it is wrong on 807 elements in column 27 of 28. At k5
> it is wrong on 659 in columns 19-20 of 21. Software must program a pitched read wherever a
> trailing pad is derived.

The pitched read is bit-exact against a tight-plane reference [HW sweep, H96 MAX M9]. The feature
base is a plain address at atom granularity, as the PPU's is. The field `conv_params_t.in_pitch_w`
is the pitch, and 0 takes `iw`, so every program that does not set it is byte-identical. Two
geometry bounds apply to a pitched read, and both are silent: past either, the output is written in
full and wrong.

> [!CAUTION]
> Both the pitch and the plane must fill whole 64-byte DDR granules. An odd plane at ic=32 is 10.5
> granules a row. It has a rounding the budget arithmetic cannot undo, and is wrong at every
> pitch. Software must keep `iw * ic * elem % 64 == 0`.

> [!CAUTION]
> A pitched task's row window is the unpitched allowance scaled down by the granule ratio twice. A
> 112-wide plane inside 128-wide rows has an allowance of 48 rows. Windows of 40, 41, 42 and 47
> rows are all wrong, while 16, 32 and 36 are bit-exact. Software must keep a pitched task's row
> window within the scaled allowance.

The scaled allowance is a bound rather than the exact limit. Like the unpitched allowance it
scales, it is safe in one direction only. A window too small costs a submit, and one too large
writes a silently wrong output.

**Not characterized:** windows between 36 and 40 rows.

> [!CAUTION]
> One register program can change what the next one computes on the RK3576. Two CNA pitch
> configurations leave the NPU writing nothing for every submit that follows, in the same process
> and the next. A preceding configuration can also change a following one's map, even when the two
> emit byte-identical streams. Software that probes registers must run one configuration per
> process before trusting a sequence.

#### The materialized stem on a graph

On ResNet-18, the materializing packed stem saves 1.8-1.9 ms, 20%, against the direct stem, at
the same 27 joins of 30 adjacent pairs either way:

| Stem | Wall-clock time, ms | Submits | Tasks |
|---|---:|---:|---:|
| Materializing packed stem, joined to the pool | **7.4** | 1 | 33 |
| Direct stem | 9.2-9.3 | 1 | 38 |

**Conditions:** H96 MAX M9, ResNet-18 at `bench 100`, three repeats each, governor `ondemand`,
everything else equal [HW sweep, H96 MAX M9, 2026-08-02]. The write guard brackets each layer's
output.

With one bracket per BO, the packed-stem graph measures 6.5-6.6 ms
([../perf/rk3576-graph.md](../perf/rk3576-graph.md) §"One bracket per BO").

Every compute layer is bit-exact against the CPU model, and the top-1 is TFLite's own. The packed
stem heads the chained run and the pool sits inside it, so the graph stays one hardware kick. The graph's
task count falls from 38 to 33, because the packed stem is one row task where the direct lowering
needs six (measured in both configurations).

The other three graphs do not change (MobileNetV1 5.0, MobileNetV2 6.7, Inception V1 8.7 ms). Both
MobileNets have TFLite's `pad_left = 0`, which no extension reaches. Inception V1's stem has
`in_zp = 0` and so materializes nothing.

With the governor pinned to `performance`, the two configurations measure 6.0 against 7.7 ms over
three repeats each, the same direction at 1.7 ms.

Per call, resident and governor-pinned, at that stem geometry, the materializing packed call takes
1.41 ms against the direct lowering's 3.13. The same packed program at `in_zp` 0 takes 1.26 ms
[HW sweep].

The join removes one tensor transposed twice: the same 784 KiB out of a cube and back into one.
Warm over 20 inferences, the stem's readback measures 1.10 ms of its 2.10 (0.10 the DPU drain).
The max pool's scatter measures 0.85 ms of its 1.45.

A host compaction is the alternative, and the join does not need it. Copying the 128-wide output
into a 112-wide cube moves 4 channel groups × 112 rows of 1792 contiguous bytes. It takes 0.178 ms
over two BOs (4.52 GB/s) and 0.163 in place, against a flat memcpy of the same bytes at 0.107
(7.47 GB/s). A 0.154 ms PREP/FINI bracket over 784 KiB comes on top. The compaction therefore costs
~0.33 ms, and as host work between two layers it breaks the chained run. Reading the output in place costs
nothing.

The frontend chooses the form, materializing where the next layer is a pool. A stem whose consumer
is a convolution is a program the RK3576 runs: the pitch encoding above is bit-exact, and the
generator emits it. The library's `rocket_conv2d_int8_cube_in_rk3576()` does not pass a pitch
through to the handle, so no graph reaches it. No graph in the corpus has a materializing stem that
feeds a convolution, either. ResNet-18's is the only materializing stem, and its consumer is the
max pool, which is why the pool is enough. [HW sweep, H96 MAX M9, 2026-08-02]

#### TFLite stem through an input shift

A TFLite stem runs on the packed path by moving the input rather than the pad. Whether the program
can have a zero left pad is decided at the geometry, not at `CNA_PAD_CON0`. A non-zero left pad
and an output extent of `ow*stride == iw` are jointly inconsistent with a zero lead at k3 s2.
There, a zero lead gives `ow = iw/2 - 1` and never `iw/2`. The entry refuses before any register
is written.

Padding cannot move a stride-2 sample grid's parity, but the grid also moves when the input moves.
An input shifted one pixel against a pad of one is a shift of two, a whole stride. Extend the image
by TFLite's trailing row and column. Feed the program that buffer starting at row 1 column 1, and
leave both register pads at 1. Output `(y,x)` then taps image rows `2y..2y+2` and columns
`2x..2x+2`, which is TFLite's grid exactly.

At 224×224 k3 s2 oc=32, every interior output is bit-exact against TFLite's own SAME convolution
over the original image [HW sweep, H96 MAX M9]. The output's own top row and left column, 1.8% of
the output, remain. Their outermost taps read the hardware's pad constant instead of image row 0
and column 0, and a host fix-up corrects them.

In a resident graph the shift is slower than the widened direct path. Its output is byte-for-byte
identical to the widened direct path over all 401408 elements of the stem's output. Interleaved at
`bench 100`, the shift costs 5.5-5.8 ms against the widened path's 3.5-3.7. The shift reduces
the layer from five submits to one. Even so, with resident weights and separate submits per
layer, it takes MobileNetV1-224's inference from ~30 ms to ~31.5 [HW sweep, H96 MAX M9,
2026-07-29].

The shift's own cost is the border fix-up, 1.7-1.9 ms for 1.8% of the output. It is memory-bound
and not MAC-bound: 7136 outputs, nine scattered input cache lines each. Hoisting the loop's bounds
into registers moves it by under 0.2 ms.

`rocket_conv2d_int8_pack_rk3576()` packs the packed-image cube too, and the host interleave is
vectorized, so the packed path has a resident handle. The lowering is kept, exact, and off by
default. The MobileNets it targets have `pad_left = 0`, and their whole stem execution is 0.30 ms
of `exec + drain` against that 1.7-1.9 ms. [HW sweep, H96 MAX M9, 2026-07-29]

#### Packed-image path traps

> [!NOTE]
> An emitter that reproduces vendor captures register for register can still write nothing away
> from the captured geometry. Submit a vendor capture verbatim, with only its address registers
> patched, before treating a datapath as non-working.

The packed-image mode works at the captured geometry. Walking back from that geometry one axis at
a time yields all four bounds above.

The CNA converter's offset is inert on the packed path:

| Registers | The ARGB register table | Measured on the RK3576 |
|---|---|---|
| `0x1054`-`0x105C` | The uint8 zero point the CVT subtracts, as the datapath's description says | Inert. The raw byte is read as a signed int8, with no subtraction [HW sweep, H96 MAX M9] |

An image written at `raw = s + (zp+0x80)` comes back with the raw byte read as a signed int8 and
no subtraction at all. A raw `0x80` reads -128, and `0xFF` reads -1. The packed image is therefore
plain two's complement. The input zero point folds into the coefficient group's `A` term exactly as
the direct path folds it. [HW sweep, H96 MAX M9]

> [!CAUTION]
> The fp16 packed-image program prevents its own next submit from writing, and that hazard is most
> of its wall-clock time. A second submit of the same program comes back with its output never
> written. The write rate against the gap between submits is 1/20 at 0 and 20 ms, and 8/20 at
> 60 ms. From 100 ms it is 20/20 [HW sweep, H96 MAX M9, 2026-07-27]. Those rates are on the
> `rocket` module before interface 1.0, at the default 50 ms `power/autosuspend_delay_ms`.
> Software must let the NPU power domain suspend before the next submit.

The gap at which every submit writes is twice the autosuspend delay
([rk3576-hazards.md](rk3576-hazards.md) §"The clearing idle").

**Not characterized:** the write rate against the gap on `rocket` 1.6.0. There a submit the
hazard leaves unwritten retires at the 125 ms backstop.

The hazard is not specific to the packed-image program. It is the wide-output hazard of a
partial output stage, which [rk3576-hazards.md](rk3576-hazards.md) §"The wide-output hazard"
describes. A wide output written through a whole output stage does not have it, and neither does
the matmul-form fp16 program's fp32 output. The int8 packed-image program does not have it
either: every submit writes at a zero gap [HW sweep, H96 MAX M9].

### Narrow input-channel counts on the direct datapath

The int8 direct cube is a 32-channel MAC group at every input-channel count: `pad_ic(3)` and
`pad_ic(32)` are both 32. An `ic` of 3 and an `ic` of 32 therefore give the same register
program, the same weight-cube size and the same feature-cube size. The channels past `ic` are
the cube's padding. A narrow input-channel count runs on the direct datapath.

For `ic <= 4`, the direct datapath is an alternative to the CNA's packed-image sub-encoding, and
it needs no host widening. It also has none of the packed-image encoding's three geometry
bounds:

- A non-zero left pad
- An output width of exactly `iw/stride`
- That width also a multiple of 16

The field `rocket_conv2d_desc.direct_datapath` selects it. The int8 entries honor it. The RK3576
fp16 entry refuses it for two reasons. Its float cube groups sixteen input channels rather than
thirty-two, and no `ic` below five has been run through it. The RK3588 generator satisfies it by
construction, having only one convolution encoding.

The direct path is bit-exact on 24 shapes, including a TFLite 224 stem at its asymmetric extent.
On the graph the stem goes 2.21-2.24 ms to 1.97-1.99, byte-identical over all 401408 elements
against both the widened lowering and the packed-image one.

The saving is the widened image's allocation, fill and copy, not the scatter. The NEON packer
stores whole 16-byte atoms whatever the live channel count is. The scatter therefore writes the
same 802 KB either way, and only its reads shrink (150 KB against 401 KB). The stem's feature
bucket moves 0.71-0.91 ms to 0.60, and the rest of its wall-clock time is the submit.

The CNA's border substitution covers the whole programmed channel group. At a pad tap the cube's
padding channels therefore read the border constant, while at an interior tap they read whatever
was memset into them. The `B` term sums over every tap. The disagreement appears in the
accumulator scaled by that output position's pad-tap count, which varies per position and cannot
be folded into `A`.

> [!CAUTION]
> With both the input and the weight zero point non-zero, every `ic` from 1 to 31 produces a wrong
> border with an exact interior. The defect does not depend on the direct-datapath flag: `ic` 8,
> 16 and 24 reach it with no flag involved. Software must apply both of the following, because
> either alone is wrong everywhere instead of only on the border:
>
> - The cube's padding channels hold the border constant itself, the input zero point. That
>   includes the allocation's fill and the dead lanes of a partial C2 atom, which the packer must
>   not zero.
> - The zero-point fold counts the programmed taps:
>   `A = bias - in_zp*sum_w + in_zp*w_zp*icreg*kh*kw`.

The fold is inert in two cases: at `ic` a multiple of 32 the two counts are equal, and at
`w_zp == 0` the term is zero.
[HW sweep, H96 MAX M9, 2026-07-30]

### Asymmetric padding as an output extent

The CNA's trailing pad is the pad its last window consumes, derived from the output extent and
the leading pad. `CNA_PAD_CON0`'s bottom and right fields contain that value, which the regcmd encoder's
`r76_trail_pad()` derives. An asymmetric pad is therefore an output extent, not a materialized
border. TFLite's SAME at an even input and stride two pads `pad_before = 0` and `pad_after = 1`.
That pad is a leading pad of zero against an output extent one larger than the symmetric formula
gives, and nothing has to be copied.

Six int8 test shapes with a zero leading pad against a consumed trailing one, direct and
depthwise, are all bit-exact. A descriptor that can only derive the output from a symmetric pad
forces a graph runner to materialize the border into a row-major buffer. That buffer breaks the
cube chain at every stride-2 depthwise layer.

`rocket_conv2d_desc.oh/.ow` name the extent. Zero means "whatever `rocket_conv2d_oh/ow` derive",
so every caller that memsets the struct keeps its existing behavior. The functions
`rocket_conv2d_trail_y/_x` return the pad the extent implies. The bound is the kernel: a
trailing pad of `kh` or more is an output row whose whole window is pad, and it is refused. The
fp16 RK3576 path, both packed-image paths and `rocket_conv2d_plan` (the RK3588 fp16 generator)
refuse an extent they did not derive themselves. The int8 path accepts this geometry, and no
other path has measured it.

On MobileNetV1-224, five layers pad asymmetrically: the stem and the four stride-2 depthwise
layers. The derived trailing pad matches the model on all 30 compute layers. Every layer stays
bit-exact against a CPU model of the RK3576's arithmetic.
[HW sweep, H96 MAX M9, 2026-07-29]

> [!NOTE]
> A per-layer reference must use the same lowering as the layer under test. A test that builds
> its own descriptor without the extent runs the layer at 55 rows against a reference of 56. The
> five asymmetric layers then report maxdiff 255 at 5-29% exact. That lowering disagreement reads
> exactly like a hardware fault.

### The depthwise weight zero point

The int8 depthwise cube gives every (channel, tap) two live bytes, and the datapath adds them.
The sum is a nine-bit effective weight, so `w - w_zp` fits exactly across the pair. Its only
bound is the pair's range of [-256, 254] [HW sweep, H96 MAX M9]. A depthwise weight zero point is
therefore applied in the weight cube. The 48-byte depthwise coefficient group has no `B` field to
fold it into, and needs none.

Every per-tensor TFLite depthwise filter has a zero point, and the graph's thirteen depthwise
layers run on this fold. The coefficient `A` already computes `-in_zp*(sum_w - w_zp*taps)`, which
is the fold a pre-centered cube wants, so nothing downstream changes.

Re-centering in int8 instead is not available, because 12 of this model's 13 depthwise layers
overflow. Re-quantizing to a symmetric scale would coarsen the weights by up to 1.65x rather than
give an exact answer. The lowering is bit-exact at both signs, at both channel-group boundaries,
at k=5 and at stride 2.
[HW sweep, H96 MAX M9]

### Per-axis weights on the depthwise path

The 48-byte depthwise coefficient group contains the same per-output-channel int16 `C` as the
64-byte one, so per-axis weight quantization reaches the depthwise path. Depthwise is the easier
case, because its accumulator bound, `128*sum|w|` over `kh*kw` taps rather than `ic*kh*kw`, is
one to two orders of magnitude smaller. The `C` ramp therefore reaches the int16 field's 32767
maximum. The gain resolution a single `OUT_CVT` shift leaves is then finer than the direct
path's at the same channel count. [HW sweep, H96 MAX M9]

A depthwise layer is one task whatever the channel count, because output channel `c` is bound to
input channel `c`. With no output-channel window to program and no scale sort to make, the
accuracy costs none of the extra submits the direct path uses. Over eight shapes (kernels 1, 3
and 5, both strides, 32-256 channels), the worst distance to an exact per-axis requant is 0.5
counts at spreads to 100x. The worst distance is 0.8 at 1000x, against 0.5-1.9 on the direct
path. A MobileNet is mostly depthwise, so a per-axis MobileNet depends on this path.
[HW sweep, H96 MAX M9]

### The weight slice and the feature allowance

On the RK3576, the resident weight slice and the feature allowance `F` share one CBUF budget
[HW sweep]. The weight slice is charged against what `F` leaves. The regcmd encoder programs
`4096+F` granules for the feature side, whatever the plane's actual height. Every granule of
`F` is therefore a granule the weight path does not get. At `F=0` the weight path has 3072
granules, and at `F` it has `3072-F`. The usable part falls granule for granule with `F`, and
the group-cap table in [rk3576-regcmd.md](rk3576-regcmd.md) §"Output-channel tiling under the
group cap" was measured at `F=0`.

The second mechanism at `k7ic64-g2` height 37 is the resident weight slice overrunning the CBUF
pool once `F` grows. It is not an `F=1024` value the hardware fails to honor. The slice cap
already models a graded output-channel-group loss. That loss is the same bound, met from the
other end of one shared budget.

**Conditions:** H96 MAX M9, one task per test point, measured 2026-08-05 on a `rocket` before
1.6.0. The plane is held well inside the `F=0` budget, so an unhonored `F` value cannot matter.

| shape | groups | slice | `F` | usable | Result |
|---|---|---|---|---|---|
| `112x112 k7 ic 64 oc 64` | 2 | 98 KiB | 0 | 156 KiB | exact |
| | | | 1024 | **92 KiB** | wrong, `chans 32-63`, 1 of 2 groups |
| | | | 2048 | 28 KiB | **no `PC_DONE` at all** |
| `112x112 k7 ic 32 oc 128` | 4 | 49 KiB | 0 | 144 KiB | exact |
| | | | 1024 | 80 KiB | exact |
| | | | 2048 | **16 KiB** | wrong, `chans 32-127`, 3 of 4 groups |

Both wrong test points pass the pool check (6688 and 6928 granules against 7168). They are wrong
at every row of the groups they lose, the slice cap's signature. An unhonored `F` value instead
gives a full output with a wrong row tail past `4096/entries`.

On `rocket` 1.6.0 the same two test points write nothing. Each job raises no completion and
retires at the driver's 125 ms backstop [HW sweep, H96 MAX M9, 594 MHz, 2026-10-12].

> [!CAUTION]
> A resident weight slice larger than what `F` leaves the weight path loses whole trailing
> output-channel groups, at every row, and raises no error. On `rocket` 1.6.0 the job instead
> writes nothing and retires at the 125 ms backstop. The pool check, feature plus weights
> within 7168 granules, does not catch it. Software must size the weight slice against the
> budget left at the programmed `F`, which falls granule for granule as `F` grows.

A feature allowance larger than the plane is valid at `F=1024`. Forced beside a 16-granule
slice, it gives an exact result over 1, 2 and 3 output-channel groups [HW sweep]. The two low
values are not always valid. Forced on the four-group shape at plane height 20, `F=256` and
`F=512` each write output row 0 wrong. At height 30 both are exact [HW sweep, H96 MAX M9,
`rocket` 1.6.0, 2026-10-12]. The planner never programs a value above the
smallest that covers the window, so it does not select either there.

> [!CAUTION]
> Past the pool, the program does not execute. At `F=2048` the two-group shape above raises no
> `PC_DONE`, and the job never completes. Software must keep the feature allowance and the weight
> slice together within the 7168-granule pool.

The governing quantity is the slice against what `F` leaves, not the `F` value. The pool check
therefore catches the non-executing case, and the slice bound lies inside it.

Software support: the library entry returns `-4` there, after its output guard runs eight power
cycles.

#### Slope and reserve

The usable weight slice falls 1:1 with `F`, granule for granule, less a fixed reserve set by
the output-channel group count. The weight path holds `3072-F` granules. The reserve is 512,
688 and 768 granules at two, three and four groups, identical at both allowances. Each
boundary is deterministic [HW sweep]. The table gives the last exact slice:

**Conditions:** a 4×2 plane, where nothing drains, at `k=1`, so the slice is `32*ic` and
moves in 1 KiB steps. `F` is forced, one task per test point.

| groups (`oc`) | `F=1024` | `F=2048` | the weight path holds | usable = hold - reserve |
|---|---|---|---|---|
| 2 (64) | **96 KiB** (1536 gran) | **32 KiB** (512 gran) | 2048 / 1024 granules | reserve **512** granules |
| 3 (96) | **85 KiB** (1360 gran) | **21 KiB** (336 gran) | | reserve **688** |
| 4 (128) | **80 KiB** (1280 gran) | **16 KiB** (256 gran) | | reserve **768** |

Extrapolated to `F=0`, the reserves put the intercepts at or above the values of the `F=0`
cap table:

| groups | intercept from the reserve | cap table | over-charge |
|---:|---:|---:|---:|
| 2 | 160 KiB | 156 KiB | 4 KiB |
| 3 | 149 KiB | 148 KiB | 1 KiB |
| 4 | 144 KiB | 144 KiB | 0 KiB |

`librocketnpu`'s cap table takes the last exact sample of a sweep over six slices (144, 145,
148, 152, 156 and 162 KiB), not the boundary. Its caps therefore over-charge and never
under-charge, at six directly measured test points. They are not raised to the implied
intercepts, because `F=0` is the one point the slice sweep cannot reach. A cap set too high
produces wrong output, and one set too low only refuses. Above 156 KiB the output-channel
tile splits a convolution, so no convolution runs as two groups there.

`librocketnpu` charges the slice in both places that read the cap. The plan refuses, and
`rocket_rk3576_max_task_rows()` skips an allowance whose F-aware cap does not cover the slice.
For `112x112 k7 ic 64 oc 64` the function returns 36 input rows, and heights 37-45 are
refused. Without that second check it returns 45, which is `F=1024`'s window and the whole
failing band. Every task the row planner cut there would be a full output with its trailing
group wrong.

No tested network reaches this bound: the five network tests keep their structure across the
change. Under the drain deadline, the bound also lies inside the deadline's own failure
region. Reaching the bound needs a slice near the cap and a plane large enough to need an
allowance above `F=0`. A 92 KiB slice is `ic*kh*kw >= 2944`, and a layer with that much `ic`
tends to have a plane small enough to fit at `F=0`. The two requirements therefore appear
anti-correlated [hypothesis], and the networks were not enumerated layer by layer.

#### Slices at a multiple of 32 KiB

A slice that is an exact multiple of 512 granules (32 KiB) is exact far above the cap
[HW sweep]. At `F=1024`, both 96 KiB and 128 KiB are exact at all three group counts, while
every neighboring KiB is wrong. At `F=2048`, so are 64 KiB (2 groups) and 32 KiB (3 groups).
A multiple of 16 KiB that is not a multiple of 32 KiB, such as 112 KiB, is wrong [HW sweep].

The slice bound therefore has an alignment term. The likely mechanism is that the weight
path stages the slice in 32 KiB units, and a partial trailing unit costs the trailing
output-channel group [hypothesis]. `librocketnpu` does not model the alignment term, because
modeling it can only make the library accept more.

The escape and the graded group loss depend on the slice's byte count alone [HW sweep, H96
MAX M9]. At `F=1024` and `oc=128`, where the cap is 80 KiB, the slices from 81 to 95 KiB lose
one and then two trailing output-channel groups. The slices from 97 to 127 KiB lose three,
and 96 and 128 KiB are exact. Neither `k=2`, where 96 KiB is `ic` 768, nor a 4×19 plane
changes that. The 4×19 plane consumes 3040-4864 granules of the forced 5120 allowance,
against 160-256 for the 4×2 plane.

**Not characterized:** the invariance at other group counts and allowances (the walks hold
`oc=128` and `F=1024`), and `k=4`, the only other kernel that reaches the lattice below the
pool.

The plane moves the boundary between wrong output and non-execution. On the 4×2 plane every
over-cap slice up to 128 KiB completes, and is wrong except at the 32 KiB multiples. On the
4×19 plane the entry returns `-4` with no completion at all from 108 to 127 KiB, and 128 KiB
runs and is exact. The non-execution limit is a function of the plane and the slice
together. The graded loss and the escape are functions of the slice alone.

The slice is `32*ic*k*k`, and the direct path requires `ic` to be a multiple of 32. The
reachable slices are therefore exactly the multiples of `k*k` KiB. A 32 KiB multiple therefore
needs `k` in {1, 2, 4}. With `k=3` the first one is 288 KiB, and with `k=5` it is 800 KiB. Both
are far past the 128 KiB the pool leaves at `F=1024`.

#### The drain deadline and the row planner

With `dpu_grace_us` a 750 us deadline, the library's row planner agrees with the RK3576 on all 23
geometries tested. They include `56x56 k7 ic 64 oc 64`, the one geometry where the planner's
bound is deliberately left above the measured one. That geometry is exact to 58 rows at 500 and to the
planner's own 91 at 750. At 500 it is the only disagreement, and the deadline is its cause.

The row planner windows a task to fit the CBUF allowance. On the shapes real models have,
that window keeps every task's drain under 500 us. No layer of the five classifiers, the two
detectors or the per-axis ResNet-18 reaches the deadline. Only the probe setting
`ROCKET_RK3576_ROW_CAP_PROBE` emits windows past it. A caller with a wider plane or a deeper
output-channel count reaches it.

A task past the drain deadline loses the tail of its output, RK3576-E3, whose Caution and
module-version scope are under [The direct path's drain
deadline](rk3576-hazards.md#the-direct-paths-drain-deadline). On the row planner's path the
failure edge moves 1-4 rows between runs. Read as a capacity bound, the edge looks like a CBUF
ceiling that falls with the group count, and it is not one. The deadline applies to a kick of
one task and to the last program of any kick.

> [!NOTE]
> The deadline's edge is a failure rate, not a fixed height. Below the height where every
> run fails lies a band where only some runs fail, so a single bisection reports one run's
> edge. Measure each height over repeated runs.

The edge likely moves with the host's timing [hypothesis]. A 50 us poll tick falls at a
varying point relative to `PC_DONE`, and the hrtimer callback runs late under load. Each
moves the start of the grace window by a poll period on a 500 us budget. The NPU clock holds
one rate for a whole boot, 786 MHz for these runs, and does not park. The NPU has no devfreq
node (only the GPU has one), so nothing on the NPU's side of the timing varies.

Patch 0022 of the series makes a job's wait depend on the hardware's own account of the
kick, not on a deadline. It does so only for a kick of more than one task.

A job of one task programs `TASK_NUMBER = 1`, where both `PC_TASK_STATUS` counters always read
zero. `PC_DONE` alone signals it, and the grace bounds the drain after it. The same is true of
the last program of any kick. On that path under `rocket` 1.5.0, `dpu_grace_us` is a fitted
value. Raising it works around the hazard without removing it, because a program's drain time
does not depend on the driver's timing. On `rocket` 1.6.0 at its default `dpu_grace_us` = 0,
the driver waits for the writing block instead.

#### The deadline under the write guard

A task far enough past the drain deadline writes nothing the write guard can see. The
library's whole-output write guard cannot tell that from a submit corrupted by an earlier
wide output, because both leave the output empty. It runs eight power cycles on each before
the entry returns `ROCKET_E_DEVICE` and the caller falls back to the host.

> [!NOTE]
> A failure at the same row task on every run comes from the plan or the drain deadline,
> not from the next-submit corruption hazard.

Closer to the deadline, the output passes the guard and is wrong. No wrong element is zero.
Where wrong elements were checked against the sentinel ([rk3576-hazards.md](rk3576-hazards.md)
§"Extent of the loss"), each still held it. Both outcomes are the same mechanism at different
distances past the same fence.

#### Output-channel group loss at a large weight slice

The output-channel group loss at a large weight slice is a bound separate from the drain
deadline. It depends on the slice against the budget `F` leaves, not on the window's drain.
The cap `r76_weight_slice_cap()` is measured on a 4×2 plane, where the drain is nowhere near
the grace. At four output-channel groups, a resident slice of 144 KiB leaves every group
exact, 145 KiB loses one, 152 KiB loses two, and 162 KiB leaves one. The cap table holds at
`F=0`.

A slice far inside the cap still loses trailing groups once a large window's `F` leaves the
weight path less than the slice. A 49 KiB slice at four groups is exact at `F=1024`, and loses
three groups at `F=2048`, where 16 KiB is usable. The loss is the same bound, met from the
other end of one shared budget ("The weight slice and the feature allowance").

#### CBUF allowances on the depthwise path

On the depthwise path, `F=256` and `F=512` deliver only the `F=0` budget for a kernel with
more than one tap [HW sweep, H96 MAX M9]. `F` takes one of five measured values, and the
planner programs the smallest whose `4096+F` granules cover the task's window. An allowance
the RK3576 does not honor delivers the `F=0` budget instead.

> [!CAUTION]
> On the depthwise path, a multi-tap task that selects `F=256` or `F=512` gets the `F=0`
> budget, and nothing faults. The output is exact below that budget's reach, wrong across the
> band of windows that select those two values, and exact again above. The failure is not
> monotone in the window height, so a bisection over the window reports whichever edge it
> walks into. Software must program `F=1024` or `F=2048` for a depthwise window past 4096
> granules.

**Conditions:** 160×160, ic = oc = 32, k3 depthwise, 80 granules a row, one task per height,
`F` chosen by the planner.

| plane rows | granules needed | planner F | output |
|---:|---:|---:|---|
| 45-51 | 3600-4080 | 0 | exact |
| **52-54** | **4160-4320** | **256** | **wrong** |
| **55-57** | **4400-4560** | **512** | **wrong** |
| 58-64 | 4640-5120 | 1024 | exact |
| 65-76 | 5200-6080 | 2048 | exact |

On the direct path, the same plane, the same channels and the same entries per row are exact
at every height from 49 through 60. In the band, the wrong elements are exactly the output
rows past `4096/entries`. At a 52-row plane that is one row: the F=0 budget's 51 rows staged
under a programmed 4352.

The tap count, not the weight footprint, decides whether a low allowance delivers. The table
holds one window that F=0 does not cover, and forces each allowance beneath it:

| path | kernel | oc | resident footprint | F=256 / F=512 |
|---|---|---:|---|---|
| direct | 1×1 | 32 | 1024 B = 16 granules | deliver |
| direct | 1×1 | 64 | 2048 B = 32 granules | fall back to 4096 |
| depthwise | 1×1 | 32 | 64 B = 1 granule | deliver |
| depthwise | 1×1 | 256 | 512 B = 8 granules | deliver |
| depthwise | 1×1 | 1024 | 2048 B = 32 granules | deliver |
| depthwise | 2×2 | 32 | 256 B = 4 granules | fall back to 4096 |
| depthwise | 3×3 | 32 | 576 B = 9 granules | fall back to 4096 |
| depthwise | 5×5 | 32 | 1600 B = 25 granules | fall back to 4096 |

Every single-tap depthwise test point delivers, at three channel counts spanning 32x, and
every multi-tap one falls back. On the direct path the low allowances follow a 16-granule
footprint threshold, which fits k1, k3 and k5. F=1024 and F=2048 deliver at every footprint
tried on both paths.

`librocketnpu` declines the two low allowances on the depthwise path outright, rather than
gating them on a fitted quantity. The refusal costs nothing measurable. The next allowance up
is strictly larger, always delivers, and needs no extra submit. Every window and task count
in the ten depthwise row-bound test points is unchanged, and only the emitted F moves.

Two real layers select a low allowance. They are EfficientDet-Lite0's `blocks_0` (160×160,
k3 s1, three windows of 55, 56 and 53 rows, all selecting F=512) and the same shape at stride
two. The `dw-k5-s1-160` test point needs 4640 granules, which selects the next allowance up. It
is exact *because* it asks for more [HW sweep, H96 MAX M9].

> [!NOTE]
> A per-operation test is exact only at the shapes it drives. Six per-operation test points
> measured this datapath at zero counts of distance from an exact per-axis requant. The
> model's own layer was wrong on 28 of its 32 live channels, because no test point used the
> model's plane.

### Quantization

The RK3576 vendor path uses per-output-channel weight scales, and Mesa's single global scale
saturates most channels [source-confirmed]. The per-channel requant is the same as on the
RK3588. A task has one `OUT_CVT` scale and shift, and each output channel's scale is on the BS
stage's per-channel multiplier `C`. See
[../encodings/out-cvt-converter.md](../encodings/out-cvt-converter.md).

### The matmul entry's requant and per-column ramp

The DPU's integer requant on the matmul path is the convolution path's function. It computes
`sat8(round_half_to_even((acc + bias) * MUL >> shift))`, with `MUL` and `shift` from the
emitter's QNNPACK derivation. The device matches that host model exactly and leaves no element
unwritten. The match covers five shapes from `32x256x64` to `512x2048x1024` and four distinct
`(MUL, SHIFT)` pairs. Each shape runs at a scale that fills the int8 range. It also runs at one
4x larger, which clips a quarter to a third of the output.

The BS stage's per-channel multiplier `C`, held in the coefficient group, applies a
per-output-column scale on the matmul path. With the BS shift word at zero, the epilogue is
`(acc + bias[n]) * C[n]` in saturating int32, then one shared `(v*MUL)>>SHIFT` per task, as on
the convolution path. The device matches it exactly at six shapes, each at two column-scale
spreads, with the shift word at zero. The set of `C` values across a tile's columns is the ramp.

At GEMM depths, the int32 product limits the ramp, not `C`'s int16 field. With the BS shift word
at zero, each column's `C` is capped at `INT32_MAX / (128*sum_k|B[n][k]|)`. The operands set
that cap, not the shape alone, so software must compute it from the operands. With a nonzero
shift, the BS stage holds the product wide and rounds it after the multiply. The wide product is
exact to 2^45.95 on both signs [HW sweep, 2026-09-23 and 2026-09-27]. The shift word is in
[rk3576-regcmd.md](rk3576-regcmd.md).

`rocket_matmul_int8_rk3576_perc()` is the per-column entry. It uses the convolution path's
per-axis planner, not a copy, and plans one `(MUL, SHIFT)` per N tile. The entry places its gain
on the shift word. The planner sets each tile's largest scale near C = 32767, with the smallest
shift that keeps every column inside int32 on both signs.

The matmul's int8 weight cube groups output columns by 32. Column `n`'s 32-byte run for K group
`k1` sits at `(n/32)*nK1*1024 + k1*1024 + (n%32)*32`, with `nK1` = ⌈K/32⌉. With an N tile width
that is a multiple of 32, the whole-`N` cube is the per-tile cubes concatenated byte for byte.
One weight buffer therefore serves every N tile at every `M` [HW sweep 2026-08-19]. Software
selects a tile by offsetting `weights_dma` by `(n0/32)*nK1*1024`, where `n0` is the tile's first
column.

The shift ramp matches an independent host model exactly on the device [HW sweep, H96 MAX M9,
rocket 1.6.0, 2026-09-27]. On Qwen2.5-1.5B's and SmolLM2-1.7B's own projections, with rotated
operands, its median column gain error is 0.0013-0.0035% [HW sweep]. Setting
`ROCKET_RK3576_MM_PC_SHIFT=0` selects the shift-0 ramp, whose median there is 0.10-0.33%.

#### Shift-0 ramp accuracy

The figures in this subsection describe the shift-0 ramp. Its worst-case relative gain error is
roughly `0.5 * spread / C_max`, and grows linearly in both the contraction depth and the spread
of the column scales.

A weight drawn from a full-range generator is the pessimistic case, and a real model's `C_max`
is an order of magnitude larger. With full-range B, `sum_k|B[n][k]|` ~ 64*K, so `C_max` ~
`262144/K` = 128 at K=2048. In a real per-channel quantized weight row, a few outlier weights set
the channel's scale, so most weights are small integers. Such a row has mean `|Bq|` near 5.5,
and the same K=2048 projection gets a `C_max` of 424 to 1496.
[host-computed, arithmetic over the library's planner, two models, 2026-08-10]

A Hadamard rotation along K lowers `C_max`, because it raises `sum|Bq|` by spreading each row's
mass. Over SmolLM2-1.7B's 144 offloadable projections, the rotation takes the median `C_max` from
1496 unrotated to 424, and so costs 3.5x of the ramp's resolution. The rotation and the ramp,
which a port combines, therefore interact. The same models' within-tile column-scale spread is
7.6-9.5x median (range 3.5-160.9). The resulting `worst_rel_err` is 0.69-0.89% median and
3.4-7.3% max, against the full-range table's 3.0%.
[host-computed, arithmetic over the library's planner, two models, 2026-08-10]

Qwen2.5-1.5B's 168 projections agree on every input and reproduce the rotation's cost. Their
spread is 10.1x unrotated and 6.3x rotated, their `C_max` median goes 1848 -> 555 (3.3x), and
their `worst_rel_err` median is 0.45-0.56%.
[host-computed, arithmetic over the library's planner, two models, 2026-08-10]

With B drawn full-range, the worst-case relative gain error is:

| K | flat columns | 8x column spread |
|---:|---:|---:|
| 256 | 0.042% | 0.341% |
| 512 | 0.080% | 0.611% |
| 1024 | 0.162% | 1.533% |
| 2048 | 0.220% | 2.96-3.01% |

Against an exact per-column scale, the shift-0 ramp moves 2.2% of elements by 1 LSB at K=2048
with flat columns. At K=2048 with an 8x spread it moves 12.7%, a few of them by 2. The 1.004x
and 1.002x perplexity ratios were simulated with an exact per-column scale. They are therefore
the per-column path's best case, so 1.004x is not this entry's figure.

The shift-0 ramp's end-to-end cost to a model is small. Modeled in place of an exact per-column
scale, over 8 windows of 512 wikitext-2 tokens and SmolLM2-1.7B's 144 offloadable projections,
it gives these perplexity ratios:

| Configuration | Exact per-column scale | Shift-0 integer ramp |
|---|---:|---:|
| Per-column output requant alone, SmolLM2 | 1.543x | **1.505x** |
| Per-column output requant alone, Qwen2.5 | 1.061x | **1.080x** |
| Hadamard + per-column requant, SmolLM2 | 1.004x (97.29% top-1) | **1.008x (96.14%)** |
| Hadamard + per-column requant, Qwen2.5 | 1.002x (96.85%) | **1.0025x (96.63%)** |

With the Hadamard rotation, the ramp costs 0.4% of ratio on SmolLM2-1.7B and 0.06% on
Qwen2.5-1.5B. The two models differ eightfold, and both costs are negligible. Both are two orders
of magnitude below the cost of the per-tensor output scale the ramp replaces (1.11-2.26x).
Without the rotation the models disagree: 1.543x against 1.061x for the same exact-scale
configuration.
[host-computed, arithmetic, 8 windows x 512 wikitext-2 tokens, 2026-08-10]

Eight windows understate SmolLM2-1.7B's ramp cost 2.8x. Over 32 windows its rotated
configuration measures 1.0165 through the shift-0 ramp and 1.0055 through the shift-word ramp.
The exact scale measures 1.0048 [host-computed, arithmetic, 32 windows x 512 wikitext-2 tokens,
2026-09-27].

Qwen2.5-1.5B's configurations fall in one noise band over 32 windows, and a 4-chunk device
perplexity does not resolve them either. Its two ramps differ by 0.012-0.095 PPL [HW sweep, H96
MAX M9, the W8A8 path, 2026-09-27]. The sign of the difference flips under a perturbation that
contains no information: the N tile, or a 0.1% scale change.

#### Stability without the rotation

A model's unrotated int8 path can be numerically unstable, and SmolLM2-1.7B's is. An arbitrary
+-0.5% per-column divisor jitter that contains no information, in layer 0 alone, takes its
perplexity to 2.3e10. The same jitter over layers 0-1 gives 10.33.
[host-computed, arithmetic, 2026-08-10]

Under the identical perturbations, the Hadamard-rotated path stays between 8.24 and 8.35 over
four configurations, including the achieved divisor everywhere. The rotation therefore gives
stability as well as accuracy. The SmolLM2 figures for the unrotated path are samples from an
unstable regime rather than measurements of an optimization.
[host-computed, arithmetic, 2026-08-10]

Dequantizing by the gain the shift-0 ramp achieves, `C[n] * MUL/2^SHIFT`, instead of by the
requested scale makes no consistent difference. The achieved gain is at most 2% from the
requested scale. On Qwen2.5-1.5B the two measure 1.0828 against 1.0800 unrotated, and 0.9989
against 1.0025 rotated.
[host-computed, arithmetic, 2026-08-10]

#### Resolution limits

Two changes would raise the shift-0 ramp's resolution, and `librocketnpu` implements neither.
Both limits were measured on the shift-0 ramp.

The first is the N tile, which sets the ramp's resolution as well as throughput. Forcing eight
tiles at K=1024 took an 8x-spread test point from 1.53% to 0.265%, because each tile then spans
only `8^(1/8)` = 1.30x. That test point's column scales are monotone in the column index, so
consecutive tiles are narrow bands by construction. A real model's unsorted scales are not
expected to show that effect [expected]. The convolution path sorts channels by scale
(`r76_sort_by_scale`) and passes a permutation, where the matmul entry passes NULL.
[HW sweep, H96 MAX M9, `rocket` 1.6.0, 2026-08-10]

The second is the accumulator bound itself. The bound `128*sum|w|` is the int8 worst case, and a
real GEMM's accumulator is ~90x below it at K=2048. The gap gives away about six bits of `C`
resolution. A tighter bound must be statistical.
[HW sweep, H96 MAX M9, `rocket` 1.6.0, 2026-08-10]

A product past such a bound saturates at int32 and does not wrap, with the shift word at zero
[HW sweep]. [rk3576-regcmd.md](rk3576-regcmd.md) gives the measurement.

### The DPU LUT and its input map

The DPU's LUT is part of the EW stage: `EW_LUT_BYPASS` is bit 7 of `0x407C`, the RK3588's field
layout at a moved offset. A nonlinear activation takes two programs. The first is a DPU-only
program that loads two 513-entry tables through an auto-incrementing window. The second is an
ordinary convolution with the LUT enabled: the direct int8 convolution plus a short register
set. `gen_lut_load_rk3576()` emits the table-load program.

> [!CAUTION]
> A runtime-PM cycle between two submits can lose the tables, so software must put the table
> load and its use in one job ([rk3576-regcmd.md](rk3576-regcmd.md) §"Table load program").

The input map is `index = (value - LE_START) / 2^sel`, with the `0x00020000` table covering
`[LE_START, 0]` and the `0x00030000` table `[0, LO_END)`, at 512 intervals each. All three
parameters are live and programmable [HW sweep, H96 MAX M9]:

| Offset | Parameter |
|---|---|
| `0x410C` | The index step |
| `0x4110`-`0x411C` | `LE_START`, four lanes |
| `0x4140`-`0x414C` | `LO_END` |

The hardware interpolates linearly between entries at the full resolution of the step. The
domain is half-open at the top: `value == LO_END` takes the overflow clamp. A CPU model of the
map reproduces the output to at most one output count. [HW sweep, H96 MAX M9]

The value the LUT sees is the BS stage's output, `(acc + A[oc]) * C[oc]`. Software therefore
places each output channel's range inside the window with the same per-channel `C` that a
per-axis quantization already uses. The vendor programs place it this way, and never move the
window. At fp16 the coefficient buffer contains that scale, not a register. Sigmoid and tanh
therefore emit register-identical programs at fp16, with tables spanning 6.25 and 3.02 input
units.

> [!CAUTION]
> The vendor activation programs' `BN_CFG` value, `0x20`, pins the LUT at the table boundary for
> every input. Software must program `BN_CFG` `0x4060` to `0x903` in a LUT program
> ([rk3576-regcmd.md](rk3576-regcmd.md) §"Input map").

#### The int8 activation op

The entry point over that map is `rocket_act_int8_rk3576()`. It computes sigmoid, tanh, swish,
hardswish, hardsigmoid and elu over a row-major `[C][H][W]` int8 tensor, with a per-tensor
quantization on both sides. The op omits `exp`, `gelu` and `sqrt`. No vendor capture emits a
513-entry table for any of the three, so the vendor lowers them some other way. A table for
them would be an invention.

The op is exact for every int8 input. It lowers onto a depthwise 1×1 identity convolution whose
weight is the LUT's own index step, `2^sel`. That weight puts input value `q` at table index
`q - in_zp + 512` exactly. Each of the 256 possible inputs therefore reads its own entry, and the
hardware's interpolation never runs. An identity weight of 1 would have put all 256 inputs inside
eight index intervals.

The per-output-channel `C` can apply the same scaling, and this op does not need it. The
coefficient `A` fold already contains `-in_zp*sum_w`, so the input zero point comes out right with
no special case. `C` stays free for a fused conv->activation, where the accumulator range differs
per channel.

The identity must be depthwise. A 1×1 direct identity needs an `oc x ic` weight matrix, which
is quadratic in the channel count. At any real width that matrix is past the emitter's
`ic*kh*kw <= 4608` weight slice rule. Depthwise binds output channel `c` to input channel `c`.
The identity is then one weight per channel, and the layer is one task at any width.

The table has two scales. A datapath value `v` means the real number `in_scale * v / 2^sel`.
An entry is read in units of `out_scale * gain`, where `gain` is the OUT_CVT pair that the
emitter programs. The op reads that pair back from `rocket_rk3576_requant_params()` rather than
re-deriving it.

> [!CAUTION]
> A table built against a gain slightly different from the programmed OUT_CVT pair is off at
> every entry, and nothing reports it. Software must build the table from the OUT_CVT pair the
> emitter programs.

The op holds the conv scale at 1/128. The 1/128 scale is the finest gain whose int16 entry
still spans the whole int8 output range a zero point can ask for (128 * 255 = 32640).

The two programs go out as one job, a multi-descriptor job. The conv driver has three submit
layouts: one submit per row task, one chained kick, and this one. The chain rewrite links
programs inside one BO, and the table load is in a separate one. A LUT call therefore declines
chaining and says so. Declining costs the single-kick saving and does not affect correctness.

Over six kinds, five quantizations and six shapes, dense over all 256 byte values, every output
is bit-exact against a CPU model of the RK3576's arithmetic. No output is more than one count from
an exact `f()`. [HW sweep, H96 MAX M9]

#### The activation fused into a convolution epilogue

The LUT sits in the EW stage of a convolution's own program, so an activation fuses into a
convolution's epilogue with no added convolution. `rocket_conv2d_int8_act_rk3576()` therefore
adds only the table-load task, and the activation is otherwise free.

The fused form is different arithmetic from conv-then-activation, and the better one. The
standalone op reads the convolution's requantized int8 output, an alphabet of 256 values, and
the fused form reads the accumulator before any rounding. The fused form gives up exactness. A
real accumulator falls between entries, so the hardware's linear interpolation runs.

Over 28 cases (six kinds, direct and depthwise, three quantizations), the fused form is at most
one count from an exact `f()`. The cases put the pre-activation inside the curved region rather
than on a saturating tail. [HW sweep, H96 MAX M9]

The conv entries' contract needs no change, even though the standalone op pins its scale at
1/128. Three quantities follow from the three scales a caller already passes:

- **The value unit.** With a per-tensor requant, the BS multiplier `C` is unity. The value the
  LUT sees is then the accumulator itself, `A` included, and `A` already contains the bias and
  the zero-point fold. One count of it means `in_scale*w_scale`.
- **The entry unit.** OUT_CVT scales the table's output by the gain the emitter derives from
  `in_scale*w_scale/out_scale`, so an entry is read in units of `out_scale*gain`. The
  standalone op must pin its conv scale to make that well defined. A real conv has the model's
  own three.
- **The step.** The window is the symmetric `[-512*2^sel, 512*2^sel)`, so `sel` is the smallest
  whose real half-span covers the domain the activation still varies over. Past it, the LUT
  returns its endpoint clamp, which is the right answer for a saturating kind. For a kind that
  keeps growing, the bound is where the int8 output saturates instead, since `f(x)` is `x` by
  then.

The entry refuses two bounds rather than computing them wrong, and both refusals name
`in_scale*w_scale` as the quantity to change. The first is a value unit too fine for the
table's peak to fit an int16. An unbounded kind over a fine unit reaches it. Swish and elu at
`in_scale*w_scale = 1.6e-4` need 49151 entries, and the table saturates at 32767, which would
give a flat-topped curve. The second is a domain that no `sel` reaches.

The entry leaves per-output-channel `C` unused. It divides the value unit per channel, which is
how a fused conv whose channels have very different accumulator ranges puts each inside
`[LE_START, LO_END)`. The product `(acc + A)*C` saturates at int32, a bound to plan inside. The
per-tensor form above needs none of it.

Two checks of a working LUT read as hardware faults:

> [!NOTE]
> A liveness check against the same conv without the LUT must allow a rounding. A one-count
> difference between the two outputs is the requant's tie-to-even against a reference that
> rounds half away from zero, not the activation.

> [!NOTE]
> ELU under an output quantization with no negative range is the identity clamped at zero, which
> the DPU's int8 saturation already computes. On that quantization the fused and plain outputs
> are legitimately identical, so a differs-from-plain assertion fires on a working LUT.

### The residual add on the convolution datapath

On the RK3576, a residual add runs on the convolution datapath rather than on the DPU's
elementwise stage. The skip connection is the one primitive a second network needs beyond the
operations MobileNetV1 uses. MobileNetV2 puts one on ten of its seventeen inverted residuals,
and every ResNet block ends in one. MobileNetV1 is a straight chain and has none.

The DPU's elementwise stage computes an affine requantization of exactly one cube. Eight sweeps
over the whole register interface find no second operand for it [HW sweep], and
[rk3576-regcmd.md](rk3576-regcmd.md) sets them out.

Software lowers the add onto a convolution. It concatenates the two operands along the
channel axis, and convolves them with a 1×1 kernel of two diagonal blocks (`W[o][o] = w1`,
`W[o][C+o] = w2`, zero elsewhere):

```
out[o] = requant( w1 * (a[o] - a_zp) + w2 * (b[o] - b_zp) )
```

The lowering is bit-exact against a CPU model of the RK3576's arithmetic, over nine
MobileNetV2 and ResNet-18 residual shapes [HW sweep, H96 MAX M9]. The shapes span channels 24
to 512 and planes 7×7 to 56×56. At every shape the result is within one count of an exact
float residual add, with unequal operand scales and with unequal zero points.

The lowering improves on the vendor's elementwise program in two respects:

- **Different operand scales.** The weights contain the scale ratio as `w2/w1`, so the pair
  only has to be representable as two int8s. `librocketnpu` takes the closest such ratio over
  every pair of weights in [1, 127]. The vendor's program has
  one operand converter, and its compiler works around that by quantizing both operands to a
  common scale. Two graph inputs calibrated 64x apart still compile to a single converter.
  Its OUT_CVT gain is then the ratio of one shared input scale to the output's.
- **Exact zero points.** The datapath has one input zero point, but `w2 * (a_zp - b_zp)` is a
  per-output-channel constant, which the bias holds. Nothing is approximated.

#### Fusion into a block's last convolution

The add can also be fused into a block's last convolution. The fused form is bit-exact on the
RK3576 [HW sweep, H96 MAX M9, 2026-07-31]. A real block's quantization, however, needs an
identity weight that int8 cannot hold, so a real network uses the standalone add.

The concatenation is along channels. A feature cube's channel-group stride is the plane, and
a direct convolution's output surface stride is `ow*oh`. Two convolutions writing adjacent
halves of one buffer therefore already form the concatenated operand, byte for byte, with no
host work. The cube chain rests on the same identity. A block's last convolution absorbs its
own skip with `C` more input channels and an identity block at its kernel's center tap. The
add then costs no program at all, where the vendor's costs one.

The vendor compiler folds `Add(Conv(x), x)` into exactly this shape, so a capture of that
graph shows no add. The fused form is bit-exact at MobileNetV2's project convolution for every
residual width (1×1, `ic` 168 to 1120). It is also bit-exact at ResNet-18's second
convolution (3×3, `ic` 128 to 512) [HW sweep, H96 MAX M9, 2026-07-31].

The identity weight limits the fusion before the weight-slice rule does. The slice rule is
`ic*kh*kw <= 4608`. A 3×3 reaches it exactly at `C = 256` (`512*9 = 4608`) and is refused at
`C = 512`. A real block's own quantization refuses the fusion long before that.

A standalone add chooses its own weight scale, because its weights are two diagonal blocks
rather than a quantized tensor. There `w_scale = 1/w1` is a free parameter, which is how the
operand ratio fits in a pair of int8s. A fused add inherits the convolution's weight scale,
which the convolution's own filter fixes. The skip therefore has to reach the output through
the accumulator unit the main term already uses:

    w_skip = skip_scale / (in_scale * w_scale) = (skip_scale / out_scale) / gain

Here `gain` is the convolution's requant gain. A residual's two operands have comparable
ranges, so `skip_scale/out_scale` is of order one (0.64 to 0.98 on MobileNetV2). The fusion
therefore needs `gain > ~1/127`, a shallow contraction. A project convolution over 576 to 960
channels runs at 1/242 to 1/893. All ten of MobileNetV2's residual blocks need an identity
weight of 173 to 865, and none fits int8.

Nothing else in the program can move that weight. The coefficient group's `C` multiplies the
whole accumulator, main term and skip together, so a per-channel gain cannot separate them. A
per-axis quantization makes it strictly worse, because the per-tensor `w_scale` is the largest
of the per-channel ones.

Software support: `rocket_residual_fuse_weight_rk3576()` computes that weight and refuses a
block whose weight does not fit, and it is a pure function. Where the weight fits, it also
computes the bias correction `w_skip*(in_zp - skip_zp)`. A block within those limits is within
one count of an exact float main+skip on the RK3576 [HW sweep, H96 MAX M9, 2026-07-31].

The standalone add is therefore the form a real network uses. The same slice rule caps it at
`C = 2304`, well past any real residual width. Its weight cube is `2C*C` bytes, 512 KiB at
ResNet-18's widest stage, a resident-weights cost incurred once rather than per inference.
With transient weights (no resident handle, so mostly host packing), a standalone add takes
0.6-3.3 ms across the tested residual shapes [HW sweep, H96 MAX M9, 2026-07-31].

### The fp16 matmul program

The RK3576 contracts an fp16 matmul's whole K in one task with a matmul-form program. The
program is the charsiu project's fp16 matmul, emitted by its own `charsiu_emit_job` at
`524e10a`. One job contracts K 32, 64, 256, 1024 and 2048 exactly, at N 64 and M 1, and at K 256
with M 4. Its fp32 output matches an fp16-rounded CPU reference bit for bit [HW sweep, H96 MAX
M9, 7.2.3-1, `rocket` 1.6.0, 2026-09-24].

The program differs from `librocketnpu`'s fp16 convolution program in its input layout and its
output stage:

- It reads the activation row major, `[m][k]`, and sets CNA `0x1090` to `ic/8` for that layout.
- It sets bit 29 of CNA `0x100C`, which reads `0x20200120` in full.
- Its output stage is the w4a16 one: CORE `0x3018` at `0x10000200`, and three DPU words
  (`0x4028`, `0x4030`, `0x40b8`) in closed forms of the channels and rows.
- The output is a flat `m` by `n` fp32 tensor, and the weight buffer is 16 output channels by 32
  input channels of two-byte elements.

The program's fp32 output does not corrupt a following submit of its own kind [HW sweep, H96 MAX
M9, 2026-09-24]. Nor does it corrupt `librocketnpu`'s int8 direct program at a zero gap [HW
sweep, H96 MAX M9, 2026-09-25]. [rk3576-hazards.md](rk3576-hazards.md) §"The wide-output hazard"
has the detail.

#### Accumulation order

The matmul-form program sums each group of 32 products along K without rounding, then
accumulates the groups in fp32. Each group sum is rounded to fp32, and the group sums are added
in K order, both roundings to nearest even. The group is the weight cube's 32 input channels.
The model matches every output bit for bit at M 4, N 64 and K from 32 to 2048. The fills have
full fp16 mantissas, with products spread over 2^-28 to 2^-6 [HW sweep, H96 MAX M9, `rocket`
1.6.0, 2026-09-25].

#### bf16 operands

The same program contracts bf16 operands when CORE `0x3018` names them. Software must set the
word's operand type, bits [10:8], to 3, and fill both buffers with bf16 bytes. One task is then
bit-exact at 16×256×64 and 64×1024×128. It is exact on an integer fill and on a fill scaled to
2^38 and 2^-51, which fp16 cannot represent. The datapath therefore keeps bf16's 8-bit exponent
rather than narrowing to fp16.

The bf16 contraction accumulates as the fp16 program does. On full 8-bit mantissas the
32-product group model matches every output bit for bit, at M 4, N 64 and K 32 to 2048.
[HW sweep, H96 MAX M9, `rocket` 1.6.0, 2026-09-26]

Only the CORE word selects the type. CNA `0x100C`'s precision fields, DPU `0x4010`'s processing
precision and the scale table can stay at fp16's values. In several combinations of them, the
output is the same and exact. A bf16 task does not corrupt the next submit, and an fp16 task
after it is exact. [HW sweep, H96 MAX M9, `rocket` 1.6.0, 2026-09-26]

No library entry emits bf16.

**Not characterized:** M tiling across tasks, and the K and N limits of one task, for bf16. The
program differs from fp16's in one field, so the limits are predicted to match [expected].

#### Single-task limits

One task of the matmul-form program has three limits [HW sweep, H96 MAX M9, `rocket` 1.6.0,
2026-09-25]. Nothing else the measurement reached limits one task.

> [!CAUTION]
> A task's input must fit the CBUF data window that CNA `0x1040` sets. A row of the activation
> takes `K/32` CBUF entries. A shape one row past the window comes back wrong on every row,
> rather than short by the rows past it. A second run is wrong the same way. Software must keep
> `(K/32)·M` at or below 4096 in each task.

> [!CAUTION]
> At K 6176 the program never reports completion, the same boundary the int8 program has.
> Software must keep K at or below 6144, and K 6144 is exact.

> [!CAUTION]
> At N 8960 the job writes exactly the first 768 columns and hangs. Software must keep N at or
> below 8192.

M is not rounded: 85×1536, 1365×96, 21×6144 and 512×256 are exact, and one row more at each is
wrong. The vendor's 4,940 fp16 streams all keep `(K/32)·M` under 4096, so that pattern is the
SoC's bound and not a compiler habit. The column count at N 8960 is 8959 mod 8192 plus one, so
CNA `0x1024`'s kernel count is 13 bits wide [hypothesis].

A 96 MiB weight at K 6144 N 8192 is exact, and so is M×N to 4096×2048, where `0x40B8`'s closed
form wraps. At every one of these shapes the charsiu emitter writes the same 148 words as
`librocketnpu`'s, so nothing in the program changes at the window.
[HW sweep, H96 MAX M9, `rocket` 1.6.0, 2026-09-25]

**Not characterized:** why the charsiu int8 program's window of 8192 entries does not apply to
fp16.

A row tile is an offset into the row-major activation and output. Past the window,
`rocket_matmul_fp16_rk3576()` therefore cuts M into equal tasks and submits them as one job of
that many task descriptors, one fence a call. Six shapes of 2 to 25 tasks are exact, to
2048×1536×256. [HW sweep, H96 MAX M9]

#### fp16 matmul entries

`librocketnpu`'s emitter for the program, `gen_matmul_fp16_rk3576()`, is exact. It emits the
program word for word, with 23 of its 148 words as closed forms of the shape (M, K, N). They
reproduce 441 of charsiu's streams, swept over M 1-32, K 32-4096 and N 16-1024. On the H96 the
emitter is exact at 23 one-task shapes to the limits above [HW sweep, `rocket` 1.6.0,
2026-09-25].

A resident weight closes most of the per-call host gap. The per-call entry is 2.9-3.3x the int8
entry at K up to 256 and 1.9-2.3x beyond, 0.96-4.19 ms against 0.30-2.16 ms. It allocates five
buffers a call, one a 257 KiB coefficient buffer that depends on N alone.
`rocket_matmul_fp16_rk3576_wbo()` holds the weight and the coefficient buffer in a handle, and
is bit-identical to the per-call entry at all 18 tested shapes.

### int8 matmul jobs that raise no completion

At specific `K`, an int8-output matmul job raises no completion and leaves a partial output. The
`rocket` driver retires every such submit at its 125 ms backstop
(`job of 1 task(s) did not report completion in 125000 us; retiring it`). At `M`=512 `N`=1536,
every row is exact up to one column and wrong from it on [HW sweep 2026-09-27]. The weight-phase
rule below gives where the job stops.

**Conditions:** H96 MAX M9, `rocket` 1.6.0, kernel 7.2.3. The int8 matmul at `M`=512 `N`=1536.

| `K` | First wrong column | Wrong elements under a write check alone |
|---|---|---|
| 2208 | 384 | 589824 of 786432 |
| 2240 | 320 | 622592 of 786432 |
| 2272 | 288 | 638976 of 786432 |
| 2432 | 160 | 704512 of 786432 |
| 4480 | 160, in each 768-column tile | 622592 of 786432 |

> [!CAUTION]
> A retired job's output is partly written, so a check that asks only whether each task wrote
> passes it. Software must score each job's completion as well as its writes.

Under a write check alone, `rocket_matmul_int8_rk3576()` returned 0 over that output at all five
`K`. The entry plans around the stall (§"Planning around the weight-phase rule"), which computes
all five exactly, and scores each job's completion as well
([../perf/rk3576-graph.md](../perf/rk3576-graph.md) §"Redo of a retired job"). On the plan that
stalls them, `K`=2304 stays exact under both checks, at 23.7-26.4 ms.

#### The weight-phase rule

Where a job stops is an arithmetic rule on the weight slice. Output-channel group `g` of a direct
task completes only if

```
(g*S mod 64 KiB) + S <= R_w
S   = 32*ic*kh*kw bytes, one 32-channel group's weight slice (32*K for the matmul)
R_w = 64 KiB * floor((3072 - F) / 1024), the CBUF weight area the feature allowance F leaves
```

The phase counts from the weight base register. The weight area `R_w` is 192 KiB at `F`=0, 128 KiB
at `F`=256, 512 and 1024, and 64 KiB at `F`=2048, and it counts in whole 64 KiB units. The first
group that breaks the rule is not written, and neither is any later group. The job raises no
completion, and `rocket` retires it at the backstop with the groups before it exact [HW sweep
2026-09-27].

The allowance moves the stall, and the rows, `M` and the weight address do not. A `K` of 2048 + d
or 4096 + d stays clean at every tile width for a power-of-two d, and only for one.

**Conditions:** H96 MAX M9, `rocket` 1.6.0, kernel 7.2.3, BO pool off. The int8 matmul at `M` 512
with `N` 1536 and 768, at `F` 1024 and 0.

Why the unit is 64 KiB is not known. A likely mechanism, not isolated: the weight side stages the
CBUF in 64 KiB units, and holds each 64 KiB window of the slice at once [hypothesis].

The same rule reproduces the convolution slice caps with no fitted constant. At `F`=0, a task of
four groups keeps this many of them at each slice:

| Slice at `F`=0 | Groups kept, of four |
|---:|---:|
| 144 KiB | 4 |
| 145 KiB | 3 |
| 148 KiB | 3 |
| 152 KiB | 2 |
| 156 KiB | 2 |
| 162 KiB | 1 |

At `F`=1024 the last exact slice is 96 KiB for 2 groups, 85 KiB for 3 and 80 KiB for 4. At
`F`=2048 it is 32, 21 and 16 KiB for the same counts. The escapes at 96 and 128 KiB (`F`=1024) and
32 and 64 KiB (`F`=2048) follow too. The reserve in `r76_weight_slice_cap_at()` is this
arithmetic.

**Not characterized:** a measurement of the rule with a kernel larger than 1. The convolution
agreement rests on the slice-cap measurements.

#### Planning around the weight-phase rule

The int8 matmul plans around the rule, so no job stalls [HW sweep 2026-09-27]. The entry takes
whichever of two plans needs fewer jobs. One shortens the row window until its allowance holds the
whole tile. The other caps the tile at the groups the planner's own window holds. The function
`rocket_rk3576_weight_phase_groups()` states the rule, and `ROCKET_RK3576_MM_PHASE=0` turns the
plan off.

**Conditions:** H96 MAX M9, `rocket` 1.6.0.

| `K` at `M` 512 `N` 1536 | Plan | First call |
|---|---|---|
| 2144, 2208, 2240, 2272, 2336, 2432, 2528 | one-row windows, full width, 8 jobs | 23.2-30.3 ms |
| 2304, 2560 (no stall) | unchanged | 23.8-27.0 ms, 28.5-32.3 ms |
| 4192 | 672-channel tiles | 62.0-63.6 ms |
| 4480, 4576 | 160- and 128-channel tiles | 83.2-90.0 ms |
| 4608 (no stall) | unchanged | 65.8-66.9 ms |

Every test point is exact with no retirement, on the first call and the repeat, with the narrowing
below turned off. At `K`=2240 the entry is also exact at `M` 192, 1024 and 2048, and the
resident-weight entry is exact at four stall shapes.

The convolution planner plans by the same rule. The slice-cap table alone passes three bands that
the rule stalls, each with enough output-channel groups:

- A slice in (64, 80] KiB at `F`=1024
- A slice in (128, 144] KiB at `F`=0
- At `F`=2048, any slice that does not divide 64 KiB, once the whole cube is past 192 KiB (the
  cube charge keeps a smaller cube off `F`=2048)

Planned by the slice-cap table alone, each shape stops where the rule says:

| Shape | Slice, allowance | Exact at | Refuses at |
|---|---|---|---|
| IC 96, k5, 48×64 | 75 KiB, `F`=1024 | 160 channels | 192 |
| IC 480, k3, 8×8 | 135 KiB, `F`=0 | 288 | 320 |
| IC 32, k3, 90×128 | 9 KiB, one task at `F`=2048 | 224 | 704 |

Each refusal is eight retirements with the output partly written. The planner skips an allowance
whose area cannot hold the task's groups, and caps the tile at what the `F`=0 area holds. With
that skip, every one of these shapes is exact with no retirement, and runs in 9-53 ms [HW sweep
2026-09-27]. The skip covers the int8 direct path it was measured on.

#### The rule on the other convolution paths

The fp16 convolution program follows the rule with a 16-channel group, and writes at most 32
output channels [HW sweep 2026-09-27]. The depthwise and packed-image planners charge the whole
cube, which keeps them off the rule except at the depthwise area's edge.

**Conditions:** H96 MAX M9, `rocket` 1.6.0.

One fp16 program writes 32 output channels and no more, at every allowance, kernels 1-7, planes
8×16 to 64×176, and one and two input-channel slices. The bound is the same as the float first
conv's.

> [!CAUTION]
> Past 32 output channels, an fp16 task completes and channels 32 and up are never written. The
> call returns 0 with no retirement. Software must tile an fp16 convolution's output channels
> at 32.

For the rule, the fp16 program's group is the float cube's 16 channels. At `F`=2048, k9 and k11 at
oc 32 on a 64×176 plane leave channels 16-31 unwritten. A 200 ms settle does not bring them back.

> [!CAUTION]
> An fp16 job that breaks the rule completes on `PC_DONE`, so the stall does not retire. Software
> must cap an fp16 tile at the rule's 16-channel groups.

The fp16 entry tiles the output channels at 32 and caps the tile at the rule's groups.

The depthwise planner charges the whole cube, which keeps it off the rule except at the area's
edge. At `F`=2048, k3 on 16×10, a 65088-byte cube is exact and 65664 bytes stalls.

> [!CAUTION]
> A depthwise cube between those two sizes returns a wrong output: at `F`=2048, k3 on 16×10, a
> 65376-byte cube is wrong in channels 0-47. Software must charge the depthwise cube at the
> feature granule the RK3576 holds.

Charged that way (`r76_dw_cf()`), those cubes plan at `F`=1024, exact. The boundary is fitted at
k3 and `F`=2048 only.

The packed-image first conv cannot reach the rule. Its planner charges the task's whole cube, at
most 1 KiB at `F`=256 and 512.

The fp16 matmul form refuses at K 4192, N 512 after eight retirements, where 4160 and 6144 are
exact. It fails as a refusal, not silently. The rule's stop channel was not read.

#### Unpredicted stalls and the rule's scope

The int8 matmul entry still computes the result after a stall the rule does not predict. When a
job retires with its output partly written, the entry halves the tile's width, down to 32
channels, and redoes the tile. The width that completed is kept per `K` for the process, and
`ROCKET_RK3576_MM_NARROW=0` turns this off. Without the plan, the narrowing took 0.75-1.28 s on
the first call and 31-91 ms after it at these `K`.

> [!CAUTION]
> A job after a stalled one can write nothing. With a 105 ms idle between jobs, 12 of 129 jobs
> that followed a stalled job were retired unwritten. None of 71 that followed a completed job
> was. Software must score the job after a stalled one. If that job retired, software must redo
> it.

The redo then computes as the rule predicts. Why the idle does not clear the state is not known.

The stall is distinct from the jobs that name no completion class. The function
`rocket_submit_matmul` passes `job_flags = 0`, which is the correct hint for an int8-output DPU
convolution, and the DPU does raise a completion on this path. The `NO_DPU_DONE` and `PPU_DONE`
classes describe other programs. The job asks for the right completion and does not get it.

The rule was not measured on these:

- The int32 writer
- The K-split path
- Varied weight values
- The fp16 allowances `F`=256 and 512
- The depthwise boundary away from k3 at `F`=2048

Why one fp16 program stops at 32 channels is not isolated.

#### Chunk depths for the K-split

Chunk depths from 768 to 2304 complete with no stall, and all sit on the entry's linear cost law
[HW sweep 2026-08-11].

**Conditions:** H96 MAX M9, `rocket` 1.6.0. `M`=512 `N`=1536.

| Chunk depth | Time, ms | Plan |
|---:|---|---:|
| 768 | 12-14 | 2 |
| 1280 | 16.7-16.9 | 2 |
| 1792 | 22.5-23.1 | 4 |
| 2048 | 25.4-27.1 | 4 |
| 2304 | 27.9-29.7 | 4 |

At `K`=6144 the entry also computes, and the call costs 166 ms, 2.7x what the linear law predicts.
The single-task planner collapses the output tile there and plans 768 row tasks. The call is
therefore bound by its submits rather than by the contraction. The same effect, a per-submit cost
that is not a fixed overhead, appears from the other end in this sheet's 32x-in-submits,
2.7x-in-wall-clock-time result. That `K` is inside the entry's `K < 6176` refusal by 32, and a call at
it does not hang the NPU. The hang that needs a reboot is the int32 K-split path on the narrow
writer (§"The K-split wedge"), not a single call at a large `K`.

A three-chunk cut of `K`=8960 (6144 + 2304 + 512) therefore costs about 201 ms a call, against
~109 ms for the default four-chunk cut. It is an accuracy test case, not a candidate default [HW
sweep 2026-08-11].

### Datapath blockers for a GEMM frontend

On `rocket` 1.5.0, two defects in the datapath, rather than its speed, block a GEMM frontend on
the RK3576.

#### The K-split wedge

At prefill scale, a matmul whose `K` takes the int32 K split can wedge the NPU until a reboot
[HW sweep 2026-08-05]. The wedge is measured at one shape, on the narrow int32 writer and
`rocket` 1.5.0. The K split begins at `K >= 6176`.

> [!CAUTION]
> On `rocket` 1.5.0, an int8 matmul at `M=512 K=8192 N=2048` through the K split wedges the NPU.
> Its plan is plane 32×16, K slice 4608, 2 slices, N tile 256, the narrow writer and 256
> submits.
> `rocket_matmul_int8_rk3576()` returns `-4` after its write guard's eight power cycles. The
> driver then raises its DMA-error interrupt, `WARNING: rocket_job.c … rocket_job_irq_handler`.
> That warning is one of the handler's two `WARN_ON`s over
> `PC_INTERRUPT_RAW_STATUS_DMA_{READ,WRITE}_ERROR`.
>
> Afterwards the NPU is unusable in every process, and shapes that ran clean minutes earlier
> return `-4`. A `rmmod`/`modprobe` does not recover it: core 0 then fails to probe with `-22`,
> alongside `rk_iommu … FORCE_RESET command timed out`. Only a reboot clears it.
>
> Software must run a matmul with `K >= 6176` on the dense int32 writer or on the host, not on
> the narrow writer. Treat any measurement taken after a wedge as contaminated.

On `rocket` 1.6.0 the dense int32 writer runs the same shape in 345.7 ms and 48 submits, with
no redo. Its 4096 sampled elements are exact [HW sweep, H96 MAX M9, 2026-09-30].

The K split's class is `K >= 6176`, not `K > 4608`, and the threshold does not move with `M` or
`N` [host-computed 2026-08-06]. The single-task planner halves the output-channel tile, down to
32 channels, before it gives up. The boundary is therefore the CBUF pool at a one-group weight
cube, a condition on `K` alone, and not the K-slice cap. Over thirty `(M, N)` with `M` 64-2048
and `N` 512-8192, the smallest 32-multiple `K` that takes the int32 K split is 6176 in every
one.

No narrower boundary inside the class is measured. Small matmuls in the class run exactly.
Every axis that separates them from the wedge moves with the others, so no boundary can be
fitted to them.

##### Software support

`rocket_matmul_int8_rk3576()` declines a `K` in the class [HW sweep 2026-08-06]. It returns
`ROCKET_E_UNSUPPORTED` with nothing submitted and no BO allocated. `ROCKET_RK3576_MM_KSPLIT=1`
takes the K split anyway, for measurement. `rocket_matmul_int8_rk3576_i32()` runs the K split
when called directly, on the dense writer by default (§"The int32 output and the K split").

#### The single-group band below the K split

Between `K` 4993 and 6144, the planner's output tile collapses to 32 channels in one step. The
matmul then takes 2.7x the wall-clock time of the wide tile, not the 32x its submit count
suggests [HW sweep 2026-08-06]. Nothing refuses and nothing produces wrong output, so a
frontend that sizes a model by whether it runs does not see the band.

`r76_weight_slice_cap()` is stated over the *group count*. The resident slice it is compared
against, `32*K`, does not depend on the tile at all. Once `32*K` passes the two-group cap of
156 KiB, the only tile left is 32 channels [host-computed 2026-08-06]:

| `K` | largest output tile | why |
|---|---|---|
| `<= 4608` | up to 2048 | `32*K <= 144 KiB`, the >= 4 group cap |
| `4609-4736` | 96 | 3 groups, 148 KiB |
| `4737-4992` | 64 | 2 groups, 156 KiB |
| `4993-6144` | 32 | one group: only the CBUF pool binds |
| `>= 6176` | none | the K split |

At `M=512 N=2048` that is 32 submits at `K`=4608 and 1024 at `K`=5120. At `N`=4096 it is 64
against 2048.

**Conditions:** H96 MAX M9, `M=512 N=2048`, one process a test point and three processes a `K`,
`taskset -c 4`, `ondemand` governor.

| `K` | tile | submits | wall-clock time, median of 3 processes | exact |
|---|---:|---:|---|---|
| 4608 | 1024 | 32 | 72.2 / 71.5 / 71.9 ms | 3 of 3 |
| 5120 | 32 | 1024 | 191.7 / 175.3 / 191.3 ms | 3 of 3 |
| 6144 | 32 | 1024 | 184.5 / 203.4 / 182.4 ms | 3 of 3 |

The collapse costs 2.41-2.86x over the repetition extremes and 2.66x on medians, so 32x the
submits gives 2.7x the wall-clock time. Each of the 992 extra submits costs 120 us, where a
wide-tile submit costs 2.25 ms.

> [!NOTE]
> A per-submit cost scales with the output tile. Estimate a matmul's time from a per-submit
> cost measured at the same tile, not from a wide-tile figure.

Inside the band, wall-clock time is flat in `K`. `K`=6144 has 20% more MACs than `K`=5120 and
measures the same 182-203 ms. The collapsed band is therefore dispatch-bound rather than
MAC-bound, and the extra contraction depth costs nothing. Offloading the band still gives
roughly 1.8x, against the 4.2x the same shape gets at `K`=4608. Scaling ggml Q8_0's measured
531.8 ms at `M=512 K=4096 N=4096` by MAC count puts the CPU near 334 ms at `K`=5120 `N`=2048
[expected, derived, not measured]. That compares with the NPU's 185.

A cap change that keeps the wide tile in the band can gain at most that 2.4-2.9x, on
`4993 <= K <= 6144` alone. The submit count depends on `(M, N)`, so neither the ratio nor the
32x transfers to another column [HW sweep 2026-08-06].

#### The K-split wedge's register program

The wedge is not a regcmd encoder overflow. In the 143-op register program of the wedge's first row
task, no value is near the width of its register [pure, 2026-08-06]:

| Register | Offset | Value | Meaning |
|---|---|---|---|
| `CNA_WEIGHT_BYTES` | 0x101C | 0x480000 | The weight BO's exact size |
| `CNA_DMA_CHANNEL` | 0x107C | 4607 | `ic-1` |
| CBUF data-entry count | | 2304 | Against a programmed feature allowance of 4096 granules |

Every library bound passes, one of them with no margin at all. The resident slice is
`32 * 4608` = 147456 bytes, against a `r76_weight_slice_cap` of exactly 147456 at >= 4 groups.
The whole cube is 4.5 MiB against a 6 MiB bound. The cause of the wedge is therefore outside
the library's model of the NPU.

#### Dropped writes at the drain deadline

On `rocket` 1.5.0, the int8 matmul entry loses part of its output at some prefill shapes [HW
sweep 2026-08-05]. The driver retires a job while the DPU is still writing. The cause is the
drain deadline, RK3576-E3, whose hazard, Caution and module-version scope are under [The direct
path's drain deadline](rk3576-hazards.md#the-direct-paths-drain-deadline). Every lost element is
a dropped write, not wrong arithmetic. It holds the library's `0xA5` device stamp, which sits
99-100 from the reference.

The loss is confined to the job's last task, and always reaches the last output column. On
`rocket` 1.5.0 at `dpu_grace_us`=500, `M=256 K=2048 N=2048` loses elements in 12 of 14
repetitions. The loss is 768 to 26112 of its 524288 output elements, changes from one repetition
to the next, and reports no error.

Two later runs of five repetitions each used the same shape and grace. Over those ten, the lost
output's extent spans 14x, 2944 to 40576 elements, 0.56% to 7.7% [HW sweep 2026-08-06]. The host
de-tile always runs, so what is lost is inside the device buffer, not a skipped copy-out.

> [!NOTE]
> A single repetition cannot size this hazard, and a repetition that reports a small extent does
> not show a nearly correct datapath. Size it over many repetitions, not a handful.

##### `dpu_grace_us` on `rocket` 1.6.0

On kernel 7.1.7 with `rocket` 1.6.0 in-tree, `dpu_grace_us` 0 means *wait for the writing block*
instead of *retire on the next tick*. A nonzero value restores the deadline. On a 1.6.0 kernel
`dpu_grace_us` therefore reproduces the hazard on demand [HW sweep 2026-08-10].

**Conditions:** H96 MAX M9, kernel 7.1.7, `rocket` 1.6.0 in-tree, `M=256 K=2048 N=2048`, one
process per configuration, a pinned core, the same boot and binary for both.

| `dpu_grace_us` | wrong reps | dropped elements |
|---|---:|---:|
| 0 (wait, the default) | 0 of 5 | 0 |
| 500 (a capped deadline) | 5 of 5 | 247728 |

Every one of the 247728 wrong elements is a dropped write.

> [!NOTE]
> On `rocket` 1.6.0, forcing a deadline also raises the driver's DMA-error warning, a `WARNING`
> in `rocket_job_irq_handler()`. It is the handler's `WARN_ON` on
> `PC_INTERRUPT_RAW_STATUS_DMA_READ_ERROR`/`_WRITE_ERROR`. Expect it with a nonzero
> `dpu_grace_us`. It is not a new
> defect.

> [!NOTE]
> An image whose boot already sets the taint word's `W` bit cannot show a new warning in
> `/proc/sys/kernel/tainted`. On this image an unrelated `rga3` warning sets it, and the taint
> word is 4608 before and after the DMA-error warning. Count `dmesg` WARNINGs instead.

#### Geometry of the lost output

The matmul entry's lost output has a different shape from the convolution path's, and its
mechanism is not decoded [HW sweep 2026-08-10]. The convolution path loses a contiguous suffix
of output-channel groups. The matmul entry loses a triangle, anchored at the last task's first
row (128) and the last output column (2047). Its front is quantized to 32 columns. The triangle
fills 0.49-0.56 of its own bounding box every time.

**Conditions:** H96 MAX M9, kernel 7.1.7, `rocket` 1.6.0, `dpu_grace_us`=500 to induce the
loss, `M=256 K=2048 N=2048`, a reference that is zero everywhere and a stamped output BO.

The per-row map shows the triangle:

- Each wrong row holds exactly one run, and it always ends at the last column. The loss is
  a suffix of each row, never scattered.
- The per-row width falls monotonically from the last task's first row to the last wrong
  row. It narrows 20-23x end to end, and ends in a single 32-wide run.
- The front moves in 32-column steps at about 8 columns per row, and every run starts on a
  multiple of 32. A channel-group *granularity* is present, but a channel-group *structure* is
  not. The convolution path's loss is a union of aligned groups. This one is a single run whose
  edge is quantized to the same 32.
- The apex does not reach the last row. The wrong region ends at rows 235, 231 and 223 of a
  0..255 output, one per repetition. Where the triangle ends is a race against wall-clock time,
  and it varies per repetition, as the 14x extent spread does.

> [!NOTE]
> The geometry is measured in the host-de-tiled output. The de-tile un-permutes the cube
> layout, so a linear front in the DPU's own write order can appear here as a triangle. Do not
> infer a write order from it. Any mechanism it suggests is [hypothesis].

#### Exposure across shapes

With the deadline induced, the dropped writes reach at least four shapes, and the rate depends
on the per-submit output size [HW sweep 2026-08-10].

**Conditions:** H96 MAX M9, kernel 7.1.7, `rocket` 1.6.0, `dpu_grace_us`=500 as the inducer, one
shape per process.

| shape | tasks | wrong repetitions | rate |
|---|---:|---|---:|
| `128x2048x2048` | 1 | 3 of 5 | 60% |
| `256x2048x2048` | 2 | 5 of 5 | 100% |
| `384x2048x2048` | 3 | 4 of 25 | 16% |
| `512x2048x2048` | 4 | 5 of 25 | 20% |
| `1024x2048x2048` | 8 | 0 of 25 | 0% |

The table shows four results:

- **The rate falls sharply with the submit count** past `M`=256: 100%, then 16-20%, then 0 of 25

- **Both `K`=2048 and `N`>=2048 are needed.** Halving either one takes the shape to 0 of 25,

#### The int32 output and the K split

On an integer program, the DPU can write its 32-bit accumulator, and the K split is built on
that output [HW sweep 2026-07-27]. Three register programs write it. The narrow and wide writers
below widen `0x4010` on the regcmd encoder's partial output stage. The dense writer uses a whole output
stage ([rk3576-regcmd.md](rk3576-regcmd.md) §"The dense writer").

The narrow writer, `gen_conv2d_int8_rk3576_i32out()`, programs `precision_int32` in DPU
`0x4010`'s output-width field, and pins OUT_CVT to exact unity. The words written are int32
accumulators on the RK3588's int32 cube map, `(c/4)*ow*oh_full*4 + 4*(y*ow+x) + c%4`.

On the partial stage, the DPU writer's budget is one 16-byte atom per (16-channel block, pixel)
at an int8 `PROC_PRECISION`, whatever the output element width is. The budget follows
`PROC_PRECISION` (`0x4010[2:0]`), the DPU's own operand width, and not the output element's.

> [!CAUTION]
> At four bytes an element on the partial stage, the DPU writes only the first eight output
> channels of every thirty-two. Software must place each real channel in a delivered slot
> ([rk3576-regcmd.md](rk3576-regcmd.md) §"The int32 output").

Widening `0x4010[2:0]` from int8 to int32 makes it two atoms. The delivered set
becomes the first eight of every sixteen, so a real channel costs two programmed ones instead of
four. The arithmetic is bit-identical, and the CNA and CORE programs are byte-unchanged.

Two atoms is the maximum `PROC_PRECISION` reaches on the partial stage. int16, fp16 and bfloat16
reach it too, and the float ones destroy the arithmetic. Neither int4 nor int8 reaches it.

`gen_conv2d_int8_rk3576_i32out_wide()` emits the two-atom form, and
`rocket_rk3576_i32_wide_word()` addresses it. The map is a stream `s = 2*p + j`, cut into runs of
`ow*oh_full` atoms inside 32-channel super-groups. The decode covers `oc` 8 to 192 and pixel
counts 4 to 33.

> [!CAUTION]
> The wide map has two bounds that fail silently. Software must keep `oc` a multiple of 32 and
> the output short. The height rule the library enforces, `oh_full * oc < 4096`, is a safe cap
> and not the boundary. With the cap lifted, the map is exact well past it at `oc` 32, 64, 96
> and 256, and wrong inside it at `oc` 128. The plane width does not enter the bound. The
> failures are neither monotone in height nor repairable by the writer's own redo
> (`chips/rk3576-regcmd.md`).

> [!CAUTION]
> On about one run in ten of its worst shape, the wide writer writes zeros over a contiguous
> block of one super-group's stream. The rest of the output is exact. The writer reaches those
> atoms and writes the wrong data. With a sentinel stamped first, the bad atoms
> hold zero rather than the sentinel. On a fresh BO, which arrives zeroed, the two readings are
> indistinguishable. Software must check each row task for this block and redo the task.

The zeroed block is not the wide-output hazard that corrupts the next submit, because the idle
time ahead of the job does not affect it. It is contiguous in the writer's emission order and in
no other, and it lies inside a single super-group. It always ends two emissions short of that
group's last.

> [!CAUTION]
> A narrow- or wide-writer job corrupts the next submit, of any kind and across processes. The
> state lives in the NPU and not in the fd. The corrupted submit writes nothing. It completes in
> the usual per-submit time, except on `rocket` 1.6.0, where the driver retires it at the 125 ms
> backstop.
>
> The corruption is the SoC's one wide-output hazard, which the partial output stage triggers.
> The regcmd encoder's fp16 programs on that stage have it too. The dense writer and the fp32-output
> fp16 convolution, both on a whole output stage, do not. Its scope, its negatives and the
> guard's sizing law are in [rk3576-hazards.md](rk3576-hazards.md) §"The wide-output hazard".
>
> Software must check, per task and not per tile, that each job wrote. One corrupted submit
> among a row-split tile's leaves its own rows empty, while its siblings are full.

> [!CAUTION]
> Software must bracket any CPU fill of an output buffer with `PREP_BO` and `FINI_BO`, Erratum
> RK3576-E5 ([rk3576-regcmd.md](rk3576-regcmd.md) §"Related hazards").

> [!CAUTION]
> The int32 sweep also wedged the IOMMU once, and only a reboot cleared it. The mechanism is not
> established. The measured extent stays inside the allocated BO, so the data do not support an
> overrun as the explanation. Software must reboot the board to recover from an IOMMU wedge.
> Details are in [rk3576-regcmd.md](rk3576-regcmd.md) [HW sweep 2026-07-27].

##### Software support

`rocket_matmul_int8_rk3576_i32()` runs the dense writer by default. `ROCKET_RK3576_I32_DENSE=0`
restores the narrow and wide writers, and `ROCKET_RK3576_I32_OC_MULT=4` or `=2` forces the
narrow or the wide one. All three are bit-exact against a CPU int32 model at K up to 16384.

On the older writers, the multiplier costs N tile width, and so submits. The measured count
falls from 4 submits to 2 at M=64 K=1024 N=2048, and from 8 to 4 at M=32 K=1024 N=4096. Below
the tile cap the two writers cost the same.

The wide writer is opt-in because of the zeroed block. `rocket_matmul_int8_rk3576_i32()` detects

Of the machine parameters, the CBUF is swept: its budget, the data/weight split, and the field
that trades between them. The matmul tile cap and the weight N-group are measured against the

#### The op library on the RK3576

The weight-slice cap applies to one register program, and its value depends on the number of
output-channel groups that program drives. Splitting the output channels lowers the group
count and raises the slice the RK3576 accepts. The single-program rule is
`ic*kh*kw <= 4608`. A program that drives one output-channel group is bounded by the CBUF pool
instead, at about `ic*kh*kw <= 5600` [HW sweep, H96 MAX M9, measured 2026-07-27].

Zero points fold exactly into the convolution program, and the library's test covers them:

- The input zero point's correction is `-in_zp*sum(w)`, with no special case at the border.
  Software programs the pad constant to the input zero point, so a pad tap's true value is
  zero.
- The weight zero point's correction is programmed in the coefficient group's `B`, which the
  DPU adds, so it is programmed negated.
- The output zero point becomes the `OUT_CVT` offset.
- A depthwise convolution's coefficient group has no `B` field. Its weight zero point is applied
  in the weight cube instead (§"The depthwise weight zero point").

> [!CAUTION]
> A BO belongs to the file descriptor that created it, and its IOVA is valid only on that fd.
> A register program submitted on another fd hands the NPU addresses that mean nothing there,
> and the submit still succeeds. Software must submit a program only on the fd that created
> its BOs.

##### Software support

`librocketnpu` runs convolution on the RK3576 through `rocket_conv2d_int8_rk3576()`,
`rocket_conv2d_dw_int8_rk3576()` and `rocket_conv2d_fp16_rk3576()`. They take row-major
tensors and handle the cubes, the row plan, the output-channel split, the de-tile and the
submit-loop retries. Where a public entry's semantics match the RK3576 datapath, it dispatches
to the RK3576 entry, and software needs no chip-specific code. Both `rocket_conv2d_dw_int8()`
and `rocket_conv2d_fp16()` dispatch this way.

The direct entry, `rocket_conv2d_int8()`, writes a raw int32 accumulator, where the RK3576's
direct int8 datapath requantizes on chip. It refuses on the RK3576 and names the entry that
matches, as `rocket_matmul_int8()` does.

A prepacked handle packs a layer's weights once. Repacking them per call takes most of a
graph's wall-clock time, and the MobileNet section gives the 2.94x figure. The packing entry,
`rocket_conv2d_int8_pack_rk3576()`, takes the weights, the bias and the quantization
parameters, and returns a handle. Each inference runs it through
`rocket_conv2d_int8_prepacked_rk3576()`. One handle covers all three per-call entries:
`desc.depthwise` selects direct or depthwise, and a non-NULL `w_scale_oc` selects the
per-axis requant.

The handle fixes three things at pack time:

- The `fd`. The handle refuses a foreign fd.
- The output-channel tile. The weight cube's group count follows the tile rather than the
  layer. On the per-axis path, the tile is an accuracy choice made from the weights and the
  scales.
- The quantization parameters. Both zero points and all three scales are folded into the
  coefficient group at pack time.

The handle also holds the scratch whose size follows that geometry: the feature cube, the
regcmd buffer and each tile's output buffer. An inference therefore allocates no BO, which
matters more to its time than the arithmetic does.

Reusing an output buffer across inferences is safe. On a SoC where the write guard checks
whether a task wrote anything, the library re-stamps the sentinel before every submit. With
the sentinel off, there is no check to mislead. Reusing the feature cube skips its zeroing
memset from the second call on. The channels past `ic` are the cube's zero padding, and
nothing writes them again.

On 173 shapes of the library table, two prepacked calls each match the per-call output
element for element [HW sweep, H96 MAX M9].

The library accepts more shapes than the emitter, by the amount the weight-slice rule
predicts. Fourteen shapes the emitter refuses run through the library
[HW sweep, H96 MAX M9, measured 2026-07-27]. They include `ic=576 k=3` and `ic=5184 k=1`, at
four tiles of 32 channels. One refusal remains, `ic=256 k=5` at 200 KiB. Its only recourse is
an ic split, which the on-chip requant rules out [HW sweep, H96 MAX M9, measured 2026-07-27].

#### Per-submit overhead and the completion poll

**Conditions:** H96 MAX M9, an 8×64×32 int8 matmul, 300 submits, pinned to one A72.

The per-submit overhead is the driver's completion poll, at about 340 us. The `INTERRUPT_MASK`
`PC_DONE` pair (bits 28-29) rejects writes, so the driver polls for it.
`patches/rk3576/npu/0006` polls `PC_DONE` on an hrtimer, and `0009` makes the period
`rocket.poll_interval_us`. With the period at 50 us, the median per-submit time is 329-331 us
on modules through 0020, and 344-348 us through 0021 and 0022. At the stock 1 ms period it is
1654 us. The overhead bounds every submit-bound workload, and on the RK3576 most workloads
are submit-bound.

> [!NOTE]
> A test's total wall-clock time does not show the per-submit overhead. Host packing and the
> CPU reference model dominate the convolution test's time, which stays flat at every poll
> period.

The DPU completion interrupt reaches the GIC, so the poll is the driver's choice
[HW sweep, H96 MAX M9, 2026-08-13]. Software can set `DPU_0`/`DPU_1` (bits 8-9) in
`INTERRUPT_MASK` at submit, and the mask holds them: `0x3300` written reads back as
`0x3300`. With them set, core 0's interrupt line fires once per submit, with `raw=0x30000155`
at each arrival. The line is `GIC_SPI 247` in the device tree, which `/proc/interrupts` lists as
GIC interrupt 279 (an SPI's number plus 32), shared with `27702000.iommu`
[HW sweep, H96 MAX M9, 2026-08-13].

A driver can therefore retire a job on the DPU interrupt, and the gahingwoo upstream v7 series
does. Two classes of program raise no DPU completion:

- Pooling, whose `PC_OPERATION_ENABLE` bitmap never enables the DPU.
- The narrow and wide int32 writers, which write a four-byte element through the partial output
  stage.

A submit that the wide-output hazard corrupts raises none either, and writes nothing. The fp16
convolution programs and the dense int32 writer raise the DPU completion (§"Retirement on the
DPU completion"). An interrupt-only driver cannot retire either class, so software must keep the
poll, or a grace, for them.

With the DPU interrupt enabled and retirement still on the poll, the per-submit median is
279.4 us. A control on the same base measures 351.2 us [HW sweep, H96 MAX M9, 2026-08-13].
The mechanism is not characterized. The likely cause is that the interrupt holds the waiting
CPU out of deep idle [hypothesis]. In that case the interrupt is worth more than the poll
latency it removes.

#### Retirement on the DPU completion

Retiring a job on the DPU completion makes a short poll period safe. `PC_DONE` means the
program counter has finished issuing, and the DPU's write DMA can still be draining. On the
RK3576 the `RAW_STATUS` bits `DPU_0`/`DPU_1`, which the RK3588 takes as its completion
interrupt, set 82-343 us after `PC_DONE`, scaling with the bytes in flight. A driver that
acts on `PC_DONE` tears the IOMMU mapping down and signals the fence before those writes
complete.

> [!CAUTION]
> A per-job IOMMU detach at `PC_DONE` faults the DPU writes still in flight. The write page
> fault (`RK_MMU_STATUS 0x2b`) blocks the next `enable_stall`. Software must not detach a
> job's IOMMU mapping until its DPU writes have drained.

The patch `patches/rk3576/npu/0011` fixes the fault. With it, stall timeouts and NPU DMA
errors are zero at every poll period.

> [!CAUTION]
> A job retired on `PC_DONE` can be read before its output is written, and more often at a
> shorter poll period. Software must retire a job on the `DPU_0`/`DPU_1` bits, as `0012`
> does.

Retiring on the DPU bits, the int8 matmul test and the whole test set pass at a 250 us and a
50 us period.

The narrow and wide int32 writers raise no DPU completion. They stop at
`RAW_STATUS = 0x30000055`, with CNA and CORE done and nothing further for milliseconds. On
`rocket` 1.5.0 the driver therefore bounds their wait by a deadline and retires them on
`PC_DONE`.

> [!CAUTION]
> A narrow or wide int32 writer retired at a 100 us deadline fails. One retired at 250 us or
> later passes [HW sweep, H96 MAX M9, measured 2026-07-28]. Software must give those writers a
> deadline of at least 250 us.

On `rocket` 1.6.0 the wait for the writing block has no deadline. There a narrow- or wide-writer
job submitted without `ROCKET_JOB_NO_DPU_DONE` waits out the 125 ms backstop [HW sweep,
2026-09-27]. Those writers also trigger the wide-output hazard
([rk3576-hazards.md](rk3576-hazards.md) §"The wide-output hazard"), which is separate from
retirement: `0012` leaves it unchanged.

The fp16 convolution programs raise the DPU completion. On 1.6.0 without the flag, the
input-channel slice program and the packed-image first conv each fence 0.38-2.2 ms after the
submit. Every element is written, and no job is retired at a deadline. At k9 over 32
channels on 120×64 the fence comes at 2.07 ms [HW sweep, H96 MAX M9, rocket 1.6.0,
2026-09-27]. After the wide-output hazard, an fp16 job writes nothing and waits out the
backstop.

At `oc` 32, 28×28 k3, the slice program fences a median 343-350 us after the submit, at
`dpu_grace_us` 0, 100 and 500. No run left a tail missing at the fence or logged a deadline
retirement [HW sweep, H96 MAX M9, rocket 1.6.0, 2026-09-30].

A slice submitted after the wide-output hazard raises no completion and writes nothing. At grace
500 it fences at 665 us. At grace 0 the driver retires it at the 125 ms backstop, and it fences
127 ms after the submit. In the same sweep, two of 50 slices with no preceding wide output also
wrote nothing after the 300 ms idle. The cause is not characterized.

> [!CAUTION]
> `ROCKET_JOB_NO_DPU_DONE` fences a job at the blind settle (the fixed `dpu_blind_us` wait),
> whatever its program is still doing. An fp16 program still running then completes without
> an error, with the last rows of each 8-channel plane unwritten. Those rows are written about
> 1.2 ms later. The write guard checks only whether a task wrote anything, so it does not see
> a missing tail. Software must set the flag only on a program that raises no DPU completion,
> and must check every element of that program's output.

Under the flag an fp16 program fences 0.73-0.94 ms after the submit [HW sweep, H96 MAX M9,
rocket 1.6.0]. Programs that finish by 0.62 ms come back whole: k1 and k3 on 120×64, and k9
on 32×32. Longer programs lose their tail: k9 over 32 channels on 120×64, k5 and k7 on that
plane, and k9 on 64×64. The threshold therefore lies between 0.62 and 0.96 ms of program
time. The narrow and wide writers' per-atom scan is the element check the flag requires.

The vendor `rknpu` driver has no special case for either class. It takes each task's interrupt
mask from userspace (`rknpu_task.int_mask`) and writes the last task's into `INT_MASK`. A job's
completion requires `INT_STATUS`, each bit pair folded to one, to equal that mask exactly. The
clear value, `0x1ffff`, never touches the `PC_DONE` pair at bits 28-29
[source-confirmed: BSP `rknpu_job.c`, 0.9.8, unchanged in `develop-6.12`]. What the vendor
stack waits on for a pool or a wide output is therefore `librknnrt`'s choice of mask.

**Not characterized:** the mask `librknnrt` programs for a pool or a wide output. Only a
capture of the submitted tasks on a vendor kernel shows it.

#### The settle wait on the fp16 path

**Conditions:** H96 MAX M9, `rocket` 1.5.0 with `0017`, `ic=128` at 28×28 k3, both fp16
entries submitting under `ROCKET_JOB_NO_DPU_DONE`, CPU governor pinned, 2026-08-06.

On that module, with the flag set, each slice of an fp16 convolution costs the poll overhead
plus a whole settle wait. An fp16 convolution is `ic/16` such submits, and takes no retries for
the wide-output hazard. The patch `0017` splits the settle into two waits. A job that raises no
DPU completion names itself with `ROCKET_JOB_NO_DPU_DONE` and waits `dpu_blind_us`, default 250.
Other wide-output jobs wait `dpu_grace_us`. Each parameter was swept with the other held:

| parameter | other parameter held | low | high | effect |
|---|---|---:|---:|---|
| `dpu_blind_us` | grace 500 | 250: **9.85 ms** (9.25-12.17) | 500: **12.90 ms** (12.09-14.63) | **3.05 ms**, ranges disjoint once the cold first pair is dropped |
| `dpu_grace_us` | blind 250 | 250: 9.83 ms (9.23-10.39) | 500: 9.95 ms (9.25-11.62) | 0.12 ms, ranges fully overlapping |

On the fp16 path the blind wait sets the cost, and the grace has no measurable effect. The
measured step is 1.5-2.1x the 8 x 250 us = 2.0 ms that one blind interval a slice predicts.
The likely cause is more than one blind wait per slice [hypothesis], and the step is not
decoded.
[HW sweep, H96 MAX M9, 2026-08-06]

On `rocket` 1.5.0 the default `dpu_grace_us` is 500 us. The int32 writers pass from a 250 us
deadline, so 250 is the measured edge rather than a margin above it. On `rocket` 1.6.0 the
default is 0, and `librocketnpu` submits the fp16 programs without the flag, because they raise
the DPU completion (§"Retirement on the DPU completion").

**Not characterized:** the int32 sweeps at a `dpu_grace_us` between 250 and 500 us.

#### Per-job core reset and the half-started job

> [!CAUTION]
> A per-job `rocket_core_reset()` does not clear the state the wide-output hazard leaves, and
> it takes the IOMMU down. The IOMMU reports `MMU_DTE_ADDR is not functioning`, and the NPU
> stays wedged. Software must reset a core only inside a scheduler stop and an IOMMU detach
> and re-attach, as the driver's timeout path does.

A bare call lacks the re-initialization around the timeout path's reset. The vendor `rknpu`
driver never resets per job either.

> [!CAUTION]
> A half-started job pins the NPU runtime-`active`. Convolutions then still run bit-exactly,
> and every int32 matmul on the narrow writer writes nothing [HW sweep, H96 MAX M9, measured
> 2026-07-27]. Only a
> power-domain cycle clears the wide-output hazard's state, and the pinned domain does not
> cycle. The symptom looks like a defect in the int32 writer. Software must check
> `power/runtime_status` before trusting any int32 result.

The fault is present in mainline `rocket` on the RK3588 as well, and
`patches/rk3576/npu/0010` fixes it. The two early returns in `rocket_job_run()` leave a
runtime-PM reference that nothing drops and a fence that nothing signals. Each pins the device
on its own. The usage counter never returns to zero, and the scheduler never takes back the
job's credit, which `rocket_device_runtime_suspend()` waits on. The usage counter is on the
platform device, so `rmmod`/`insmod` does not clear it
[HW sweep, H96 MAX M9, measured 2026-07-27].

Without 0010 the state also sustains itself. One failed attach times out, the timeout path's
core reset takes the IOMMU down, and the next attach fails as well. One injected failure
produced seven failures and leaked seven references
[HW sweep, H96 MAX M9, measured 2026-07-27].

### The PPU's pad nibbles

The PPU register `0x6040` contains four four-bit pads, with the leading pads in the low half,
not the trailing ones [HW sweep]:

| Offset | Field | Bits | Reset | Function |
|---|---|---|---|---|
| PPU `0x6040` | Left pad | [3:0] | | Leading pad on x |
| PPU `0x6040` | Top pad | [7:4] | | Leading pad on y |
| PPU `0x6040` | Trailing pads | [15:8] | | The right and bottom pads, the high pair |

The regcmd encoder's output does not depend on the trailing pads. It programs the window count
explicitly in `PPU_OUT_WIDTH`/`_HEIGHT` and the span in `PPU_IN_WIDTH`/`_HEIGHT`.

> [!CAUTION]
> With the two pad pairs swapped, an asymmetrically padded pool writes output of the correct
> size that is wrong nearly everywhere. No error is raised. A symmetric pad gives the same
> output under either map, so a symmetric test cannot detect the swap. Software must program
> the left pad in bits [3:0] and the top pad in bits [7:4].

A classifier's first max pool is asymmetrically padded. It is TFLite's SAME on an even plane at
stride 2, or torchvision's explicit pad whose trailing row no window reaches. It is therefore
the first asymmetric pool a real graph reaches.

> [!NOTE]
> Software must give a pool the trailing pad its last window consumes, which can legitimately be
> smaller than the pad the model declares. Torchvision's stride-2 3×3 pads one row at each end
> of an even plane, and its last window never reaches the trailing one. The programmed geometry
> must agree with the consumed value.

### The pooling output-width allowance

A PPU pooling task has an output-width allowance, and past it the task writes a full-size output
that is wrong from column 0. The limit is on the output width alone. At k3 stride 1, a 33-wide
plane is exact at every height up to 112. A 34-wide one is wrong at a height of 2. Past the
allowance every output column is wrong, in every mode including max, at both pads and at every
channel count. The output is written in full rather than partially, so a check for unwritten
output cannot detect it either.

> [!CAUTION]
> A pooling task wider than its output-width allowance writes a full-size, incorrect output and
> raises no fault. Software must keep each task's output width within the allowance for its
> kernel height and vertical stride. An allowance computed from the kernel width admits `kh > kw`
> windows that exceed it.

**Conditions:** H96 MAX M9, int8 max pool, c=32, both pads.

| kernel / stride | last exact `ow` | first wrong `ow` |
|---|---:|---:|
| k3 s1 | 32 | 33 |
| k2 s1 | 64 | 65 |
| k3 s2 | 64 | 65 |
| k5 s1 | 14 | 30 (bracketed, not pinned) |
| k3 s3 | 49 | none found in a plane of 147 |

An allowance of 128 at no overlap, halving for each additional output window in flight over an
input row, fits all five rows [hypothesis]. It matches a line-buffer budget shared across
`ceil(kh/stride_y)` windows [hypothesis].

The allowance's axis is the kernel height and the vertical stride. A square kernel cannot separate
the two axes, and a rectangular kernel at one plane does. The rows below give the last exact and
the first wrong output width, at VALID pad, height 8 and c=32:

| kernel h×w | last exact / first wrong `ow` | allowance keyed on the height |
|---|---:|---:|
| 3×1 | 32 / 33 | 32 |
| 1×3 | no limit found to 145 | 128 |
| 4×2 | 33 / 34 | 16 |
| 2×4 | 63 / 68 | 64 |

Keyed on the height, the allowance reproduces all four rows and every row of the square table.
Where it differs from an allowance keyed on the width, the height-keyed value is conservative
rather than over.

#### PPU destination and source addressing

The PPU's destination address has a channel-group stride and no line stride. Register `0x607C` is
the channel-group stride. The PPU honors it at every value at or above the plane, including odd
values. The value need not be a multiple of four atoms or of a 64-byte line. A value one atom
under the plane loses one atom.

Register `0x6084` is inert for the address. The destination row stride is always the programmed
output width, and no value of either register moves it. A column slice therefore cannot write into
a wider output plane, and each column slice writes its own.

A direct convolution's output surface stride is exactly `ow*oh`, and a pool's own is
`round4(ow*oh)`: 289 against 292 at a 17×17 plane. A pool can share a concatenation buffer with
convolutions only because the PPU honors a group stride that is not a multiple of four. A pool
written at such a stride is bit-exact in cube layout at planes of 289 and 49 (odd). It is also
bit-exact at a padded average whose divisor varies with position.

On the input side, the PPU programs what its windows consume (`0x600C`) separately from the DDR
line stride (`0x7024`). It honors a base part way into a row. A column slice can therefore read its
window directly from a wider feature cube, as the ordinary pitched cube.

#### Software support

`rocket_pool_int8_rk3576_max_ow()` computes the allowance keyed on the height, and is used as a
bound. It sits under the measurement where the two differ: it allows 8 at k5 s1, where 14 is
exact. An allowance under the measurement costs a refusal, and one over it costs a wrong answer.
The entry takes the whole descriptor rather than a `(kw, stride_x)` pair, so a caller cannot pass
the wrong axis.

The planner `rocket_pool_int8_rk3576_plan()` refuses a task past the allowance. The flag
`ROCKET_RK3576_POOL_OW_PROBE=1` lifts the refusal, so the limit can be measured.

The entry splits a wider plane by columns rather than refusing it. Each slice is one task. It reads
a column window of the caller's tensor and writes a column window of the output, so neither end
costs a copy. The scatter and the de-tile walk rows instead of whole planes, through the same
16×16 NEON block. **The entry refuses a plane that needs more than
`ROCKET_RK3576_POOL_MAX_SLICES` (8) slices.** The count is `rocket_pool_int8_rk3576_ow_slices()`,
which is pure and needs no device, so a caller can cost a shape before packing it.

A split costs `ceil(ow / max_ow) - 1` extra submits plus a row-walking de-tile. Because each
slice writes its own output, a split handle cannot be the producer end of a cube join, and cannot
be a chain node.

The field `pool_params_rk3576_t.dst_surf_elems` contains the group stride. A value of 0 keeps the
derived value, so every program that does not set it is byte-identical. The entry
`rocket_pool_int8_cube_out_at_rk3576()` takes the stride from the slice it is given, and refuses
only a stride below the plane.

The input end of a column-split pool joins, because one output per slice is a property of the
output side only. `rocket_pool_int8_cube_in_rk3576()` hands each slice a view of the same cube at
its own width and column. The split costs the input side nothing. The split input is bit-exact
against a CPU model of the RK3576's arithmetic, in max and both average modes and at two and five
slices. A cube that already declares a pitch and a column offset is bit-exact too. The
divisor-lag check below needs no change for it, because its cube view is written over `src_pitch`
and `src_col`.

#### Performance

**Conditions:** H96 MAX M9, Inception V3 at 299, int8, `bench 100`.

The column split runs Inception V3's four wide pools on the NPU instead of the host. The distance to
TFLite stays 0.0328%, and the top-1 is the same [HW sweep, H96 MAX M9].

Refusing the split pools' input join costs the graph 8.9 ms, 17% of its wall-clock time. Joining it
leaves the result byte-identical on all 130 layers [HW sweep, H96 MAX M9]. The gain comes from the
host transposes at the joins, not from the submits. The submit time is the NPU's own execution,
which a merged submit does not reduce. On this 64-submit graph, a marginal submit costs about
20 us. Fragmentation costs the transposes at the joins it refuses.

### The AVG_NOPAD pooling mode

PPU mode `0x18` (`ROCKET_RK3576_POOL_AVG_NOPAD`) is the exclude-pad average. It moves the divisor
and not the sum. It divides a border window by the taps that land inside the plane. The taps that
do not are still added, at the pad value. It is therefore neither count-include-pad nor TFLite's
`AVERAGE_POOL_2D`, and only the border outputs differ from either.

With a zero pad value, the mode is TFLite's function. TFLite's quantized average pool averages the
stored values over the valid count, and requires the input and output quantization to match. A zero
pad value gives exactly that [HW sweep, H96 MAX M9].

> [!CAUTION]
> With the pad value at the input zero point, PPU mode `0x18` adds the outside taps at that value.
> At a nonzero zero point, every border output is then wrong. Software must program the pad value
> as zero to compute TFLite's `AVERAGE_POOL_2D`.

> [!NOTE]
> At input zero point 0, all three candidate functions agree, so a test there cannot see this
> mode's behavior. Test the mode at a nonzero input zero point.

`librocketnpu`'s descriptor field `rocket_pool_desc.avg_exclude_pad` programs the pad value as zero
rather than as the input zero point.

With a truncated reciprocal, an exact tie rounds toward zero. With an exact reciprocal, it rounds to
even. The PPU multiplies by `0x10000/dw` and `0x10000/dh`, both floored. Unless each divisor
divides 65536, the product is slightly under `1/n`, and a sum falling exactly on a half goes to
the smaller magnitude.

In the seven-model corpus, only a padded average reaches this case. Every
other window is either odd, where no tie exists, or a power of two on both axes, where the
reciprocal is exact. Excluding the pad reaches 3×2, the first even window with a truncated
reciprocal.

### Erratum RK3576-E1: incorrect output with two jobs executing at once

- **Description:** Two `rocket` jobs that execute at the same time, one on each core, corrupt
  each other's output. The vulnerable window is the whole job. Wrong calls cover as much as
  94% of the output, with deltas spanning the whole int8 range. The damage grows with the other
  job's feature plane. The mechanism is not isolated. A shared CBUF feature-staging
  datapath, an undervolt at this operating point, and the per-core `S_POINTER` bit are open
  candidates [hypothesis] ([rk3576-validation.md](rk3576-validation.md) §"Two-core operation").
- **Conditions:** RK3576 with both cores bound, and two jobs in flight at once, from two fds in
  one process or from two processes. Measured at 786 MHz and `vdd_npu_s0` 750 mV only. Work
  from a single fd is not affected, and the whole test suite passes with core 1 bound.
- **Symptom:** 96-100% of calls return incorrect output. Each job completes in the usual time,
  and no error is reported [HW sweep, H96 MAX M9].
- **Workaround:** Software must keep one `rocket` job in flight at a time. Leave core 1
  disabled (`status = "disabled"` on its device-tree node), unbind it, or serialize every
  submit. A mutex inside one process does not cover a second process. With one job in flight,
  every call is exact, however many cores are bound.
- **Status:** Open.

To unbind core 1 without a device-tree change:

```sh
echo 27708000.npu | sudo tee /sys/bus/platform/drivers/rocket/unbind
```

Writing the same name to `bind` puts it back.

### Erratum RK3576-E2: next submit unwritten after a wide output

- **Description:** A program can write a DPU output element wider than one byte through a
  partial output stage. It then leaves a state inside the NPU, outside the DPU register file, in
  which the next submit writes nothing. Only a power-domain collapse resets it. The regcmd encoder's
  int32 writers set it through DPU `0x4010` alone, and its fp16 programs through `0x4038[4]` and
  `0x4050[17]`. A whole output stage writes the same widths without the hazard, so neither
  condition decides it alone [HW sweep, H96 MAX M9].
- **Conditions:** H96 MAX M9. On the regcmd encoder's partial output stage, the fp16 direct and first
  convolutions and the narrow and wide int32 writers trigger it. A one-byte output never does, and a pooling job does not. Neither do
  the matmul-form fp16 program, the dense int32 writer or the fp32-output fp16 convolution on a
  whole output stage. The hazard persists on `rocket` 1.6.0, kernel 7.2.3-1
  [HW sweep, H96 MAX M9, measured 2026-09-24 UTC].
- **Symptom:** The next submit, of any kind and from any process, writes nothing and reports no
  error. Every victim kind measured behaves this way: the seven convolution and matmul kinds, a
  LUT job and an elementwise program. The victim completes in the usual time, except on
  `rocket` 1.6.0. There the driver retires it at the 125 ms backstop and logs a `retiring it`
  line [HW sweep, H96 MAX M9, 2026-09-27]. No submit writes until the power domain collapses.
  An unwritten output keeps what the CPU left in its BO, which can read as a computed wrong
  value.
- **Workaround:** Software must let the NPU power domain collapse before the next submit, or
  write through the whole nine-word output stage
  ([The wide-output hazard](rk3576-hazards.md#the-wide-output-hazard)).
- **Status:** Open.

### Erratum RK3576-E3: output tail lost at the DPU drain deadline

- **Description:** The RK3576 raises `PC_DONE` when the program counter retires the descriptor,
  not when the pipeline behind it has finished. A driver that retires a job a fixed
  `dpu_grace_us` after `PC_DONE` can signal the fence while the DPU is still writing. The
  deadline is a fixed time, between 500 and 750 us at the measured shapes. The limit falls at
  about the same amount of work, not at a CBUF footprint. On the `112x112 k7 ic32` family it is
  766-830 MMACs [HW sweep, H96 MAX M9, 2026-08-05].
- **Conditions:** `rocket` 1.5.0, where `dpu_grace_us` is a deadline, 500 us by default.
  Measured on the direct convolution path at an NPU clock of 786 MHz, and on the int8 matmul
  entry at prefill shapes ([Dropped writes at the drain deadline](#dropped-writes-at-the-drain-deadline)).
  On `rocket` 1.6.0, `dpu_grace_us` = 0 is the default and means wait for the writing block.
  No loss was then measured on either path [HW sweep, H96 MAX M9]. On 1.6.0 a nonzero
  `dpu_grace_us` restores the deadline, and `ROCKET_JOB_NO_DPU_DONE` fences a job at the blind
  settle. Either brings the loss back.
- **Symptom:** The job completes and reports no error. The output has the correct size, and a
  suffix of it is never written. On the convolution path that is the row tail of the last
  output-channel group, or every row at an earlier cut. It resembles a CBUF row-allowance
  overrun. Every wrong element measured is a dropped write, never a wrong value
  [HW sweep, H96 MAX M9, 2026-08-05]. At a fixed shape the failure rate varies widely between
  identical runs.
- **Workaround:** Software must run on `rocket` 1.6.0 with `dpu_grace_us` at 0, or on 1.5.0 keep
  each program's drain inside the grace ([The direct path's drain
  deadline](rk3576-hazards.md#the-direct-paths-drain-deadline)).
- **Status:** Worked around in `rocket` 1.6.0, which waits for the writing block. `PC_DONE`
  still precedes the drain.

### Erratum RK3576-E4: average-pool divisor one window late

- **Description:** A padded average pool in exclude-pad mode intermittently divides an output
  window by the tap count of the previous window in raster order. The sum is right, and only the
  divisor is one output position late. Once the lag starts, it persists to the last channel
  group of the program. Its rate depends on the job's IOVA placement modulo 64 KiB, on whether
  the pool runs inside a chained kick, and on CPU-side DRAM traffic. The mechanism is not
  identified [HW sweep, H96 MAX M9].
- **Conditions:** A padded average pool with the pad excluded from the divisor, on the
  row-major and the cube-in paths. A max pool or a count-include-pad average has a constant
  divisor, so the lag cannot change its output. The lag is independent of RK3576-E2, and
  occurs with nothing submitted before it.
- **Symptom:** The output is written in full, with no fault. It is wrong at a few columns of
  every row, over a contiguous run of channel groups. The same geometry and entry fail on
  between ~0% and ~95% of calls, depending on the buffers the process allocated. In a graph the
  rate is about a third of calls, and a failing output has 30-40% of its observable elements
  wrong.
- **Workaround:** Software must check each padded exclude-pad average pool at the positions
  whose predecessor's tap count differs, and redo on a mismatch
  ([the divisor lag](rk3576-hazards.md#the-pooling-divisor-lag)).
- **Status:** Open.

### Erratum RK3576-E5: CPU cache writeback over a DPU output

- **Description:** A CPU write to an output BO leaves dirty cache lines. Their writeback races
  the DPU's DMA and can overwrite the result [HW sweep, H96 MAX M9, measured 2026-07-27].
  Detail: [The int32 output and the K split](#the-int32-output-and-the-k-split), and
  [rk3576-regcmd.md](rk3576-regcmd.md) §"Related hazards".
- **Conditions:** An output BO zeroed or stamped from the CPU before a submit, with no `PREP_BO`
  before the write and no `FINI_BO` after it.
- **Symptom:** A zeroed output comes back all zeros, intermittently, on the first submit as
  readily as on a later one. It looks like an arithmetic failure.
- **Workaround:** Software must bracket any CPU write to an output BO with `PREP_BO` and
  `FINI_BO` ([rk3576-regcmd.md](rk3576-regcmd.md) §"Related hazards").
- **Status:** Open.

### Erratum RK3576-E6: geometry extent wrapped past its field

- **Description:** The RK3576 computes each geometry extent with fewer bits than the register
  half that contains it. Width and output channels have 13 bits, the kernel 5 and the stride 3.
  An extent past its field wraps [HW sweep, H96 MAX M9, 2026-09-26]. Detail:
  [CNA register encoding](#cna-register-encoding), and
  [rk3576-regcmd.md](rk3576-regcmd.md) §"Geometry field widths" for each field's limit.
- **Conditions:** Any task whose width, output-channel count, kernel or stride exceeds its
  field.
- **Symptom:** No error is reported. Past the width, kernel or stride field, the task
  completes normally and writes an output of the correct size with incorrect values. Past the
  output-channel field, a depthwise task leaves its output unwritten and retires at the
  driver's 125 ms backstop on `rocket` 1.6.0. After a wrapped width, the next valid job in the
  same process is incorrect as well.
- **Workaround:** Software must keep every geometry extent within its field, and refuse one past
  it before the device sees it ([rk3576-regcmd.md](rk3576-regcmd.md) §"Geometry field widths").
- **Status:** Open.

### Erratum RK3576-E7: output from only the first submit of a power session

- **Description:** `PC_TASK_CON` packs `TASK_NUMBER` in its low bits. The field is 16 bits wide
  on the RK3576 and 12 on the RK3588 [source-confirmed]. A word built with the 12-bit field,
  such as `0x7001`, asks the RK3576's PC for a task count of 28673 instead of 1. The PC runs the
  one task it was handed and is left mid-stream.
- **Conditions:** A driver that builds `PC_TASK_CON` with the RK3588's 12-bit `TASK_NUMBER`, as
  mainline `rocket` does unconditionally, and submits within one NPU power session. The control
  bits above the field do not matter [HW sweep, H96 MAX M9, measured 2026-07-25].
- **Symptom:** Only the first submit of a power session writes output. Every later submit in the
  same session leaves its output buffer untouched. A gap past the 50 ms runtime-PM autosuspend
  hides the defect, because the power cycle resets the PC.
- **Workaround:** Software must build `PC_TASK_CON` with a 16-bit `TASK_NUMBER` on the RK3576
  ([`PC_TASK_CON` task-number width](#pc_task_con-task-number-width)).
- **Status:** Fixed by patch `0008`, which takes the width from per-SoC data. Gap-free submits
  are then byte-identical to each other and bit-exact against a CPU model
  [HW sweep, H96 MAX M9, measured 2026-07-25].

### Erratum RK3576-E8: kernel oops or heap corruption from an unprivileged client

- **Description:** Three defects in `rocket` are reachable by any `render`-group client. One
  malformed submit oopses the kernel (fixed by `0013`). A client that submits and closes without
  waiting leaves a use-after-free in the IOVA allocator (`0014`). A submit the kernel rejects
  for its task array frees the array twice, which corrupts the kmalloc-16 freelist (`0020`).
- **Conditions:** A `rocket` without patches `0013`, `0014` and `0020`.
- **Symptom:** A kernel Oops, or a fault in whatever allocates next. Tests still run after one
  Oops, but three Oopses take the file-close path into the IOMMU layer, and the board needs a
  reboot.
- **Workaround:** Software must run on a `rocket` that contains patches `0013`, `0014` and
  `0020` ([Memory-safety fixes](#memory-safety-fixes)).
- **Status:** Fixed by patches `0013`, `0014` and `0020`.

### Erratum RK3576-E9: incorrect first pooling outputs after a unit-kernel pool

- **Description:** A pooling program with a unit kernel on one axis changes the NPU's state for
  the next process. That process's first two pooling submits return incorrect output. The state
  clears itself after two pooling submits [HW sweep, H96 MAX M9, 2026-08-02]. Which register or
  state contains it is not identified. Detail:
  [Pooling state across processes](rk3576-hazards.md#pooling-state-across-processes).
- **Conditions:** A process that starts after a unit-kernel pooling program. The failure follows
  that program, and not a wide-output int32 program or no program at all. Measured on a k3 s2
  max pool at 16 channels.
- **Symptom:** The output has the correct size, and no error is reported. The failure is
  byte-identical every time. On a 16×16 plane 128 elements are wrong, one output row across all
  sixteen channels. On a 24×24 plane 2302 of 2304 elements are wrong.
- **Workaround:** Software must not rely on the first two pooling outputs of a process that
  follows a unit-kernel pooling program, and must verify them.
- **Status:** Open.

### Erratum RK3576-E10: early fence and board hang in a long chained stream

- **Description:** `PC_DONE` is raised per task. `PC_OPERATION_ENABLE` reads back 0 from the
  first poll of a running kick. Neither marks the end of a chained kick, and only a set
  `PC_DONE` together with a zero `PC_TASK_STATUS` (`0x48`) does. A driver can start its
  `dpu_grace_us` deadline on either of the first two signals. It then fences the job while the
  core is still writing, and programs the next job into a core still running the last one.
- **Conditions:** A `rocket` below interface version 1.4, which lacks patch `0022`, and a chained
  stream whose remaining run time outlasts the deadline. The deadline a stream needs is not
  monotone in its program count. The 500 us default falls inside the measured range
  [HW sweep, H96 MAX M9].
- **Symptom:** The caller reads an output that was never written. Past the bound the NPU raises
  a DMA write error, which `rocket_job_irq_handler()` takes as a `WARN_ON` (taint +512). The
  IOMMU then reports `Enable stall request timed out` and `FORCE_RESET command timed out`, and
  every later job fails. A chained stream of slow programs hangs the board: it answers no ping,
  and recovery needs a physical power cycle.
- **Workaround:** Software must not submit a long chained stream of slow programs to a kernel
  below interface 1.4 ([Completion on the task-status
  counter](../perf/rk3576-graph.md#completion-on-the-task-status-counter)).
- **Status:** Fixed by patch `0022` (interface 1.4).

### Erratum RK3576-E11: system hang during int8 matmul work

- **Description:** The whole board can hang during int8 matmul work. The cause is not known.
  The `performance` governor under an all-core load, the K-split submit, `dpu_grace_us`=0 and the
  test harness's structure are each excluded as a necessary condition. The hanging shape passes
  every bound `librocketnpu` models.
- **Conditions:** Kernel 7.1.6 with `rocket` 1.5.0 out of tree gave five system hangs. The last
  was at `M=128 K=2048 N=2048`, as one task in one submit, in one foreground process
  [HW sweep, H96 MAX M9]. On kernel 7.1.7 with `rocket` 1.6.0 in tree, 39 repetitions of 9 shapes in one boot,
  that shape included, did not hang [HW sweep 2026-08-10]. No single change between the two
  images is identified as the fix.
- **Symptom:** The library prints its initialization lines and nothing else. The board leaves
  the network before a 120 s `timeout` can act, and only a power cycle recovers it.
- **Workaround:** Software must read the board's module version and parameter block before
  running a matmul shape not yet run on that module ([System hang during matmul
  work](#system-hang-during-matmul-work)).
- **Status:** Not reproduced on `rocket` 1.6.0. Whether the SoC can still hang on 1.6.0 is not
  characterized.

### Erratum RK3576-E12: NPU wedge in the int32 K split

- **Description:** An int8 matmul that takes the int32 K split can wedge the NPU until a reboot
  [HW sweep 2026-08-05]. The wedge's register program has no value near its register's width,
  and it passes every library bound. The cause therefore lies outside `librocketnpu`'s model of
  the NPU.
- **Conditions:** Measured at one shape, `M=512 K=8192 N=2048`: plane 32×16, K slice 4608, 2
  slices, N tile 256, the narrow writer and 256 submits, on `rocket` 1.5.0. The dense int32
  writer runs the same shape exactly (Detail). The K split begins at `K >= 6176` for
  every `(M, N)` measured [host-computed 2026-08-06]. No narrower boundary inside that class is
  measured, and small matmuls in the class run exactly.
- **Symptom:** The driver raises its DMA-error interrupt, one of `rocket_job_irq_handler`'s two
  `WARN_ON`s over `PC_INTERRUPT_RAW_STATUS_DMA_{READ,WRITE}_ERROR`. Afterwards the NPU is
  unusable in every process, and shapes that ran clean minutes earlier fail. A
  `rmmod`/`modprobe` does not recover it: core 0 then fails to probe with `-22`, alongside
  `rk_iommu … FORCE_RESET command timed out`. Only a reboot clears it.
- **Workaround:** Software must run a matmul with `K >= 6176` on the dense int32 writer or on
  the host, not on the narrow writer ([The K-split wedge](#the-k-split-wedge)).
- **Status:** Open.

### Erratum RK3576-E13: int32 output unwritten on an NPU pinned runtime-active

- **Description:** `rocket_job_run()` takes a runtime-PM reference and then attaches the IOMMU
  group. Both of its early returns leave a reference that nothing drops and a fence that
  nothing signals, and each pins the device runtime-`active`. The reference is on the platform
  device, so `rmmod`/`insmod` does not clear it. Only a power-domain cycle clears the state
  RK3576-E2 leaves, and the pinned domain does not cycle [HW sweep, H96 MAX M9, measured
  2026-07-27].
- **Conditions:** Mainline `rocket` without patch `0010`. The fault is present on the RK3588 as
  well. Without `0010` the state sustains itself. One failed attach times out, the timeout
  path's core reset takes the IOMMU down, and the next attach fails as well.
- **Symptom:** Convolutions still run bit-exactly, and every int32 matmul on the narrow writer
  writes nothing. The symptom looks like a defect in the int32 writer.
- **Workaround:** Software must run a `rocket` that contains patch `0010`, and check
  `power/runtime_status` before trusting an int32 result ([Per-job core reset and the
  half-started job](#per-job-core-reset-and-the-half-started-job)).
- **Status:** Fixed by patch `0010`.

## Performance

### Cost of the library entries

Each public RK3576 entry with a CPU reference is 2.1-90.6x faster than a single-threaded scalar
CPU loop over the same tensors.

**Conditions:** H96 MAX M9, kernel 7.1.7 with `rocket` 1.6.0 in-tree, `dpu_grace_us` 0, the
`ondemand` governor, the driver's default 50 ms autosuspend delay, measured 2026-08-10.

The NPU column is the whole public entry, the cost a frontend sees. It covers host packing into
the cubes, the submits and the de-tile back to row-major, and it is not a kernel time. The
CPU column is a single-threaded scalar direct loop over the same tensors, auto-vectorized at the
library's own optimization level. It has no im2col, no packing and no threading, so it is a
reference rather than a tuned kernel.

Each ratio is therefore an upper bound against a tuned kernel. A good NEON GEMM across the four
A72s would close much of every one of them. Rows vary 20-40% run to run. [HW sweep, H96 MAX M9]

| Shape | NPU ms | CPU ref ms | ratio |
|---|---|---|---|
| stem 3×224×224 k3 s2 oc32, int8 | 3.21 | 41.7 | 13.0x |
| stem 3×224×224 k3 s2 oc64, int8 | 4.62 | 83.1 | 18.0x |
| stem 3×224×224 k7 s2 oc32, int8 | 3.12 | 188.8 | 60.6x |
| stem 3×224×224 k3 s2 oc32, fp16 | 13.98 | n/a | n/a |
| conv 32->64 k1 56×56 | 2.41 | 12.0 | 5.0x |
| conv 64->64 k3 56×56 | 2.68 | 242.8 | 90.6x |
| conv 128->128 k3 28×28 | 2.52 | 186.9 | 74.3x |
| conv 256->256 k3 14×14 | 4.44 | 185.0 | 41.7x |
| conv 256->512 k1 14×14 | 1.87 | 52.3 | 28.0x |
| depthwise 64 k3 56×56 | 2.36 | 7.5 | 3.2x |
| depthwise 128 k3 28×28 | 1.42 | 4.0 | 2.9x |
| depthwise 256 k3 14×14 | 1.07 | 2.2 | 2.1x |
| matmul 32×1024×1024 | 4.32 | 13.3 | 3.1x |
| matmul 32×1024×2560 | 9.78 | 31.1 | 3.2x |
| matmul 128×1024×1024 | 5.20 | 52.8 | 10.2x |
| matmul 256×512×2048 | 7.12 | 106.5 | 15.0x |

The table shows four results at this operating point:

- **Submit cost.** A submit costs about 340 us (§"Per-submit overhead and the completion poll"),
  and the submit-bound rows track it.
- **Depthwise.** Depthwise convolution is 2.1-3.2x faster than the CPU reference. Against a
  threaded CPU kernel it would be close. A depthwise convolution has `ic` times fewer MACs than
  a direct one at the same shape. The same per-submit cost therefore gives `ic` times less work. Batching several
  depthwise layers into one submit is the optimization the encoding would have to supply.
- **Matmul.** N is the axis that sets matmul throughput, and the planner already uses it. At M=32
  the planner puts K=N=1024 in a single submit, the largest N tile the RK3576 takes. The matmul
  at low M is therefore not dispatch-bound. Its limit was the host cube scatter, below.
- **Stem.** The quantized stem is the one to run, but the gap is 3.21 ms against 13.98, not
  against 226. Driving the power cycle the fp16 path's guard waits for closes the gap, not
  arithmetic. The remainder is one real cycle per call. The fp16 programs raise their own DPU
  completion on `rocket` 1.6.0 (§"Retirement on the DPU completion"), but at this measurement
  `librocketnpu` submitted them under `ROCKET_JOB_NO_DPU_DONE`. Each fp16 job therefore fenced
  at the `dpu_blind_us` settle past `PC_DONE`, not on that completion. Without the flag, as the
  library submits them, an fp16 job fences on its own completion.

#### The host cube scatter

The host cube scatter packs row-major tensors into the RK3576's cubes and de-tiles the
results back. Done an element at a time through the index functions, it costs a divide, a modulo
and a call per byte. Done that way, it takes most of a call's wall-clock time, more than the
submit. At
K=N=1024 that is a million of them, and twelve of that matmul's thirteen milliseconds.
[HW sweep, H96 MAX M9]

Three of the scatters are block copies once the index is written out. At `kh=kw=1`,
`weight_conv_int8()` puts thirty-two consecutive contraction elements at thirty-two consecutive
bytes on both sides, and `feature_data()` at C2=16 does the same for sixteen. The matmul's
feature pack, weight pack and output de-tile are therefore blocked memcpys. The convolution
entries stay a real transpose, CHW against NC1HWC2, with a strided store, and their per-element
division hoists out to one pair per channel. The cost table above is measured with the block
copies.

The convolution entries' weight side has two more host loops of this kind. Both are functions of
the weights alone, and done per element, each walks a million elements through index arithmetic.
Only a whole graph, not a single shape, shows them:

- The per-output-channel filter sums, a contiguous scan written as a triple-nested index
  expression.
- The weight cube scatter. Its `taps == 1` case is thirty-two contiguous source bytes going to
  thirty-two contiguous cube bytes, a run of block moves rather than byte stores.

Straightening both takes MobileNetV1's graph from 146 ms to 115 ms, with every layer still
bit-exact [HW sweep, H96 MAX M9, 2026-07-29]. Setting `ROCKET_RK3576_INT8_PROF=1` splits a
call's time into its operand packs, its submits and its de-tile.

A pixel-outer, channel-inner feature scatter is slower on the RK3576. It fills each C2-byte atom
in one go, and touches every destination line once instead of once per channel. It needs C2
concurrent read streams, though. On the graph it costs the depthwise layers more than it saves
the 1×1 ones: layer 3's feature pack goes from 3.2 to 5.3 ms. The scatter stays channel-outer,
with one sequential read stream and a strided store.

#### The int8 matmul entry

On the RK3576 an int8 matmul is a 1×1 convolution, which the convolution's register program runs
unchanged. Its M axis, its contraction width, its throughput along N and its two output-channel
bounds are in [rk3576-regcmd.md §"The matmul as a 1×1
convolution"](rk3576-regcmd.md#the-matmul-as-a-11-convolution). Two properties differ from the
RK3588:

- **Precision.** One int8 task contracts `ic*kh*kw` up to 4608, and one task of the fp16
  convolution program contracts sixteen input channels. A matmul lowered onto that fp16 program
  therefore costs 30-299x the int8 one. The matmul-form fp16 program contracts the whole K in one
  task, and at a prefill's M costs about twice the int8 matmul (§"The precision fork"). On the
  RK3588 fp16 is faster, and int8 saves only RAM.
- **Output.** The output is int8, through the DPU's requant, where the RK3588's int8 matmul writes
  raw int32 and sums K partials on the host. Inside one task's contraction the requant is the
  DPU's own, which is the fast path. A K with no single-task plan, `K >= 6176`, is declined
  (§"The K-split wedge").

`rocket_matmul_int8_rk3576()` is the userspace layer around the convolution. It is a separate
entry, not a path behind `rocket_matmul_int8()`, because of the output difference. Its work is:

- The operand scatter into the RK3576's cubes
- The output de-tile
- The tiling planner
- The per-chip dispatch point

Its CBUF planner refuses both output-channel bounds. The default tile of 2048 sits far enough
inside them to act as a guard. A CPU model holds the entry bit-exact over 33 shapes.

#### The int8 GEMM against a real CPU GEMM, at LLM prefill shapes

Against a tuned CPU GEMM at the shapes an LLM prefill issues, `rocket_matmul_int8_rk3576()` is
3.3-6.8x faster. The median is 5.4x over the six shapes with correct output.
[HW sweep, H96 MAX M9, measured 2026-08-05]

**Conditions:** H96 MAX M9, measured 2026-08-05. `M` is the ubatch, never 1. The NPU column is
the whole public entry: the host pack of A and B into the cubes, the submits and the de-tile.
The CPU column is the fastest of ggml's F32 `MUL_MAT`, ggml's Q8_0 `MUL_MAT` and OpenBLAS
`cblas_sgemm`, on four threads on the A72s.

| M / K / N | NPU ms | best CPU ms | ratio |
|---|---:|---:|---:|
| 512 / 2048 / 512 | 10.29 | 34.39 | 3.34x |
| 512 / 2048 / 2048 | 28.20 | 133.22 | 4.72x |
| 1024 / 2048 / 2048 | 48.50 | 267.79 | 5.52x |
| 2048 / 2048 / 2048 | 78.70 | 532.24 | 6.76x |
| 512 / 2048 / 8192 | 91.07 | 533.27 | 5.86x |
| 512 / 4096 / 4096 | 100.13 | 531.80 | 5.31x |

The ggml Q8_0 kernel is the fastest CPU configuration at every shape: 3.2x its own F32, and a few
percent under OpenBLAS. The RK3576's CPU cores are ARMv8.0-A (`/proc/cpuinfo` has no `asimddp` and
no `asimdhp`), so they have no SDOT and no fp16 arithmetic. A CPU with the dot-product extension
would close some of this gap.

The ratio rises with M because a fixed cost amortizes. At K=N=2048 over four values of M, the
entry fits `T(M) = 10.9 + 0.0337*M` ms. The intercept is M-independent work: B's cube pack plus
the per-call BO allocation and teardown. It is 39% of the M=512 wall-clock time and 14% of the
M=2048 one.

The entry re-packs B on every call. The resident-weight entry
`rocket_matmul_int8_rk3576_perc_wbo()` packs B once into a device BO
([../perf/rk3576-w8a8-llm.md](../perf/rk3576-w8a8-llm.md#supplied-sums-the-resident-weight-cube-and-the-bo-pool)).
At 512×2048×2048 its call measures 12.5-13.0 ms with the BO pool off [HW sweep, H96 MAX M9,
`rocket` 1.6.0, 786 MHz, 2026-09-25] (§"Cost at a prefill's M").

Weighted by a model's MAC shares, the ratio is smaller. A Llama-3.2-1B-shaped layer at ubatch 512
has MAC shares of 17% for attention QKVO, 55% for gate/up and 28% for down. With those weights,
and the down-projection left on the CPU because the entry declines its K (§"The K-split wedge"),
one layer is 2.39x, not 5.4x [host-computed, 2026-08-05]. That figure covers the GEMMs alone.
A second weighting of the GEMMs on 2026-08-10 gave 2.44x, and with a W8A8 path's host rotation
and quantization added, 2.37x
([../perf/rk3576-w8a8-llm.md](../perf/rk3576-w8a8-llm.md#host-cost-of-the-rotation-and-quantization)).
**Not characterized:** what separates the two GEMM-only weightings, 2.39x and 2.44x.

#### Cost at M = 1 and the decode projection

At M = 1 the call costs its M-independent intercept, so the transient entry is not a decode
engine. About 94% of an M = 1 call is machinery that a resident-weight path would not run: the
weight pack and the BO round trip.

**Conditions:** H96 MAX M9, kernel 7.1.7 with `rocket` 1.6.0 in-tree, the `ondemand` governor,
measured 2026-08-18/19.

| shape | NPU ms | CPU ms | ratio |
|---|---:|---:|---:|
| matmul 1×1024×1024 | 3.88 | 0.43 | 0.11x |
| matmul 1×2048×1024 | 8.72 | 0.78 | 0.09x |
| matmul 1×1536×1536 | 8.25 | 0.94 | 0.11x |
| matmul 32×2048×1024 | 7.85 | 24.63 | 3.14x |

[HW sweep, H96 MAX M9, 7.1.7 / `rocket` 1.6.0 in-tree, `ondemand`, 2026-08-18/19]

At the same K and N, M = 1 tracks M = 32 within 3-11%, which measures the intercept a second
way. The profiler `ROCKET_MM_PROFILE` splits the whole call into buckets: the entry's setup, its
BO teardown and its own entry-spanning time. At 1×2048×1024 the buckets measure:

| Bucket | ms/call |
|---|---:|
| `packB` | 3.27 |
| `alloc` | 2.36 |
| `bofree` | 1.18 |
| submit plus fence wait | ~0.27 |
| everything else | ~0 |

[HW sweep, H96 MAX M9, 7.1.7 / `rocket` 1.6.0 in-tree, `ondemand`, 2026-08-18/19]

The machinery is the pack and the five-BO create/mmap/munmap/GEM_CLOSE round trip. The packB cache
and the BO pool that remove it are in
[../perf/rk3576-w8a8-llm.md](../perf/rk3576-w8a8-llm.md#supplied-sums-the-resident-weight-cube-and-the-bo-pool). The teardown term is M-independent:
1.18 ms/call at M = 32 too, and 0.91 at 1×1024×1024. The write guard's read and every PREP/FINI
pair are inside other buckets.

The device-side remainder follows a weight-fetch line. The fence-wait marginal between the
1.05 MB and 2.10 MB rows is 86 us/MB, to about +-60 us/MB. The charsiu project fits 84.3 us/MB on
a ROCK 4D through its own kernel (`github.com/gahingwoo/charsiu`, chained tasks, 2026-08-15). The
two are the same regime, not the same number.

Decode cost with the transient machinery gone is a projection [expected], untested end to end.
A resident, chained M = 1 path costs the bytes term: an int8 model's weights once per token at
~86 us/MB. A CPU GEMV has the same DRAM cost on the RK3576, where one A72 thread saturates
memory. With int8 weights, NPU decode therefore projects to parity with the CPU rather than a
gain. Halving the bytes (int4) is the optimization that would move it.

The charsiu project reaches the same conclusion from the vendor side. The vendor runtime runs
M = 1 NPU decode at ~13 tokens/s on Llama-3.2-1B (their measurement, their board, their kernel).

### W8A8 LLM prefill

`ggml-rocket`'s W8A8 path drives the int8 matmul entry from stock llama.cpp. On Qwen2.5-1.5B at
`pp2048`, its prefill is 1.31x the CPU's Q8_0 kernel [HW sweep, `rocket` 1.6.0, 2026-08-23]. It
is 2.37x the same F16 GGUF on the CPU. At `pp512` the two ratios are 1.02x and 2.01x
[HW sweep, 2026-08-11]. That mean averages one calibrating timed rep with converged ones
[hypothesis]. Its
wikitext-2 perplexity is 1.011x the CPU's [HW sweep, 2026-08-11].

The path needs a Hadamard
rotation and a per-column requant to reach that accuracy.
[../perf/rk3576-w8a8-llm.md](../perf/rk3576-w8a8-llm.md) gives the port, its accuracy, its
calibration and its conditions.

### The precision fork: what the op library should be founded on here

The matmul-form fp16 program, its accumulation, its bf16 form and its single-task limits are in
§"The fp16 matmul program".

The RK3588's composed op library is built on the fp16 matmul. It comprises:

- The norms
- Softmax
- The gated FFN
- Attention
- The ViT/Whisper encoder blocks

That foundation does not port to the RK3576, and the choice of what to put in its place is a
decision rather than a port. `librocketnpu`'s fp16 convolution program is not a matmul precision
here. One int8 task contracts `ic*kh*kw <= 4608`, and one task of that fp16 program contracts
exactly sixteen input channels. The same K therefore costs one submit against 288, and the
measured ratio runs 30x to 299x over ordinary shapes. Anything that lowers to that program
inherits the ratio. The sixteen channels are the convolution program's bound, not the SoC's,
because the matmul-form program contracts K in one task.

#### Cost against the int8 entry

**Conditions:** H96 MAX M9, `rocket` 1.6.0, NPU 786 MHz, both CPU clusters at governor
`performance`, 2026-09-25 UTC.

On the device, the fp16 program costs what int8 costs at N 64, and more at K 2048 N 256. From
submit to fence, with its buffers packed once, the program takes 0.076-0.084 ms to K 2048 at
N 64, the int8 entry's per-submit cost there. At K 2048 N 256 it takes 0.12-0.19 ms. In one
process at those two shapes, the fp16 program's device time is 0.122 ms at 1×2048×256 and
0.173 ms at 16×2048×256. The whole pooled int8 resident call is 0.102 ms and 0.136 ms there,
device time included. The fp16 weight is twice the int8 weight's bytes, which is the likely
cause [hypothesis]. [HW sweep]

Paired in one process against `rocket_matmul_int8_rk3576_perc_wbo()`, the resident int8 entry
an LLM's GEMMs call, the resident fp16 entry measures [HW sweep]:

| Shape (M×K×N) | fp16 resident | int8 resident | Ratio |
|---|---:|---:|---:|
| 14 shapes to K 2048 at N 64, or K 512 at N 256 | 0.23-0.26 ms | 0.26-0.29 ms | 0.86-0.94x |
| 1×2048×256 | 0.32 ms | 0.30 ms | 1.07x |
| 16×2048×64 | 0.43 ms | 0.38 ms | 1.15x |
| 16×2048×256 | 0.59 ms | 0.40 ms | 1.50x |

The ratios above 1x come from the device time above, plus larger per-call buffers. The fp16
activation is twice the bytes, and its output four times. What is left per call is buffer
allocation, which fits as about 0.03 ms a BO plus 9 us a 4 KiB page. With
`ROCKET_RK3576_BO_POOL=1` and one entry per process, the resident call sits 0.014-0.043 ms above
its device time at every shape. [HW sweep]

> [!NOTE]
> A pooled cost depends on the pool's history. A pooled BO keeps the size it was allocated at,
> and a request takes the smallest free BO that covers it. After the mix of entries or shapes
> changes, a small request can hold a far larger buffer. The `PREP_BO` and `FINI_BO` ioctls
> sync the whole BO every call.

Five entries sharing one pool put the fp16 resident call 0.09-0.16 ms above its device time at 9
of 18 shapes, not monotone in any size. The resident entry alone, whose three buffers are all
small, stays at the single-entry figure above at all 18. The per-call entry alone still steps,
from 0.147 to 0.185 ms between its first two shapes. By the matching arithmetic, its 8 KiB weight
request is served by a 257 KiB BO the coefficients left [hypothesis]. [HW sweep, same board,
2026-09-25 UTC]

#### Cost at a prefill's M

**Conditions:** H96 MAX M9, `rocket` 1.6.0, NPU 786 MHz, governor `performance`, host on the
A72s, 2026-09-25 UTC. Both entries are resident and paired within a round, with the BO pool off.

Past one task the fp16 call costs about twice the int8 call, and the gap does not shrink as M
grows [HW sweep]:

| Shape (M×K×N) | fp16 resident | int8 resident | Ratio |
|---|---:|---:|---:|
| 16×1536×1536 | 1.06 ms | 0.67-0.71 ms | 1.5-1.6x |
| 64×1536×1536 | 2.44-2.46 ms | 1.25-1.26 ms | 2.0x |
| 128×1536×1536 and 256×1536×1536 | 4.7 and 9.1 ms | 2.2 and 4.1-4.2 ms | 2.2x |
| 512×1536×1536 | 17.5-17.8 ms | 8.5-8.7 ms | 2.0-2.1x |
| 512×1536×256 | 7.4-7.6 ms | 4.1 ms | 1.8-1.9x |
| 512×1536×4096 | 37.6-38.2 ms | 18.0-19.3 ms | 2.0-2.1x |
| 512×1536×8192 | 84.4-85.5 ms | 32.3-32.6 ms | 2.6x |
| 512×256×1536 | 11.7-11.8 ms | 4.3 ms | 2.7x |
| 512×4096×1536 | 39.0-39.6 ms | 20.5-21.1 ms | 1.9-2.0x |
| 512×6144×1536 | 86.2-86.4 ms | 87.1-90.3 ms | 1.0x |
| 512×2048×2048 | 24.6-24.7 ms | 12.5-13.0 ms | 1.9-2.0x |

The device time sets the ratio. At 512×1536×1536 the fp16 job takes 4.5 ms from submit to fence,
and the int8 entry's four submits take 2.1 ms by its own profile. Each fp16 task re-reads the
whole weight, and at that shape the program contracts at about half the int8 program's rate. The
two tie at K 6144 because the int8 entry slows there, while the fp16 program does not speed up.

The rest of the fp16 call is its per-call buffers. Allocating and freeing them is 7.2 ms of the
17.5-17.8. With `ROCKET_RK3576_BO_POOL=1`, one entry a process, the fp16 call is 6.9 ms against
the int8 call's 4.8, 1.4x. [HW sweep]

#### The int8 path's host terms

**Conditions:** H96 MAX M9, `rocket` 1.6.0, NPU 786 MHz, Qwen2.5-1.5B F16 on llama.cpp b10356,
`pp2048 -ub 512`, four A72 threads, governor `performance`, BO pool off, 2026-09-25.

An fp16 path would skip three host passes the int8 path makes around every GEMM: rotating and
quantizing the activation, and dequantizing the output. It would add one, narrowing the
activation to fp16. The frontend profiler measures each per GEMM shape, inside the model
[HW sweep]:

| M 512, K 1536, N | Projections | Calls reusing the previous activation | `quant+rot` | `dequant` | fp16 narrowing |
|---|---|---|---:|---:|---:|
| 1536 | q, o | none | 7.48-7.56 ms | 0.90-0.91 ms | 0.50 ms |
| 256 | k, v | all | 7.48-7.56 ms | 0.152 ms | 0.50 ms |
| 8960 | gate, up | half | 7.39-7.60 ms | 5.32-5.41 ms | 0.50 ms |

`quant+rot` depends on M·K alone, about 9.5 ns an element on the one thread that dispatches.
The entry measures 1-10% above its resident cost from the standalone library measurement. The
processes, which ran the frontend profiler's per-shape buckets on the 2026-09-25 build, measure
12.70-12.83 t/s.

Path against path, the int8 path is those host terms plus the resident int8 call. The fp16 path
is the narrowing plus the resident fp16 call. The fp16 entry takes N up to 8192, so N 8960 is
costed as two calls of N 4480. The fp16 device time grows faster than N: 11.3 ms at N 4480 and
35.7 ms at N 8192. Resident costs are measured one entry a process.

| Shape | int8 path, pool off | int8 path, pool on | fp16 path, pool off | fp16 path, pool on | fp16/int8, pool off | fp16/int8, pool on |
|---|---:|---:|---:|---:|---:|---:|
| 512×1536×1536 | 17.0 ms | 13.2 ms | 18.4 ms | 7.4 ms | 1.08x | 0.56x |
| 512×1536×256 | 11.7 ms | 9.5 ms | 8.1 ms | 3.0 ms | 0.69x | 0.32x |
| 512×1536×8960 | 50.9 ms | 41.9 ms | 81.5 ms | 34.5 ms | 1.60x | 0.82x |
| One layer, two of each | 159 ms | 129 ms | 216 ms | 90 ms | 1.36x | 0.70x |

[HW sweep, same board and date]

The host terms decide the pooled comparison and not the unpooled one. At 512×1536×1536 they come
to 7.9 ms net of the narrowing. The host terms exceed the pooled fp16 excess of 2.1 ms and fall
below the unpooled one of 9.3 ms. Unpooled, the fp16 call is its buffers: 29 of its 40.5 ms at
N 4480.

In prefill wall-clock time the comparison is small. The offloaded GEMMs are about 17.4 s of the
160 s a `pp2048` takes here, 11%, with the pool off. Pooled, an fp16 path takes 4.4 s off, 2.7%
of the wall-clock time, and unpooled it adds 6.1 s [host-computed].

Half of the pooled 4.4 s is repeat work. The k and v projections rotate and quantize q's
activation again, and up does gate's. Quantizing each activation once removes 2.5 s by the same
arithmetic. The rest is single-threaded host work beside three idle A72s [expected].

**Not characterized:** four terms the comparison leaves out:

- Accuracy (the int8 path is 1.011x perplexity)
- An fp16 K split for `ffn_down` (K 8960 is past the fp16 entry's 6144)
- Another model or `-ub`
- Calibration

The int8 path calibrates on its first two forward passes, 21.9-22.1 s a process here. A
`llama-bench` warm-up hides that time, and a process's first prompt incurs it. An fp16 path has
no calibration.

#### Outcome of the precision fork

The fork does not turn on speed. The int8 path's host terms exceed the fp16 GEMM's extra cost
only with the BO pool on. Even then the fp16 path saves 2.7% of Qwen2.5-1.5B's prefill
wall-clock time, and half of that is removable on the int8 side. At M 16 the matmul form costs
0.86-1.15x the int8 resident entry and needs no power-cycle guard. At a prefill's M its GEMM
costs about twice the int8 one.

The int8 matmul serves the GEMMs but not the reductions. The entry `rocket_matmul_int8_rk3576()`
is fast and bit-exact, but its output goes through the DPU's requant and is int8. The RK3588
builds RMSNorm, softmax's row sums and every ReduceMean as a matmul by a ones vector. A
reduction of that kind needs an accumulator wider than its operands, and an int8 output
saturates on the first long row. The 32-bit entry, `rocket_matmul_int8_rk3576_i32()`, runs on
the dense writer ([rk3576-hazards.md](rk3576-hazards.md) §"The whole output stage"). It does not
corrupt the next submit, idles only on a redo, and one task writes a 38 KiB output exactly.

The older int32 writers are the wrong instrument for a per-layer norm for three reasons, and the
dense writer removes two of them. The older writers corrupt the next submit and need a power
cycle for it, and their output is bounded at 8 KiB a task. The matmul test's 21 int32 shapes are
exact on the dense writer in 0.26 s, against 6.3 s on the older ones
(`ROCKET_RK3576_I32_DENSE=0`). [HW sweep, H96 MAX M9, rocket 1.6.0, 2026-09-30]

> [!CAUTION]
> On the narrow int32 writer, the shape M 512 K 8192 N 2048 takes the SoC down until a reboot.
> Software must run that shape on the dense writer, where it completes in 345.7 ms and 48 submits
> with no redo. Its 4096 sampled elements are exact [HW sweep, H96 MAX M9, rocket 1.6.0,
> 2026-09-30].

The third reason is not characterized on the dense writer. The older writers drop atoms at a rate
the memory system sets, so the library keeps its sentinel scan.

On the RK3576 the transformer composition stays on the CPU, and the NPU runs four kinds of op:

- Convolution
- int8 GEMM
- Pooling
- LUT activations

That decision rests in part on the fp16 cost above, which the int8 host terms do not repay.

The three operations that support the decision are all on the convolution and DPU side rather
than the matmul side. The direct and depthwise int8 convolutions and the int8 first conv are
bit-exact, and 2.1-90.6x faster than a single-threaded scalar CPU loop (§"Cost of the library
entries"). The PPU gives pooling as an independent 31-write
program in the cube the conv path already packs, and the DPU LUT gives the nonlinear activations.
Together they form a CNN, detection and classification stack, the workload this silicon is
shaped for.

All four parts that decision named are implemented and tested:

- Per-output-channel weight scales on the direct and depthwise paths and through a graph
- The PPU pooling emitter
- The DPU LUT and its activation entry
- A whole network

### A whole network

MobileNetV1-224 at int8 runs end to end on the RK3576 and returns TFLite's own label. The graph
is 27 convolutions, a PPU pooling layer and a classifier. Every one of the 29 compute layers is
bit-exact against a CPU model of the RK3576's arithmetic. The whole graph's wall-clock time per
inference depends on which optimizations are in place:

**Conditions:** H96 MAX M9, MobileNetV1-224 int8. Each row is its own measurement, taken as its
optimization was added, from 2026-07-29 (the bottom row) to 2026-08-03 (the top row).

| Configuration | Wall-clock time per inference |
|---|---:|
| The pooling layer inside the kick, so the whole graph is one kick in one submit | **4.9-5.0 ms** |
| Resident weights, tensors kept in cube layout between layers, each chained run of cube-joined layers as one hardware kick, and the pooling layer resident, reading its input as a cube and retiring on the PPU's own completion | 5.1 ms |
| The same with the pooling layer transient, scattering its input on the host, allocating its buffers per call and retiring at the `dpu_grace_us` deadline | 6.2 ms |
| One submit per layer | 10.4-10.5 ms |
| The transposes at every layer boundary | 21 ms |
| No resident weights at all | 98.8 ms |

[../perf/rk3576-graph.md](../perf/rk3576-graph.md) takes that difference apart and measures each
part of it. It also gives the planner, the TFLite delegate's results on five classifiers and two
detectors, and the composition of a graph's wall-clock time.
