# RK3566 SoC parameter sheet

## Overview

The RK3566 and RK3568 integrate the small [RKNPU](../GLOSSARY.md): a single core rated at
0.8 TOPS [source-confirmed: RK3568 `rocket` RFC]. The RK3588 has 3 cores and the RK3576 has 2.
The upstream RK3568 `rocket` RFC (per-SoC `num_cores` / `dma_bits` from the driver's match
data, selected by the `compatible` string) was written for this NPU. As a port
target, the RK3566 therefore tests mainly the core-count and DMA-width axis of portability. The
RK3576 tests the register-encoding axis (its re-packed CNA/CORE/DPU geometry map).

## Support status

> Do not assume an RK3588 machine parameter on the RK3566. Confirm each one on hardware.

## Register offset map

The RK3568 RFC reports the same NVDLA core as the RK3588. Its PC, CNA and CORE register
regions, its interrupt and its IOMMU follow the RK3588's layout [source-confirmed]. The series'
v2 cover letter (2026-05-29) also reports that several shape-independent register values
differ.

The cover letter places each block's `OPERATION_ENABLE` at offset `0x_00c`, not the RK3588's
`0x_008` [external: the v2 cover letter]. Its vendor captures write nothing at `0x_008` and
multi-bit values at `0x_00c`. Those captures do not separate the two SoCs. No RK3588 or RK3576
program these notes use writes a per-block `OPERATION_ENABLE`, because the trailer's bitmap
starts a task's blocks ([../encodings/regcmd-task-model.md](../encodings/regcmd-task-model.md)).
The capture's DPU_RDMA value, `0x13f` at `0x500C`, is the RK3588 map's cube width for a
320-wide output, the YOLOv5s first layer's [host-computed]. The `0x_00c` values are therefore
probably geometry and mode words [hypothesis].

The RK3566 therefore likely shares the RK3588 geometry-register encoding, with the CNA block not
re-packed as it is on the RK3576 [expected]. If it does, it needs a `rocket_hw_profile` (core
count, DMA width, datatype menu) and any value changes in the regcmd, not the per-chip regcmd
encoder the RK3576 requires. Confirm on hardware before relying on it.
